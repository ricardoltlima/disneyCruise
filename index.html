Java 16, Java 17, and Java 21 Features

Modern Java adds concise data modeling, safer type handling, stronger domain modeling, better concurrency options, and cleaner syntax for everyday backend code.

Java 16

Records

Records are compact immutable data carriers. Java generates the constructor, accessors, equals, hashCode, and toString.

public record ReservationResponse(
        Long id,
        String guestName,
        String status
) {}

Not all methods in a record are final. The record class itself is final, and the immutability comes from private final fields, no setters, and the canonical constructor initializing all fields.

Records are immutable because their fields are private final, they have no setters, and their state is fully initialized in the canonical constructor. This immutability is ideal for functional programming because it eliminates side effects, makes objects thread-safe, and ensures predictable behavior when passed through pipelines such as Stream or Reactor.

Use records for DTOs, API responses, commands, events, and value-style objects where identity and mutation are not the main concern.

Pattern Matching for instanceof

Pattern matching removes the extra cast after an instanceof check and keeps type checks easier to read.

if (event instanceof ReservationCreated created) {
    return created.reservationId();
}

This is useful when handling events, exceptions, request payload variants, or generic domain objects.

Java 17

Sealed Classes and Interfaces

Sealed types restrict which classes or records can implement or extend a type. They make domain models explicit and easier to reason about.

public sealed interface PaymentEvent
        permits PaymentAuthorized, PaymentDeclined {}

public record PaymentAuthorized(String paymentId)
        implements PaymentEvent {}

public record PaymentDeclined(String paymentId, String reason)
        implements PaymentEvent {}

How do records work with sealed interfaces?

Records can implement sealed interfaces naturally because they are implicitly final, which satisfies the requirement of a sealed hierarchy. Since a sealed parent allows only subclasses that are final, sealed, or non-sealed, a record fits perfectly. The only rule is that the record must appear in the permits list of the sealed type. This makes records a great fit for modeling immutable domain events.

Use sealed hierarchies when the list of allowed variants is known, such as workflow states, commands, events, and result types.

Switch Expressions

Switch expressions return values directly and avoid fall-through bugs from missing break statements.

String message = switch (status) {
    case "CONFIRMED" -> "Reservation is confirmed";
    case "CANCELLED" -> "Reservation is cancelled";
    case "PENDING" -> "Reservation is pending";
    default -> "Unknown reservation status";
};

They are a good fit for mapping states, roles, event types, and simple decision tables.

Text Blocks

Text blocks make multiline strings cleaner. They are helpful for SQL, JSON examples, logs, documentation snippets, and test fixtures.

String json = """
        {
          "reservationId": "R123",
          "status": "CONFIRMED"
        }
        """;

Strong LTS Baseline

Java 17 is a long-term support release and a common modern baseline for Spring Boot services. It combines records, sealed types, text blocks, switch expressions, and JVM/runtime improvements into a stable platform.

Java 21

Virtual Threads

Virtual threads are lightweight JVM-managed threads. They make blocking-style code scale better when work spends most of its time waiting on I/O.

try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    executor.submit(() -> reservationClient.fetchReservation(id));
}

They are useful for servlet-style services and blocking libraries. They do not remove the need for timeouts, connection pool limits, backpressure thinking, or careful resource management.

Pattern Matching for switch

Switch can match by type, which works especially well with sealed hierarchies.

String describe(PaymentEvent event) {
    return switch (event) {
        case PaymentAuthorized authorized ->
                "Authorized: " + authorized.paymentId();
        case PaymentDeclined declined ->
                "Declined: " + declined.reason();
    };
}

When all sealed variants are handled, the compiler can help detect missing cases.

Record Patterns

Record patterns let code unpack record values directly during pattern matching.

if (response instanceof ReservationResponse(Long id, String guest, String status)) {
    return id + " - " + guest + " - " + status;
}

This is helpful when extracting values from small immutable data structures.

Sequenced Collections

Sequenced collections provide a consistent API for collections with a defined encounter order, including first and last element access.

SequencedCollection<String> steps = new ArrayList<>();
steps.addFirst("validate");
steps.addLast("publish event");

This improves readability when order matters, such as workflow steps, ordered rules, or ordered response sections.

Practical Backend Guidance

  • Use records for immutable DTOs and event payloads, but avoid them for persistence entities that require framework mutation or lazy loading.
  • Use sealed types to model a closed set of states, events, commands, or results.
  • Use switch expressions for clear value mapping and avoid mutation-heavy branching.
  • Use text blocks in tests and infrastructure code where multiline JSON, SQL, or configuration improves readability.
  • Use virtual threads for blocking I/O workloads where the stack supports them, but keep reactive pipelines non-blocking.

Functional Programming Foundations

Functional programming is a style of writing code where data flows through small predictable operations. Instead of changing objects step by step, the code describes transformations from input to output.

Mental Model

Imagine a cruise boarding process. A reservation enters the process, then each station performs one clear job: validate documents, verify payment, assign boarding group, create a boarding pass. Each station should not secretly change another station's paperwork. It receives information, does its job, and hands forward a clear result.

Reservation -> validate -> verify payment -> assign group -> boarding pass

Functional programming tries to make code feel like that: small steps, clear inputs, clear outputs, and fewer hidden changes.

Pure Functions

A pure function always returns the same output for the same input and does not change anything outside itself. It does not update a database, mutate a list, write a file, call an API, log as part of business behavior, or depend on the current time unless the time is passed in as an input.

public int calculateTotalInCents(List<Payment> payments) {
    return payments.stream()
            .filter(payment -> payment.status().equals("APPROVED"))
            .mapToInt(Payment::amountInCents)
            .sum();
}

This is pure if the same list always produces the same total and the method does not change the list or any external system.

// Not pure: it changes external state.
public int calculateTotalAndSaveAudit(List<Payment> payments) {
    int total = calculateTotalInCents(payments);
    auditRepository.save(new AuditRecord("TOTAL_CALCULATED", total));
    return total;
}

Real-life analogy: pure function is like a calculator. If you type 10 + 20, it returns 30 every time and does not change your bank account. An impure function is like a payment terminal: it may calculate, but it can also charge a card, print a receipt, and change real-world state.

Why Pure Functions Help

  • They are easier to test because there is no hidden setup.
  • They are easier to debug because inputs explain outputs.
  • They are safer in concurrent code because they do not mutate shared state.
  • They fit naturally into Stream and Reactor pipelines.
  • They separate business calculations from side effects such as database writes and HTTP calls.

Immutability

Immutability means an object's state does not change after it is created. Instead of editing the same object, code creates a new value with the desired change.

public record Reservation(
        String id,
        String guestName,
        String status,
        int balanceInCents
) {}

public Reservation markPaid(Reservation reservation) {
    return new Reservation(
            reservation.id(),
            reservation.guestName(),
            "PAID",
            0);
}

The original reservation remains unchanged. The method returns a new reservation representing the updated state.

// Mutable style
reservation.setStatus("PAID");
reservation.setBalanceInCents(0);

// Immutable style
Reservation paidReservation = markPaid(reservation);

Real-life analogy: changing a printed cruise itinerary with a pen can create confusion because people may hold different versions. Issuing a new itinerary with a new state is clearer: the old document existed, and the new document represents the updated truth.

How do you avoid mutating lists in Java?

Instead of modifying the original list, create a new one. In functional programming and reactive systems, immutability prevents side effects and makes data flows predictable.

List<String> originalGuestIds = List.of("G1", "G2");

List<String> updatedGuestIds = Stream.concat(
        originalGuestIds.stream(),
        Stream.of("G3"))
        .toList();

updatedGuestIds contains the new value, but originalGuestIds is unchanged. This is crucial for thread safety and correctness in asynchronous pipelines.

// Avoid this when shared state can be observed elsewhere.
guestIds.add("G3");

// Prefer this when you want predictable data flow.
List<String> updatedGuestIds = Stream.concat(
        guestIds.stream(),
        Stream.of("G3"))
        .toList();

Why Mutability Matters in Functional Programming and Reactor

  1. Mutability causes bugs in concurrent systems. Reactor uses non-blocking asynchronous execution. If multiple operations mutate shared data at the same time, the code can produce race conditions where the final result depends on timing instead of business rules.
  2. Pure functions require no side effects. Mutating an external list, updating a shared object, or changing state outside the function is a side effect. That makes the function harder to test and harder to reason about.
  3. Immutability creates safer, predictable data flow. If a value cannot change, every operator in a Stream or Reactor pipeline receives a stable value. The code becomes easier to understand because earlier steps cannot secretly change what later steps see.
  4. Reactive Streams do not expect mutation between operators. Modifying objects inside a pipeline breaks referential transparency. A pipeline is clearest when each step receives a value and returns a new value instead of mutating the existing one.

Why is immutability important in reactive programming?

Immutability is essential in Reactor and WebFlux because reactive systems are asynchronous and often run work on multiple threads. When threads share mutable data, one thread can change a value while another thread is reading or processing it. That creates race conditions and unpredictable behavior.

  • Async code is safer with immutable values. If a value cannot change, it can move between threads without another operator secretly modifying it.
  • Referential transparency is preserved. Pure functions and immutable data make it possible to replace an expression with its result without changing behavior.
  • Non-blocking scheduling stays reliable. Reactor may shift work across schedulers and threads. Mutable shared state can break assumptions about ordering and visibility.

By using immutable data, each value in a reactive pipeline is safe to share across threads and operators. This preserves referential transparency and makes the pipeline deterministic. That is what makes Reactor's non-blocking, concurrent execution model easier to trust.

// Risky: mutates external shared state from inside the pipeline.
List<String> approvedIds = new ArrayList<>();

payments.stream()
        .filter(payment -> payment.status().equals("APPROVED"))
        .forEach(payment -> approvedIds.add(payment.id()));

// Safer: the pipeline produces the result directly.
List<String> approvedIds = payments.stream()
        .filter(payment -> payment.status().equals("APPROVED"))
        .map(Payment::id)
        .toList();

Immutability in Payment Systems

Payment systems benefit from immutability because historical facts should not be casually edited. A payment was authorized, declined, refunded, or settled. Instead of mutating the old event, systems usually add a new event.

public sealed interface PaymentEvent
        permits PaymentAuthorized, PaymentDeclined, PaymentRefunded {}

public record PaymentAuthorized(String paymentId, int amountInCents)
        implements PaymentEvent {}

public record PaymentDeclined(String paymentId, String reason)
        implements PaymentEvent {}

public record PaymentRefunded(String paymentId, int amountInCents)
        implements PaymentEvent {}

This keeps the payment history understandable. A refund does not erase the original charge; it adds a new fact.

Higher-Order Functions

A higher-order function receives a function as an argument, returns a function, or both. In Java, this usually means receiving or returning a functional interface such as Predicate, Function, Consumer, or Supplier.

public List<Payment> findPayments(
        List<Payment> payments,
        Predicate<Payment> rule
) {
    return payments.stream()
            .filter(rule)
            .toList();
}

findPayments is higher-order because it receives a rule as a parameter. The caller decides what rule to use.

List<Payment> declined = findPayments(payments,
        payment -> payment.status().equals("DECLINED"));

List<Payment> highValue = findPayments(payments,
        payment -> payment.amountInCents() >= 1_000_00);

Real-life analogy: the same security checkpoint can use different rules depending on the situation. One day it checks passports. Another day it checks boarding group. The checkpoint process is reusable because the rule can change.

Returning Functions

A method can also return a function. This is useful when code needs to build rules dynamically from configuration, user role, region, feature flag, or business context.

public Predicate<Payment> paymentReviewRule(int highValueLimitInCents) {
    return payment ->
            payment.status().equals("DECLINED")
                    || payment.amountInCents() >= highValueLimitInCents;
}

Predicate<Payment> reviewRule = paymentReviewRule(1_000_00);

List<Payment> reviewQueue = payments.stream()
        .filter(reviewRule)
        .toList();

The method creates a rule. The stream later applies that rule to every payment.

Function Composition

Function composition is the process of combining functions so that the output of one becomes the input of the next. In Java, this is done with methods such as andThen() and compose() on Function, and with composition methods such as and(), or(), and negate() on Predicate.

It allows code to build transformation pipelines from small, reusable pure functions. Each function handles one part of the work, and the output of one step becomes the input of the next step.

Function<String, String> trim = String::trim;
Function<String, String> uppercase = String::toUpperCase;
Function<String, String> addPrefix = name -> "Guest: " + name;

Function<String, String> formatGuestName =
        trim.andThen(uppercase).andThen(addPrefix);

String label = formatGuestName.apply("  Ana  ");

andThen reads left to right: trim, then uppercase, then add prefix. It is like an assembly line where each station performs a small step.

Function<Reservation, BoardingPass> createPass = reservation ->
        new BoardingPass(reservation.id(), reservation.guestName());

Function<BoardingPass, BoardingPassEmail> createEmail = pass ->
        new BoardingPassEmail(pass.guestName(), "Your boarding pass is ready");

Function<Reservation, BoardingPassEmail> createBoardingEmail =
        createPass.andThen(createEmail);

In reactive programming, composition is essential. Every operator in a Reactor pipeline, such as map, filter, and flatMap, is composing behavior into a larger data flow. This makes the logic declarative, easier to test, and avoids shared mutable state, which is crucial for asynchronous, non-blocking workflows.

Declarative vs Imperative Thinking

Imperative code focuses on how to do each step. Declarative code focuses on what result is wanted. Neither style is always wrong. The value of declarative code is that it often expresses business intent more clearly.

Imperative

List<String> approvedGuestNames = new ArrayList<>();

for (Payment payment : payments) {
    if (payment.status().equals("APPROVED")) {
        String name = payment.guestName();
        approvedGuestNames.add(name);
    }
}

This says: create a list, loop over payments, check status, extract name, add to list.

Declarative

List<String> approvedGuestNames = payments.stream()
        .filter(payment -> payment.status().equals("APPROVED"))
        .map(Payment::guestName)
        .toList();

This says: from payments, keep approved ones, extract guest names, return a list.

Real-life analogy: imperative is like giving turn-by-turn driving directions. Declarative is like saying the destination. In code, declarative pipelines still execute step by step, but the source code emphasizes the outcome.

Disney Cruise Example

This example keeps the business rules separate from the pipeline, which makes the process easier to read and test.

Predicate<Reservation> isConfirmed = reservation ->
        reservation.status().equals("CONFIRMED");

Predicate<Reservation> isPaid = reservation ->
        reservation.balanceInCents() == 0;

Function<Reservation, BoardingPass> toBoardingPass = reservation ->
        new BoardingPass(reservation.id(), reservation.guestName());

List<BoardingPass> passes = reservations.stream()
        .filter(isConfirmed.and(isPaid))
        .map(toBoardingPass)
        .toList();

The pipeline reads like the business process: confirmed reservations, paid reservations, then boarding passes.

Payment Example

This example calculates approved revenue without changing payment objects or touching external systems.

Predicate<Payment> isApproved = payment ->
        payment.status().equals("APPROVED");

Function<Payment, Integer> amount = Payment::amountInCents;

int approvedRevenue = payments.stream()
        .filter(isApproved)
        .map(amount)
        .reduce(0, Integer::sum);

The calculation is predictable: same payment list, same answer. Database writes, audit records, and notification sending should happen outside this pure calculation.

Practical Guidance

  • Keep calculations pure when possible.
  • Use immutable data for DTOs, events, commands, and read models.
  • Pass rules and transformations as functional interfaces when it makes the workflow more reusable.
  • Compose small functions instead of writing one large method with many unrelated responsibilities.
  • Prefer declarative pipelines when they make business intent clearer.
  • Keep side effects at the edges: repositories, HTTP clients, messaging clients, logging, and monitoring.
  • Use names for important predicates and functions so the code explains the business rule.

Common Mistakes

  • Thinking functional programming means never using objects. Java functional programming still works with records, classes, services, and domain models.
  • Calling a function pure when it secretly reads time, random values, files, databases, or shared mutable state.
  • Mutating a list or object inside map, filter, or forEach and making the pipeline harder to reason about.
  • Using streams for everything, even when a simple loop would be clearer.
  • Mixing business calculation and side effects in the same method.

Higher-Order Functions

A higher-order function is a function that receives another function as an argument, returns a function as its result, or both. In Java, this usually means a method receives or returns a functional interface such as Predicate, Function, Consumer, or Supplier.

Mental Model

Imagine a payment review desk. The desk always does the same general workflow: receive payments, apply a rule, and return the payments that need attention. What changes is the rule. One day the rule is declined payments. Another day it is payments over $1,000. The desk is reusable because the rule is passed in.

Receiving a Function as an Argument

This method is higher-order because it receives a Predicate<Payment>. The method does not hard-code the rule; the caller supplies the rule.

public List<Payment> findPayments(
        List<Payment> payments,
        Predicate<Payment> rule
) {
    return payments.stream()
            .filter(rule)
            .toList();
}

List<Payment> declinedPayments = findPayments(payments,
        payment -> payment.status().equals("DECLINED"));

List<Payment> highValuePayments = findPayments(payments,
        payment -> payment.amountInCents() >= 1_000_00);

The same method supports different business questions because the behavior is passed in as data.

Returning a Function

A method can build and return a function. This is useful when a rule depends on configuration, region, product type, guest tier, or feature flags.

public Predicate<Payment> createReviewRule(int highValueLimitInCents) {
    return payment ->
            payment.status().equals("DECLINED")
                    || payment.amountInCents() >= highValueLimitInCents;
}

Predicate<Payment> standardReviewRule = createReviewRule(1_000_00);
Predicate<Payment> vipReviewRule = createReviewRule(500_00);

List<Payment> standardQueue = payments.stream()
        .filter(standardReviewRule)
        .toList();

The method creates a rule once, and that rule can be reused in a stream, service method, validator, or test.

Disney Cruise Example

This higher-order method can find reservations based on any rule: ready to board, missing documents, unpaid, cancelled, or VIP.

public List<Reservation> findReservations(
        List<Reservation> reservations,
        Predicate<Reservation> rule
) {
    return reservations.stream()
            .filter(rule)
            .toList();
}

Predicate<Reservation> readyToBoard = reservation ->
        reservation.status().equals("CONFIRMED")
                && reservation.balanceInCents() == 0
                && reservation.hasRequiredDocuments();

List<Reservation> boardingQueue =
        findReservations(reservations, readyToBoard);

Real-life analogy: the same crew member can use different checklists. One checklist is for boarding readiness. Another is for missing documents. The process is the same; the rule changes.

Transforming with a Function Argument

Higher-order functions are not only for filtering. They can also receive transformations.

public List<String> createLabels(
        List<Payment> payments,
        Function<Payment, String> labelFunction
) {
    return payments.stream()
            .map(labelFunction)
            .toList();
}

List<String> receiptLabels = createLabels(payments,
        payment -> payment.id() + " - $" + payment.amountInCents() / 100);

List<String> reservationLabels = createLabels(payments,
        payment -> payment.reservationId() + " - " + payment.guestName());

The same method can create different outputs because the transformation is supplied from outside.

Connection to Streams and Reactor

Many common Java APIs are built from higher-order functions. filter receives a Predicate. map receives a Function. forEach receives a Consumer. Reactor follows the same idea with asynchronous data.

// Stream: synchronous collection pipeline
payments.stream()
        .filter(payment -> payment.status().equals("APPROVED"))
        .map(Payment::id)
        .toList();

// Reactor: asynchronous publisher pipeline
paymentFlux
        .filter(payment -> payment.status().equals("APPROVED"))
        .map(Payment::id);

Reactor and WebFlux also depend on higher-order functions. Each operator receives functions as inputs.

flux.flatMap(this::callApi)
        .map(this::transform)
        .filter(this::isValid);

The operators are higher-order because they receive behavior and compose it into a pipeline. This is why functional programming is so important for reactive systems.

Why Higher-Order Functions Matter

  • They allow composition. Code can build powerful pipelines by passing functions into other functions.
  • They enable declarative, functional code. Instead of manually controlling every loop and temporary variable, the code describes behavior.
  • They reduce boilerplate. Many workflows no longer need repetitive loops, nested if statements, or manual collection building.
  • They make code more reusable. The same method can accept different functions to customize behavior for payments, reservations, guests, or events.

Practical Guidance

  • Use higher-order functions when the workflow is stable but the rule or transformation changes.
  • Name important rules with variables such as readyToBoard or requiresManualReview.
  • Keep passed functions small and focused.
  • Prefer pure functions for calculations and transformations.
  • Keep side effects such as saving, sending, and logging at clear boundaries.

Reference Definition

A higher-order function is a function that either takes another function as an argument or returns a function. In Java, this is common with Streams and Reactor, where operators like map, filter, and flatMap receive functions. Higher-order functions enable functional composition, reusability, and declarative programming.

Composability

Composable means small, independent pieces can be combined to build bigger and more complex behavior without modifying the pieces themselves.

Simple Definition

Think LEGO blocks, not glue. If something is composable, you can plug it together with other things, each piece keeps doing one job, and you do not need to rewrite existing code to combine behavior.

  • Each piece has a clear responsibility.
  • Each piece can be reused in different workflows.
  • Pieces can be added, removed, or reordered more easily.
  • The original pieces do not need to be modified every time the workflow changes.

Composable in Functional Programming

Functions are composable when the output of one function can become the input of another function.

Function<Integer, Integer> doubleIt = x -> x * 2;
Function<Integer, Integer> addOne = x -> x + 1;

Function<Integer, Integer> composed =
        doubleIt.andThen(addOne);

int result = composed.apply(10);

doubleIt is reusable. addOne is reusable. composed is built by combining them. That is composability.

Real-life analogy: a payment workflow may have separate steps for validating the request, calculating fees, authorizing the payment, and creating a receipt. Each step does one job, and the workflow combines them.

Composable in Streams

Stream pipelines are composable because each operator does one job and returns a new stream for the next operator.

List<Integer> result = numbers.stream()
        .filter(n -> n > 10)
        .map(n -> n * 2)
        .sorted()
        .toList();

Each operation can be added, removed, or reordered when the business rule changes. filter keeps matching data. map transforms it. sorted orders it. toList produces the final result.

List<PaymentSummary> summaries = payments.stream()
        .filter(payment -> payment.status().equals("APPROVED"))
        .sorted(Comparator.comparingInt(Payment::amountInCents).reversed())
        .map(payment -> new PaymentSummary(
                payment.id(),
                payment.reservationId(),
                payment.amountInCents()))
        .toList();

The payment pipeline reads as separate business steps: keep approved payments, order by amount, convert to summaries.

Composable in Reactor

Composability is especially important in Reactor. Each step receives input, returns a Mono or Flux, and can be chained without changing the previous steps.

getUserId()
        .flatMap(this::findUserById)
        .filter(this::isActive)
        .flatMap(this::sendNotification);

This is why Reactor code scales well. The pipeline can grow from simple behavior into a larger asynchronous workflow while each operator remains focused.

public Mono<BoardingPass> createBoardingPass(String reservationId) {
    return reservationRepository.findById(reservationId)
            .filter(this::isConfirmed)
            .flatMap(this::verifyPayment)
            .flatMap(this::verifyDocuments)
            .map(this::toBoardingPass);
}

The Disney cruise workflow is composed from separate steps: find reservation, check confirmation, verify payment, verify documents, create boarding pass.

What Is Not Composable

Imperative code can become hard to compose when the logic is tangled, deeply nested, and full of side effects.

User user = getUser();
if (user != null) {
    if (user.isActive()) {
        save(user);
        sendEmail(user);
    }
}

This style can work, but it is harder to reuse steps, harder to reorder behavior, and easier to mix validation, persistence, and notification side effects in one place.

Why Composability Matters in Reactive Systems

Reactive systems are asynchronous, concurrent, and non-blocking. Composable code helps keep that complexity manageable.

  • It avoids shared mutable state because each step can return a new value or publisher.
  • It is easier to reason about because each operator has a focused role.
  • It is easier to test because individual rules and transformations can be tested separately.
  • It is safer in asynchronous environments because behavior is expressed as a pipeline instead of scattered side effects.

Composable means that small, independent pieces of logic can be combined together to build more complex behavior without modifying the original pieces. In functional and reactive programming, functions and operators are composable, which allows code to build declarative pipelines that are easy to extend, reuse, and reason about.

Functional Interfaces

A functional interface is an interface that contains exactly one abstract method. This enables Java to use lambda expressions and method references, because the compiler can unambiguously match a lambda to the single abstract method.

Functional interfaces often also contain default or static methods, which do not affect their functional nature. They let Java treat behavior as a value, so code can pass an action, rule, calculation, or transformation into another method.

Mental Model

Imagine a cruise terminal with different workers. One worker checks whether a guest can board. Another worker prints a boarding pass. Another sends a notification. A functional interface is like describing one job role: given this input, perform this one kind of work.

@FunctionalInterface
public interface BoardingRule {
    boolean canBoard(Reservation reservation);
}

The interface has one abstract method, so Java can implement it with a lambda instead of a full class.

BoardingRule isPaidAndConfirmed = reservation ->
        reservation.isPaid() && reservation.status().equals("CONFIRMED");

Why Functional Interfaces Matter

  • They are the foundation of lambdas in Java.
  • They let methods receive behavior, not just data.
  • They power Stream operations such as filter, map, flatMap, and forEach.
  • They make business rules easier to compose and test.
  • They appear constantly in reactive programming, where pipelines receive small functions for transformation, validation, error handling, and side effects.
  • Without functional interfaces, Java's Stream API and Reactor would not be possible in their current declarative style.

Lambda Shape

A lambda is a compact implementation of a functional interface. It has inputs on the left, an arrow, and behavior on the right.

payment -> payment.status().equals("APPROVED")

Real-life analogy: the left side is the item handed to a worker, and the right side is what the worker does with it.

// Input: one payment
// Work: check whether it is approved
Predicate<Payment> isApproved = payment ->
        payment.status().equals("APPROVED");

Consumer<T> T -> void performing actions
Supplier<T> () -> T lazy creation
UnaryOperator<T> T -> T transformations T to T
BiFunction<T, U, R> (T, U) -> R merging, combining
  • Predicate<T> for filtering with test.
  • Function<T, R> and BiFunction<T, U, R> for transformations with apply.
  • Consumer<T> for side-effect actions with accept.
  • Supplier<T> for lazy value generation with get.
  • UnaryOperator<T> and BinaryOperator<T> for transformations where the input and output stay the same type.

Predicate<T>

A Predicate receives one value and returns true or false. It represents a rule or question.

Predicate<Payment> isApproved = payment ->
        payment.status().equals("APPROVED");

Predicate<Reservation> canBoard = reservation ->
        reservation.isPaid() && !reservation.isCancelled();

Used by filter. In plain English: should this item stay in the pipeline?

Function<T, R>

A Function receives one value and returns another value. It represents a transformation.

Function<Payment, String> toReceiptLine = payment ->
        payment.id() + " - $" + payment.amountInCents() / 100;

Function<Reservation, BoardingPass> toBoardingPass = reservation ->
        new BoardingPass(reservation.id(), reservation.guestName());

Used by map. In plain English: turn this thing into another thing.

Consumer<T>

A Consumer receives one value and returns nothing. It represents doing something with the value.

Consumer<Payment> logPayment = payment ->
        System.out.println("Processed payment " + payment.id());

Consumer<BoardingPass> printPass = pass ->
        printer.print(pass);

Used by forEach and side-effect hooks. In plain English: take this item and do an action.

Supplier<T>

A Supplier receives nothing and returns a value. It represents delayed creation.

Supplier<String> idGenerator = () ->
        UUID.randomUUID().toString();

Supplier<PaymentAudit> auditFactory = () ->
        new PaymentAudit(Instant.now(), "SYSTEM");

In plain English: when someone asks, produce a value.

BiFunction<T, U, R>

A BiFunction receives two values and returns one value.

BiFunction<Integer, Integer, Integer> add = (left, right) ->
        left + right;

BiFunction<Payment, Integer, PaymentSummary> toSummary = (payment, fee) ->
        new PaymentSummary(payment.id(), payment.amountInCents() + fee);

Use it when a calculation needs two inputs, such as payment plus fee, reservation plus room assignment, or old state plus new event.

UnaryOperator and BinaryOperator

UnaryOperator<T> is a Function where input and output have the same type. BinaryOperator<T> is a BiFunction where both inputs and the output have the same type.

UnaryOperator<String> normalizeName = name ->
        name.trim().toUpperCase();

BinaryOperator<Integer> addAmounts = Integer::sum;

These are good for cleanup, normalization, and combining values of the same type.

Method References

A method reference is a shorter lambda when the lambda only calls an existing method.

Function<Payment, String> getStatus = Payment::status;

Consumer<String> print = System.out::println;

List<String> statuses = payments.stream()
        .map(Payment::status)
        .distinct()
        .toList();

Payment::status means: given a Payment, call its status() method. It is the same idea as payment -> payment.status().

Composition

Composition means building bigger behavior from smaller behaviors. This is like a cruise check-in process made from small steps: normalize the guest name, verify payment, assign boarding group, and print the pass.

Function<String, String> trim = String::trim;
Function<String, String> uppercase = String::toUpperCase;

Function<String, String> normalizeGuestName = trim.andThen(uppercase);

String normalized = normalizeGuestName.apply("  Ana  ");

andThen runs the first function, then the second. compose runs the function passed into it first.

Function<Payment, Integer> amount = Payment::amountInCents;
Function<Integer, String> formatDollars = cents -> "$" + cents / 100;

Function<Payment, String> paymentAmountLabel = amount.andThen(formatDollars);

Predicate Composition

Predicates can be combined with and, or, and negate. This keeps business rules readable.

Predicate<Payment> isApproved = payment ->
        payment.status().equals("APPROVED");

Predicate<Payment> isLarge = payment ->
        payment.amountInCents() >= 500_00;

Predicate<Payment> needsManualReview = isApproved.negate().or(isLarge);

List<Payment> reviewQueue = payments.stream()
        .filter(needsManualReview)
        .toList();

Plain analogy: a port security rule can say a guest needs review if their document is invalid OR their reservation needs special handling. Each rule stays separate, then the rules are combined.

Custom Functional Interfaces

Use built-in interfaces when their names are clear enough. Create a custom functional interface when the domain meaning matters.

@FunctionalInterface
public interface PaymentRule {
    boolean passes(Payment payment);
}

PaymentRule approvedCardPayment = payment ->
        payment.status().equals("APPROVED")
                && payment.method().equals("CARD");

Predicate<Payment> works technically, but PaymentRule can communicate business meaning more clearly in important domain code.

Pure Functions and Side Effects

A pure function returns the same result for the same input and does not change outside state. Pure functions are easier to test, easier to reuse, and safer in asynchronous code.

Function<Payment, String> pureReceiptLabel = payment ->
        payment.id() + " - " + payment.status();

Consumer<Payment> sideEffect = payment ->
        auditRepository.save(payment);

The first example only calculates a value. The second changes an external system. Side effects are sometimes necessary, but keep them at clear boundaries such as persistence, logging, messaging, or HTTP calls.

Payment System Example

This example builds a payment review pipeline from reusable functional interfaces.

Predicate<Payment> isDeclined = payment ->
        payment.status().equals("DECLINED");

Predicate<Payment> isHighValue = payment ->
        payment.amountInCents() >= 1_000_00;

Function<Payment, String> toReviewMessage = payment ->
        "Review " + payment.id()
                + " for reservation " + payment.reservationId();

List<String> reviewMessages = payments.stream()
        .filter(isDeclined.or(isHighValue))
        .map(toReviewMessage)
        .toList();

The predicates decide which payments matter. The function converts those payments into readable messages. The stream connects the rules into a full workflow.

Disney Cruise Example

This example uses functional interfaces to decide which reservations are ready for boarding.

Predicate<Reservation> isConfirmed = reservation ->
        reservation.status().equals("CONFIRMED");

Predicate<Reservation> isPaid = Reservation::isPaid;

Predicate<Reservation> hasRequiredDocuments = reservation ->
        reservation.documents().contains("PASSPORT")
                || reservation.documents().contains("BIRTH_CERTIFICATE");

Function<Reservation, BoardingPass> createBoardingPass = reservation ->
        new BoardingPass(reservation.id(), reservation.guestName());

List<BoardingPass> boardingPasses = reservations.stream()
        .filter(isConfirmed.and(isPaid).and(hasRequiredDocuments))
        .map(createBoardingPass)
        .toList();

This reads like a real process: keep confirmed reservations, keep paid reservations, keep guests with documents, then create boarding passes.

How This Connects to Streams and Reactor

Stream and Reactor operators receive functional interfaces. Once this idea is clear, the APIs become easier to read.

// Stream
payments.stream()
        .filter(payment -> payment.status().equals("APPROVED")) // Predicate
        .map(Payment::id)                                      // Function
        .forEach(System.out::println);                         // Consumer

// Reactor
paymentMono
        .filter(payment -> payment.status().equals("APPROVED")) // Predicate
        .map(Payment::id)                                       // Function
        .doOnNext(System.out::println);                         // Consumer-style callback

The difference is the execution model. Stream is usually synchronous and collection-focused. Reactor is asynchronous, lazy, and built around publishers such as Mono and Flux. But both rely heavily on the same functional-interface idea.

Common Mistakes

  • Thinking a functional interface means many methods. It must have exactly one abstract method.
  • Forgetting that default and static methods are allowed because they are not abstract methods.
  • Putting database writes, HTTP calls, or shared mutable state inside lambdas that should be simple transformations.
  • Using a custom interface when Predicate, Function, Consumer, or Supplier would be clearer.
  • Using Consumer when a Function is needed. A Consumer returns nothing; a Function returns a transformed value.

Java Streams Deep Dive

A Stream is a pipeline for processing data from a collection or another source. It lets code describe what should happen to the data: filter these items, transform them, sort them, group them, count them, or reduce them into a final answer.

Mental Model

Imagine a Disney cruise check-in line. Guests enter the line, staff remove invalid reservations, sort guests by boarding group, transform each reservation into a boarding pass, and finally collect the passes into a stack. A Java Stream works the same way: data moves through a sequence of steps until a terminal operation produces the result.

List<BoardingPass> passes = reservations.stream()
        .filter(Reservation::isPaid)
        .filter(reservation -> !reservation.isCancelled())
        .sorted(Comparator.comparing(Reservation::boardingGroup)
                .thenComparing(Reservation::guestName))
        .map(reservation -> new BoardingPass(
                reservation.id(),
                reservation.guestName(),
                reservation.boardingGroup()))
        .toList();

The source is reservations. The intermediate operations are filter, sorted, and map. The terminal operation is toList.

Stream Vocabulary

  • Source: where data comes from, such as a List, Set, array, file, or generated sequence.
  • Intermediate operation: returns another Stream and does not run by itself. Examples: map, filter, sorted, distinct.
  • Terminal operation: starts the pipeline and produces a result or side effect. Examples: toList, collect, count, sum, forEach.
  • Lazy execution: intermediate operations wait until a terminal operation is called.
  • One-time use: a Stream cannot be reused after a terminal operation.

List<Payment> payments = List.of(

map

map transforms each item into another value. If a payment is a row in a spreadsheet, map creates a new column from each row.

List<String> guestNames = payments.stream()
        .map(Payment::guestName)
        .toList();

List<String> labels = payments.stream()
        .map(payment -> payment.id() + " - " + payment.status())
        .toList();

Use map when one input item becomes one output item. A payment becomes a guest name. A reservation becomes a response DTO. An entity becomes an API response.

filter

filter keeps only items that pass a condition. In real life, it is like letting only guests with valid boarding documents continue through the line.

List<Payment> approvedPayments = payments.stream()
        .filter(payment -> payment.status().equals("APPROVED"))
        .toList();

List<Payment> largeApprovedPayments = payments.stream()
        .filter(payment -> payment.status().equals("APPROVED"))
        .filter(payment -> payment.amountInCents() >= 100_00)
        .toList();

Multiple filters are often more readable than one large condition because each rule has its own line.

flatMap

flatMap is used when each item contains another collection or stream, and the final result should be one flat stream. It transforms and flattens at the same time.

public record CruiseReservation(
        String id,
        String guestName,
        List<String> excursionCodes
) {}

List<CruiseReservation> reservations = List.of(
        new CruiseReservation("R1", "Ana", List.of("CASTAWAY-5K", "SPA")),
        new CruiseReservation("R2", "Luke", List.of("SNORKELING"))
);

List<String> allExcursions = reservations.stream()
        .flatMap(reservation -> reservation.excursionCodes().stream())
        .toList();

Without flatMap, the result would be shaped like Stream<List<String>>. With flatMap, the result is shaped like Stream<String>.

// map keeps the boxes:
List<List<String>> excursionsByReservation = reservations.stream()
        .map(CruiseReservation::excursionCodes)
        .toList();

// flatMap opens the boxes and puts all items in one line:
List<String> flatExcursions = reservations.stream()
        .flatMap(reservation -> reservation.excursionCodes().stream())
        .toList();

distinct

distinct removes duplicates using equals and hashCode. With records, Java generates those methods from the record components.

List<String> uniqueGuestNames = payments.stream()
        .map(Payment::guestName)
        .distinct()
        .toList();

List<String> uniqueReservationIds = payments.stream()
        .map(Payment::reservationId)
        .distinct()
        .toList();

Use distinct when repeated values are not meaningful, such as unique guest names, reservation IDs, payment methods, or event IDs already seen.

sorted

sorted orders stream elements. For simple values like strings and numbers, natural ordering often works directly.

List<String> names = payments.stream()
        .map(Payment::guestName)
        .distinct()
        .sorted()
        .toList();

For objects, use a Comparator to say which field should control the order.

List<Payment> cheapestFirst = payments.stream()
        .sorted(Comparator.comparingInt(Payment::amountInCents))
        .toList();

List<Payment> biggestFirst = payments.stream()
        .sorted(Comparator.comparingInt(Payment::amountInCents).reversed())
        .toList();

Comparator Main Methods

  • Comparator.comparing: sort by an object field, such as name, status, method, or date.
  • Comparator.comparingInt: sort by an int without boxing overhead.
  • Comparator.comparingLong: sort by a long.
  • Comparator.comparingDouble: sort by a double.
  • thenComparing: add a tie-breaker when the first comparison is equal.
  • reversed: reverse the whole comparator.
  • nullsFirst and nullsLast: define where null values should appear.
  • naturalOrder and reverseOrder: use normal ascending or descending order for comparable values.
List<Payment> ordered = payments.stream()
        .sorted(Comparator
                .comparing(Payment::status)
                .thenComparing(Payment::guestName)
                .thenComparingInt(Payment::amountInCents))
        .toList();

Real-life analogy: sorting luggage first by deck, then by room number, then by guest name. If two bags have the same deck, the room number breaks the tie. If the room is also the same, the guest name breaks the next tie.

public record LuggageTag(
        int deck,
        int roomNumber,
        String guestName
) {}

List<LuggageTag> deliveryOrder = tags.stream()
        .sorted(Comparator
                .comparingInt(LuggageTag::deck)
                .thenComparingInt(LuggageTag::roomNumber)
                .thenComparing(LuggageTag::guestName))
        .toList();

limit and skip

limit keeps the first N items. skip ignores the first N items. Together, they are useful for pagination.

int page = 2;
int size = 10;

List<Payment> secondPage = payments.stream()
        .sorted(Comparator.comparing(Payment::id))
        .skip((long) (page - 1) * size)
        .limit(size)
        .toList();

peek

peek lets code observe items passing through the pipeline. It is mainly useful for debugging. Avoid using it for business logic.

List<Payment> approved = payments.stream()
        .peek(payment -> System.out.println("Before filter: " + payment.id()))
        .filter(payment -> payment.status().equals("APPROVED"))
        .peek(payment -> System.out.println("Approved: " + payment.id()))
        .toList();

Terminal Operations

Terminal operations start the stream. Without a terminal operation, the pipeline is just a description and nothing runs.

toList

toList creates a list from the stream result. In modern Java, this list is unmodifiable.

List<String> approvedIds = payments.stream()
        .filter(payment -> payment.status().equals("APPROVED"))
        .map(Payment::id)
        .toList();

collect

collect uses a Collector to build a result such as a list, set, map, string, or grouped structure.

Set<String> methods = payments.stream()
        .map(Payment::method)
        .collect(Collectors.toSet());

count

count returns how many items remain after filtering.

long declinedCount = payments.stream()
        .filter(payment -> payment.status().equals("DECLINED"))
        .count();

forEach

forEach performs an action for each item. It returns nothing, so it is usually for boundary actions such as logging or calling a void API.

payments.stream()
        .filter(payment -> payment.status().equals("DECLINED"))
        .forEach(payment -> System.out.println("Review payment " + payment.id()));

sum, average, min, and max

sum exists on primitive streams such as IntStream, LongStream, and DoubleStream. Convert with mapToInt, mapToLong, or mapToDouble.

int approvedTotal = payments.stream()
        .filter(payment -> payment.status().equals("APPROVED"))
        .mapToInt(Payment::amountInCents)
        .sum();

double averagePayment = payments.stream()
        .mapToInt(Payment::amountInCents)
        .average()
        .orElse(0);

int biggestPayment = payments.stream()
        .mapToInt(Payment::amountInCents)
        .max()
        .orElse(0);

Real-life analogy: after filtering only completed purchases, sum is like adding every receipt total in the cash register at the end of the day.

reduce

reduce combines many values into one value. Use it when there is no simpler operation like sum, count, or Collectors.joining.

int total = payments.stream()
        .filter(payment -> payment.status().equals("APPROVED"))
        .map(Payment::amountInCents)
        .reduce(0, Integer::sum);

String paymentSummary = payments.stream()
        .map(payment -> payment.id() + ":" + payment.status())
        .reduce("", (left, right) -> left.isBlank() ? right : left + ", " + right);

findFirst, findAny, anyMatch, allMatch, noneMatch

These operations answer questions without necessarily processing every item. They can stop early when the answer is known.

Optional<Payment> firstDeclined = payments.stream()
        .filter(payment -> payment.status().equals("DECLINED"))
        .findFirst();

boolean hasDeclinedPayment = payments.stream()
        .anyMatch(payment -> payment.status().equals("DECLINED"));

boolean allApproved = payments.stream()
        .allMatch(payment -> payment.status().equals("APPROVED"));

boolean noNegativeAmounts = payments.stream()
        .noneMatch(payment -> payment.amountInCents() < 0);

anyMatch is like asking whether at least one guest in line needs assistance. allMatch asks whether every guest has a valid ticket. noneMatch asks whether nobody is missing required documents.

Collectors

Collectors are reusable recipes for turning a stream into a final structure.

toList, toSet, toMap

List<Payment> approvedList = payments.stream()
        .filter(payment -> payment.status().equals("APPROVED"))
        .collect(Collectors.toList());

Set<String> paymentMethods = payments.stream()
        .map(Payment::method)
        .collect(Collectors.toSet());

Map<String, Payment> paymentById = payments.stream()
        .collect(Collectors.toMap(
                Payment::id,
                payment -> payment));

toMap With Duplicate Keys

If keys can repeat, provide a merge function. This example keeps the larger payment per reservation.

Map<String, Payment> largestPaymentByReservation = payments.stream()
        .collect(Collectors.toMap(
                Payment::reservationId,
                payment -> payment,
                (left, right) -> left.amountInCents() >= right.amountInCents()
                        ? left
                        : right));

groupingBy

groupingBy creates buckets. It is like sorting cruise passengers into lines by boarding group.

Map<String, List<Payment>> paymentsByStatus = payments.stream()
        .collect(Collectors.groupingBy(Payment::status));

Map<String, List<Payment>> paymentsByReservation = payments.stream()
        .collect(Collectors.groupingBy(Payment::reservationId));

partitioningBy

partitioningBy splits items into exactly two groups: true and false.

Map<Boolean, List<Payment>> expensiveOrNot = payments.stream()
        .collect(Collectors.partitioningBy(
                payment -> payment.amountInCents() >= 100_00));

joining

joining combines strings.

String guestList = payments.stream()
        .map(Payment::guestName)
        .distinct()
        .sorted()
        .collect(Collectors.joining(", "));

mapping and counting

Collectors can be nested. This counts payments per status.

Map<String, Long> countByStatus = payments.stream()
        .collect(Collectors.groupingBy(
                Payment::status,
                Collectors.counting()));

summing and averaging

Map<String, Integer> totalByStatus = payments.stream()
        .collect(Collectors.groupingBy(
                Payment::status,
                Collectors.summingInt(Payment::amountInCents)));

Map<String, Double> averageByMethod = payments.stream()
        .collect(Collectors.groupingBy(
                Payment::method,
                Collectors.averagingInt(Payment::amountInCents)));

maxBy and minBy

Map<String, Optional<Payment>> largestByMethod = payments.stream()
        .collect(Collectors.groupingBy(
                Payment::method,
                Collectors.maxBy(
                        Comparator.comparingInt(Payment::amountInCents))));

toList vs Collectors.toList

  • stream().toList() is concise and returns an unmodifiable list.
  • collect(Collectors.toList()) returns a mutable list in common JDK implementations, but the interface does not strongly promise the exact list type.
  • Use toCollection(ArrayList::new) when you specifically need a mutable ArrayList.
List<String> unmodifiable = payments.stream()
        .map(Payment::id)
        .toList();

List<String> mutable = payments.stream()
        .map(Payment::id)
        .collect(Collectors.toCollection(ArrayList::new));

mutable.add("manual-adjustment");

Common Mistakes

  • Using map when the function returns a collection and the result should be flattened. Use flatMap.
  • Expecting intermediate operations to run without a terminal operation.
  • Reusing a stream after toList, collect, count, or another terminal operation.
  • Using forEach to build lists manually instead of map, filter, and toList.
  • Using sorted on large datasets that should be sorted by the database with proper indexes.
  • Using parallel streams for I/O-heavy work without understanding thread pools, blocking calls, and ordering.

Project Reactor Fundamentals

Project Reactor is a reactive programming library for Java. It lets backend code describe asynchronous data pipelines using Mono and Flux, instead of blocking a thread while waiting for work to finish.

What Reactive Programming Is

Reactive programming is a style where code reacts to data as it becomes available. Instead of saying "call this method, wait here, then continue", the code builds a pipeline that says "when a value arrives, transform it, validate it, maybe call another service, handle errors, and return the final result."

Reactive programming is about asynchronous execution, non-blocking processing, event-driven data flows, and backpressure-aware streams.

// Pulling data in a blocking style:
User user = repository.findById(id);

// Describing non-blocking data that will arrive later:
Mono<User> userMono = repository.findById(id);

Nothing happens until someone subscribes. In WebFlux, the framework subscribes for you when it handles the HTTP request.

Real-life analogy: a restaurant does not make one waiter stand frozen while the kitchen prepares food. The waiter takes the order, the kitchen works, and the waiter can handle other tables until the food is ready. Reactive systems follow the same idea: do not block threads while waiting for databases, APIs, queues, or files.

Mono<ReservationResponse> response = reservationRepository.findById(id)
        .filter(reservation -> reservation.status().equals("CONFIRMED"))
        .flatMap(paymentService::loadPayment)
        .map(payment -> new ReservationResponse(id, payment.status()));

The code describes the work. It does not immediately execute the work just because the pipeline was created.

Mono vs Flux

This distinction is very important: Mono is for zero or one value, and Flux is for zero to many values.

Mono<T>

A Mono represents zero or one value. It is similar to Optional<T>, but asynchronous. Use it when the operation returns one thing, or possibly nothing.

Mono<Reservation> reservation =
        reservationRepository.findById("R123");

Mono<PaymentReceipt> receipt =
        paymentService.authorize(paymentRequest);

Mono<User> userMono =
        Mono.just(new User("1"));

Examples: find by ID, make an HTTP request returning one object, authorize one payment, save one record, fetch one profile, return one HTTP response, or complete an operation with no value using Mono<Void>.

Flux<T>

A Flux represents zero to N values. It is an asynchronous stream of elements. Use it when the operation can emit multiple items.

Flux<Reservation> reservations =
        reservationRepository.findByGuestId("G123");

Flux<PaymentEvent> events =
        paymentEventConsumer.receive();

Flux<User> usersFlux =
        Flux.just(user1, user2, user3);

Examples: list users, list reservations, stream payment events, consume a Kafka topic, process Kinesis records, handle WebSocket messages, return multiple search results, or send server-sent events.

Plain rule: use Mono for one answer and Flux for many answers. A single cruise reservation lookup is Mono. A stream of all reservations for a sailing is Flux.

Mono represents an asynchronous stream that emits zero or one element, while Flux represents an asynchronous stream that can emit zero to many elements. Mono is typically used for operations like finding a user by ID or saving an entity, where only one result is expected. Flux is used for streams of data such as fetching all users, consuming messages from Kafka, or handling continuous event streams. Both represent reactive pipelines that emit data and then complete.

Lazy Execution

Reactor pipelines are lazy. Creating a Mono or Flux usually describes work, but the work does not start until something subscribes.

Project Reactor is considered lazy because a reactive pipeline is not executed until a Subscriber subscribes to a Publisher. Defining a Mono or Flux only describes how data should flow, but no work is done upfront.

When a subscriber subscribes, it also signals demand, which allows Reactor to control the flow of data through backpressure. This laziness avoids unnecessary computation, gives the subscriber control over consumption, and is essential for building efficient, non-blocking systems.

Mono<String> guestName = Mono.fromCallable(() -> {
    System.out.println("Loading guest");
    return "Ana";
});

// Nothing printed yet.

guestName.subscribe(System.out::println);
// Now "Loading guest" runs, then "Ana" is printed.

In Spring WebFlux controllers, you normally do not call subscribe() yourself. You return the Mono or Flux, and Spring subscribes as part of handling the HTTP request.

@GetMapping("/reservations/{id}")
public Mono<ReservationResponse> getReservation(@PathVariable String id) {
    return reservationService.getReservation(id);
}

Most Important Reactor Operators

Operator Purpose
map Transform data
filter Keep matching data
flatMap Async composition
defaultIfEmpty Fallback value
switchIfEmpty Alternate publisher
doOnNext Side effects, such as logging

map

Use map for synchronous one-to-one transformations.

Mono<ReservationResponse> response =
        reservationMono.map(reservation ->
                new ReservationResponse(
                        reservation.id(),
                        reservation.guestName(),
                        reservation.status()));

flatMap

Use flatMap when the next step returns another Mono or Flux, usually an asynchronous operation.

Mono<PaymentReceipt> receipt =
        reservationMono.flatMap(reservation ->
                paymentService.authorize(reservation.id()));

If the function returns Mono<PaymentReceipt>, flatMap keeps the result as Mono<PaymentReceipt> instead of creating Mono<Mono<PaymentReceipt>>.

flatMap is used when composing asynchronous operations. If the mapping function returns another reactive type like Mono or Flux, using map would result in a nested publisher such as Mono<Mono<T>>. flatMap flattens this structure and keeps the pipeline as a single reactive stream, allowing the pipeline to continue correctly.

filter

Use filter to keep only values that pass a rule. If a Mono value does not pass, it becomes empty.

Mono<Reservation> activeReservation =
        reservationMono.filter(reservation ->
                !reservation.status().equals("CANCELLED"));

switchIfEmpty

Use switchIfEmpty when no value was emitted. It is common for 404-style behavior.

Mono<Reservation> reservation = repository.findById(id)
        .switchIfEmpty(Mono.error(
                new ReservationNotFoundException(id)));

onErrorResume

Use onErrorResume to recover from an error with another publisher.

Mono<PaymentStatus> status = paymentClient.getStatus(paymentId)
        .onErrorResume(TimeoutException.class, error ->
                Mono.just(PaymentStatus.UNKNOWN));

Use fallbacks only when they are truthful. Do not pretend a payment succeeded if the payment provider failed.

onErrorMap

Use onErrorMap to translate one exception into another.

Mono<PaymentReceipt> receipt = paymentClient.authorize(request)
        .onErrorMap(WebClientException.class, error ->
                new PaymentProviderException("Payment provider failed", error));

doOnNext and doOnError

Use doOnNext and doOnError for observation such as logging or metrics. Avoid putting core business changes there.

Mono<Reservation> reservation = repository.findById(id)
        .doOnNext(value -> log.info("Loaded reservation {}", value.id()))
        .doOnError(error -> log.warn("Reservation load failed", error));

then and thenReturn

Use then when you care that one operation completes before another starts, but you do not need the previous value.

Mono<Void> result = repository.deleteById(id)
        .then(auditService.recordDeletion(id));

Mono<ResponseEntity<Void>> deleted = repository.deleteById(id)
        .thenReturn(ResponseEntity.noContent().build());

Cold Publishers

A cold publisher starts producing data for each subscriber. Each subscriber gets its own execution of the pipeline.

  • It starts emitting when a subscriber subscribes.
  • Each subscriber gets the full sequence.
  • Each subscriber usually triggers a separate execution of the source.
Flux<Integer> cold = Flux.range(1, 3);
Flux<Integer> coldNumbers = Flux.range(1, 3)
        .doOnNext(number -> System.out.println("Producing " + number));

coldNumbers.subscribe(number -> System.out.println("A: " + number));
coldNumbers.subscribe(number -> System.out.println("B: " + number));

Each subscriber receives 1, 2, 3. Real-life analogy: a recorded training video starts from the beginning for every person who presses play.

Hot Publishers

A hot publisher is a reactive stream that produces data independently of subscribers. It emits data whether or not anyone is listening, and new subscribers may miss previously emitted values.

  • It emits continuously or independently of individual subscribers.
  • Subscribers share the same stream.
  • Subscribers may miss data if they arrive late.

Think of it like live radio. If you tune in late, you do not hear what was already broadcast.

Common Examples of Hot Publishers

  • Kafka topic: messages are produced whether consumers are connected or not.
  • WebSocket messages: clients only receive messages after connecting.
  • Mouse or UI events: events happen regardless of listeners.
  • Shared interval streams: Flux.interval() can become hot when shared.
Flux<Long> hotTicks = Flux.interval(Duration.ofSeconds(1))
        .share();

hotTicks.subscribe(tick -> System.out.println("First: " + tick));

// A later subscriber sees only future ticks.
hotTicks.subscribe(tick -> System.out.println("Second: " + tick));

Real-life analogy: a live show on the ship keeps going whether or not someone is in the theater. If a guest walks in halfway through, they do not see the beginning.

Simple Hot Publisher Example

Flux<Long> hot = Flux.interval(Duration.ofSeconds(1))
        .share();

hot.subscribe(v -> System.out.println("Subscriber 1: " + v));

Thread.sleep(3000);

hot.subscribe(v -> System.out.println("Subscriber 2: " + v));
Subscriber 1: 0
Subscriber 1: 1
Subscriber 1: 2
Subscriber 2: 3   // missed 0, 1, 2

A hot publisher emits data independently of subscribers. It produces values continuously, and subscribers only receive items emitted after they subscribe. Examples include Kafka topics, WebSocket streams, UI events, and shared Flux.interval() streams.

Thinking in Reactive Pipelines

Imperative code often says: get a value, store it in a variable, check it, call something else, mutate another variable, return. Reactive code says: when the value arrives, apply this chain of operations.

Imperative Shape

Reservation reservation = repository.findById(id);

if (reservation == null) {
    throw new ReservationNotFoundException(id);
}

Payment payment = paymentClient.load(reservation.paymentId());

return mapper.toResponse(reservation, payment);

Reactive Shape

return repository.findById(id)
        .switchIfEmpty(Mono.error(
                new ReservationNotFoundException(id)))
        .flatMap(reservation ->
                paymentClient.load(reservation.paymentId())
                        .map(payment ->
                                mapper.toResponse(reservation, payment)));

The reactive version keeps the work inside the pipeline. It does not call block(), does not manually subscribe, and does not rely on mutable temporary state.

End-to-End Payment Example

This flow loads a reservation, validates that it can be paid, authorizes payment, saves the receipt, and returns a response.

public Mono<PaymentResponse> payReservation(String reservationId, PaymentRequest request) {
    return reservationRepository.findById(reservationId)
            .switchIfEmpty(Mono.error(
                    new ReservationNotFoundException(reservationId)))
            .filter(reservation -> reservation.status().equals("PENDING_PAYMENT"))
            .switchIfEmpty(Mono.error(
                    new InvalidReservationStateException(reservationId)))
            .flatMap(reservation ->
                    paymentClient.authorize(request)
                            .flatMap(receipt -> paymentRepository.save(receipt))
                            .map(savedReceipt -> new PaymentResponse(
                                    reservation.id(),
                                    savedReceipt.id(),
                                    savedReceipt.status())));
}

End-to-End Disney Cruise Example

This flow finds all confirmed reservations for a sailing, loads their payment status, keeps paid reservations, and creates boarding pass previews.

public Flux<BoardingPassPreview> previewBoardingPasses(String sailingId) {
    return reservationRepository.findBySailingId(sailingId)
            .filter(reservation -> reservation.status().equals("CONFIRMED"))
            .flatMap(reservation ->
                    paymentClient.getStatus(reservation.paymentId())
                            .filter(status -> status.equals(PaymentStatus.PAID))
                            .map(status -> new BoardingPassPreview(
                                    reservation.id(),
                                    reservation.guestName(),

Practical Rules

  • Use Mono for zero or one value.
  • Use Flux for zero to many values.
  • Use map for synchronous transformations.
  • Use flatMap for asynchronous composition.
  • Use switchIfEmpty for missing values.
  • Use onErrorResume for recovery and onErrorMap for translation.
  • Do not call block() inside WebFlux request handling.
  • Do not call subscribe() inside controllers or services just to make work happen.
  • Keep data immutable and avoid shared mutable state inside pipelines.

Reference Definition

Reactive programming is a way to build asynchronous, non-blocking data flows. In Project Reactor, Mono represents zero or one value, while Flux represents zero to many values. Reactor pipelines are lazy, so the work starts on subscription. Operators like map, filter, and flatMap compose small functions into a larger pipeline, allowing services to handle asynchronous work without blocking threads.

Reactor Deep Dive

Once the basic Mono, Flux, and operator model is clear, the next step is understanding execution: which thread runs the work, where blocking work belongs, how errors flow, how context travels, and how backpressure protects systems.

How Reactor Uses Threads

Reactor does not create threads unless the pipeline reaches an asynchronous boundary or code explicitly uses a Scheduler. By default, Reactor runs on the caller thread. There is no magic thread pool unless one is specified.

Mono.just("A")
        .map(value -> {
            System.out.println(Thread.currentThread().getName());
            return value;
        })
        .subscribe();
main

If this code is subscribed from the main thread, the simple synchronous work runs on the main thread. In WebFlux, request handling usually starts on an event-loop thread. That event-loop thread must not be blocked.

Real-life analogy: a cruise check-in employee can handle many guests efficiently if nobody makes them stand still waiting for a slow printer. If one guest blocks the employee for a long time, the whole line suffers. Event-loop threads are like those employees: keep them free and fast.

Why Threading Is Hard in Reactive Systems

Reactive systems are asynchronous, non-blocking, and concurrent. Problems happen when blocking code runs on non-blocking threads, when thread pools are exhausted, or when multiple threads share mutable state. Schedulers help by isolating different kinds of work onto thread pools designed for that purpose.

  • Blocking code on event-loop threads can create latency spikes.
  • Too many blocking calls can exhaust available threads.
  • Shared mutable state can create race conditions when work moves across threads.
  • Wrong scheduler choices can make a reactive service slower or less stable than imperative code.

Mono.fromCallable

Mono.fromCallable(...) means: create a Mono that will run this Callable later, then emit its result or emit an error signal if it throws.

A Callable<T> is similar to a Supplier<T>, but it is allowed to throw checked exceptions. That makes fromCallable useful when adapting imperative code into a reactive pipeline.

Reactive programming is non-blocking, but real systems still contain blocking code: JDBC, blocking REST clients, file I/O, legacy libraries, and calls such as Thread.sleep(...). These must be integrated without breaking the reactive system. That is where fromCallable is useful.

  • Blocking database calls such as JDBC.
  • Reading files.
  • Calling legacy libraries.
  • Any operation that returns a value and may throw.

Common Beginner Mistake

This looks innocent, but it is wrong when blockingCall() blocks:

Mono<String> mono =
        Mono.just(blockingCall());

blockingCall() is executed immediately, before any scheduler, before any subscription, and before any backpressure can apply. That can block the caller thread, the Netty event loop, or the whole application under load.

Key rule: never put blocking code inside Mono.just(). Use Mono.just(value) only when the value already exists.

Code Meaning
Mono.just(value) I already have the value.
Mono.fromCallable(fn) Call this later to get the value. 
Mono<String> mono = Mono.fromCallable(() -> {
    // This can block and can throw.
    return blockingCallThatReturnsString();
});

With fromCallable, you are not calling the method yet. You are describing how to call it later. Reactor will call it only on subscription and capture exceptions as error signals.

fromCallable is lazy. Nothing runs until someone subscribes.

Mono<String> mono = Mono.fromCallable(() -> {
    System.out.println("Calling...");
    Thread.sleep(1000);
    return "data";
});

// At this moment nothing is printed, blocked, or executed.

mono.subscribe();

fromCallable describes blocking work. subscribeOn decides where it runs. The safe pattern for unavoidable blocking code is:

Mono.fromCallable(() -> blockingCall())
        .subscribeOn(Schedulers.boundedElastic());

This runs the blocking call on a scheduler designed for blocking work, without tying up reactive event-loop threads.

Mono.fromCallable(() -> {
    throw new RuntimeException("boom");
})
.onErrorReturn("fallback");

If the callable throws, Reactor turns the exception into an error signal. That error can then be handled with operators such as onErrorReturn, onErrorResume, or onErrorMap.

Mono.fromCallable(this::blockingDbCall)
        .subscribeOn(Schedulers.boundedElastic())
        .publishOn(Schedulers.parallel())
        .map(this::cpuTransform)
        .subscribe();

Meaning: the blocking database call runs on boundedElastic, CPU work runs on parallel, and the pipeline keeps blocking work separated from reactive threads.

fromCallable defers blocking work until subscription and converts exceptions into reactive error signals. It should be paired with subscribeOn(Schedulers.boundedElastic()) to safely integrate blocking code into Reactor.

subscribeOn vs publishOn

subscribeOn controls where subscription and source-side work starts. publishOn changes the execution context for downstream operators after that point in the pipeline.

Classic rule: subscribeOn decides where the source runs; publishOn decides where downstream operators run.

subscribeOn

Use subscribeOn near a blocking or expensive source to move that source work onto the right scheduler.

Mono<PaymentStatus> status = Mono.fromCallable(() ->
        legacyPaymentClient.getStatus(paymentId))
        .subscribeOn(Schedulers.boundedElastic());

publishOn

Use publishOn when downstream processing should continue on another scheduler.

Flux<PaymentEvent> processed = paymentEvents
        .publishOn(Schedulers.parallel())
        .map(this::calculateRiskScore);
Mono.fromCallable(this::blockingCall)
        .subscribeOn(Schedulers.boundedElastic())
        .publishOn(Schedulers.parallel())
        .map(this::cpuTask)
        .subscribe();

In this example, the blocking source runs on boundedElastic. After publishOn, the CPU-oriented mapping runs on parallel.

Mono.fromCallable(() -> {
    System.out.println("source thread = " + Thread.currentThread().getName());
    return "data";
})
.subscribeOn(Schedulers.boundedElastic())
.publishOn(Schedulers.parallel())
.map(value -> {
    System.out.println("map thread = " + Thread.currentThread().getName());
    return value.toUpperCase();
})
.subscribe();

The source thread prints something like boundedElastic-.... The map thread prints something like parallel-.... That is the clean separation: source work on one scheduler, downstream CPU work on another.

Where publishOn appears matters. Only operators after publishOn move to the new scheduler.

Mono.just("x")
        .map(value -> {
            // Runs on the current thread.
            return value;
        })
        .publishOn(Schedulers.parallel())
        .map(value -> {
            // Runs on a parallel thread.
            return value;
        });

What Happens Without publishOn

If a pipeline uses subscribeOn(Schedulers.boundedElastic()) but never uses publishOn, the downstream operators continue on boundedElastic.

Mono.fromCallable(this::blockingDbCall)
        .subscribeOn(Schedulers.boundedElastic())
        .map(this::cpuTransform)
        .subscribe();

This means the blocking database call runs on boundedElastic, and cpuTransform also runs on boundedElastic. There is one scheduler and no handoff.

This is not wrong. It is safe because boundedElastic is allowed to block, and small CPU work can run there too. It may be suboptimal if the CPU work is heavy.

Mono.fromCallable(this::blockingDbCall)
        .subscribeOn(Schedulers.boundedElastic()) // I/O
        .publishOn(Schedulers.parallel())         // switch
        .map(this::cpuTransform)                  // CPU
        .subscribe();

Add publishOn(Schedulers.parallel()) when you want thread responsibility separation: boundedElastic for blocking I/O and parallel for CPU-heavy computation.

Aspect Without publishOn With publishOn
Correctness Safe Safe
Blocking safety Safe Safe
CPU efficiency Potentially suboptimal Better for heavy CPU work
Thread separation No Yes
Clarity of intent Less explicit Clearer

Common trap: you do not always need publishOn after subscribeOn(boundedElastic). It is only needed when you want to switch execution to a different scheduler. Without it, downstream operators continue on the same scheduler.

  • Use publishOn when CPU-heavy transformations follow blocking I/O.
  • Use publishOn when clear separation of responsibilities improves readability and performance under load.
  • Skip publishOn when the pipeline is short, CPU work is minimal, thread separation is unnecessary, and simplicity is preferred.

subscribeOn chooses where execution starts. publishOn is optional and only needed to change threads downstream. Missing publishOn means there is no thread switch; nothing breaks because of that alone.

Choosing the Right Scheduler

Schedulers define where work runs. Think of them as thread pools with specific purposes.

Scheduler Best For Example
Schedulers.boundedElastic() Blocking I/O or legacy blocking APIs; grows as needed within limits Mono.fromCallable(this::blockingCall).subscribeOn(Schedulers.boundedElastic())
Schedulers.parallel() CPU-bound work; fixed-size pool, usually based on CPU cores .publishOn(Schedulers.parallel()).map(this::cpuHeavyTask)
Schedulers.single() Ordered execution on one shared worker .publishOn(Schedulers.single())
Schedulers.immediate() Current thread; mostly useful for simple cases and tests No scheduling boundary 
public Mono<Reservation> loadFromBlockingLegacySystem(String id) {
    return Mono.fromCallable(() -> legacyReservationClient.findById(id))
            .subscribeOn(Schedulers.boundedElastic());
}

Use boundedElastic for unavoidable blocking work. If the whole stack is already non-blocking, such as WebClient plus R2DBC, do not add schedulers just because the code is reactive. Never run blocking work on parallel; it is meant for CPU work, not waiting on I/O.

Why Blocking Is Dangerous

Reactive threads are few, shared, and optimized for asynchronous work. Blocking them with database calls, blocking REST clients, Thread.sleep(), or file I/O can cause thread starvation, latency spikes, and eventually system instability. Blocking code must be isolated on Schedulers.boundedElastic() when it cannot be avoided.

// Correct for unavoidable blocking I/O:
Mono.fromCallable(this::blockingDbCall)
        .subscribeOn(Schedulers.boundedElastic());

// Wrong idea: parallel is for CPU work, not blocking I/O.
Mono.fromCallable(this::blockingDbCall)
        .subscribeOn(Schedulers.parallel());

Error Handling in Reactive Pipelines

In Reactor, errors are signals in the pipeline. An error is terminal unless the pipeline handles it and switches to another value or publisher.

Unlike normal imperative code, errors are not thrown down the stack in the usual try/catch style. A reactive stream communicates with three signal types:

  • onNext(value): emits a value.
  • onComplete(): completes successfully.
  • onError(error): fails and terminates the stream.

Once a stream emits onError, it is done unless an operator recovers by returning a fallback value or fallback publisher.

Operator Purpose
onErrorReturn Fallback value
onErrorResume Fallback publisher
doOnError Side effects such as logging or metrics
retry Retry immediately
retryWhen Retry with a strategy, such as delay or backoff 
Mono.fromCallable(this::callApi)
        .retry(3)
        .onErrorResume(error -> Mono.just("fallback"));

onErrorReturn

Return a fixed fallback value. Use this when the fallback is constant and the exception details do not matter.

Mono<String> status = paymentClient.status(id)
        .onErrorReturn("UNKNOWN");
Mono<String> result = Mono.fromCallable(this::callApi)
        .onErrorReturn("fallback");

onErrorResume

Recover with another reactive operation. This is the most common recovery operator because the fallback can depend on the error or call another async source.

Mono<PaymentStatus> status = paymentClient.status(id)
        .onErrorResume(TimeoutException.class, error ->
                paymentCache.lastKnownStatus(id));
Mono<String> result = Mono.fromCallable(this::callApi)
        .onErrorResume(error -> Mono.just("fallback"));

Mono<String> pathSpecific = Mono.fromCallable(this::callApi)
        .onErrorResume(TimeoutException.class, error ->
                Mono.just("timeout-fallback"))
        .onErrorResume(error ->
                Mono.just("generic-fallback"));

onErrorMap

Translate a low-level error into a domain exception. Use this when the service should expose consistent error types or hide low-level implementation details.

Mono<Receipt> receipt = paymentClient.authorize(request)
        .onErrorMap(WebClientException.class, error ->
                new PaymentProviderException("Authorization failed", error));
Mono<String> result = Mono.fromCallable(this::callApi)
        .onErrorMap(error ->
                new MyServiceException("API failed", error));

doOnError

Observe an error without recovering from it. Use it for side effects only, such as logging and metrics.

Mono<Receipt> receipt = paymentClient.authorize(request)
        .doOnError(error ->
                log.warn("Payment authorization failed", error));
mono.doOnError(error ->
        log.error("failed", error));

onErrorResume vs onErrorReturn

Operator Behavior Use When
onErrorReturn("fallback") Always returns the same fallback value. The fallback is simple, static, and does not need exception details.
onErrorResume(error -> ...) Chooses a dynamic fallback based on the exception. The fallback depends on exception type, or recovery needs another async operation. 
Mono.fromCallable(this::risky)
        .retry(2)
        .onErrorResume(error -> {
            if (error instanceof TimeoutException) {
                return Mono.just("timeout-fallback");
            }
            return Mono.error(new RuntimeException("wrapped", error));
        });

This is a common real-world pattern: retry transient failures first, use a fallback for known recoverable cases, and wrap or propagate unexpected failures.

Retry

retry(n) retries a fixed number of times immediately. The total attempts are the original attempt plus the retries.

Mono.fromCallable(this::callApi)
        .retry(2); // total attempts = 1 original + 2 retries = 3

If the operation keeps failing after retries, the stream emits onError.

retryWhen(...) retries with a strategy, such as delay, exponential backoff, or filtering which exceptions are retryable.

Mono.fromCallable(this::callApi)
        .retryWhen(Retry.backoff(2, Duration.ofMillis(200)));

Mono.fromCallable(this::callApi)
        .retryWhen(
                Retry.backoff(2, Duration.ofMillis(200))
                        .filter(error -> error instanceof TimeoutException)
        );

Production-Style Error Pattern

A common structure is: do the risky call, log if an error happens, retry if appropriate, and fall back if it still fails.

Mono.fromCallable(this::callApi)
        .doOnError(error -> log.warn("API call failed", error))
        .retryWhen(Retry.backoff(2, Duration.ofMillis(200)))
        .onErrorResume(error -> Mono.just("fallback"));

Error Operator Ordering

Ordering matters. retry must come before onErrorReturn or onErrorResume, because once the error is recovered, there is no error left to retry.

// Correct: retry first, then recover.
Mono.fromCallable(this::callApi)
        .retry(2)
        .onErrorReturn("fallback");

// Wrong: retry will not happen because the error is already handled.
Mono.fromCallable(this::callApi)
        .onErrorReturn("fallback")
        .retry(2);

Error Handling Mental Model

  • doOnError: log the crash.
  • onErrorReturn: if it crashes, use this default value.
  • onErrorResume: if it crashes, take another route.
  • retry: try again.
  • onErrorMap: rename or wrap the crash.

Be careful with blanket error mapping. If code creates a ReservationNotFoundException with switchIfEmpty, a later broad onErrorMap can accidentally convert that 404-style error into a 500-style error.

return repository.findById(id)
        .switchIfEmpty(Mono.error(new ReservationNotFoundException(id)))
        .onErrorMap(DatabaseException.class, error ->
                new ReservationDataAccessException(error));

This maps only database errors and preserves the not-found error.

Reactor Context

Reactor Context is an immutable per-subscriber key/value store that travels with the reactive chain. It is useful for metadata such as correlation IDs, trace IDs, tenant IDs, auth tokens, or request-scoped values that should not be passed manually through every method argument.

Mono<String> result = Mono.deferContextual(context ->
        Mono.just("traceId=" + context.get("traceId")))
        .contextWrite(Context.of("traceId", "abc-123"));
Mono.just("data")
        .contextWrite(context -> context.put("traceId", "123"))
        .flatMap(value ->
                Mono.deferContextual(context ->
                        Mono.just(context.get("traceId"))));

Real-life analogy: a guest wristband travels with the guest through the ship. Each station can read the wristband to know the guest's package, room, or permissions without asking them to carry separate paperwork for every activity.

public Mono<PaymentReceipt> authorize(PaymentRequest request) {
    return Mono.deferContextual(context -> {
        String correlationId = context.getOrDefault("correlationId", "missing");
        return paymentClient.authorize(request)
                .doOnNext(receipt ->
                        log.info("correlationId={} payment={}", correlationId, receipt.id()));
    });
}

Reactor Context is not ThreadLocal. It follows the reactive subscription, not a specific Java thread. Do not use Reactor Context as a replacement for domain parameters. If a value is part of the business operation, pass it normally. Use Context for cross-cutting metadata.

Backpressure

Backpressure means the consumer can control how fast the producer emits data. It is not buffering forever and it is not crashing when the consumer is slow. It is controlled flow.

Real-life analogy: imagine a factory and a delivery truck. The factory is the producer, and the truck is the consumer. Without backpressure, the factory keeps producing boxes as fast as possible even if trucks are slow and storage is limited. The warehouse fills up, boxes fall, and the system crashes. With backpressure, the truck says, "I can take 10 boxes at a time." The factory produces 10 and waits for the next request.

The Reactive Streams contract is simple: the subscriber requests n items, the publisher emits at most n items, and the subscriber requests more when it is ready. This is built in; most application code does not manually implement demand management.

Flux.range(1, 1_000)
        .doOnRequest(n -> System.out.println("Requested " + n))
        .subscribe(new BaseSubscriber<>() {
            @Override
            protected void hookOnSubscribe(Subscription subscription) {
                request(10);
            }

            @Override
            protected void hookOnNext(Integer value) {
                System.out.println(value);
                request(1);
            }
        });

What Happens by Default

For many Reactor sources and operators, backpressure is handled automatically. Reactor requests data in controlled batches instead of pulling everything into memory at once.

Flux.range(1, 1_000_000)
        .subscribe(value -> slowConsumer(value));

Behind the scenes, Reactor does not need to load all one million values into memory at the same time. Demand moves through the pipeline so memory stays safer.

When Backpressure Becomes Visible

You usually notice backpressure when the producer is much faster than the consumer, the consumer is slow, or the source is push-based, such as Kafka, WebSockets, sockets, UI events, or intervals.

Flux.interval(Duration.ofMillis(10)) // fast producer
        .doOnNext(value -> Thread.sleep(100)) // slow consumer
        .subscribe();

The producer emits every 10 ms, but the consumer takes 100 ms per item. Without demand control or an overflow strategy, memory can grow, latency can spike, and the process can fail with OutOfMemoryError.

When Backpressure Is Not Enough

Some sources cannot always be slowed down by the subscriber. Message brokers, sockets, UI events, and externally pushed streams may keep producing. In those cases, Reactor needs an explicit strategy: buffer, drop, keep latest, or fail.

Important clarification: backpressure is not buffering by default. Backpressure is demand signaling. Buffering is one possible reaction when demand is exceeded.

In real services, backpressure matters when processing event streams, WebSocket traffic, file streams, Kafka/Kinesis-like data, or any producer that can be faster than the consumer.

Flux.range(1, 100)
        .onBackpressureBuffer()
        .subscribe();

Without backpressure or a clear overflow strategy, fast producers can create memory pressure, OutOfMemoryError, high latency, and system instability.

Backpressure Strategies

  • onBackpressureBuffer: store extra items until the consumer catches up. Risk: memory growth if the consumer stays too slow.
  • onBackpressureDrop: drop items that cannot be handled. Useful for metrics, UI events, and lossy streams.
  • onBackpressureLatest: keep only the most recent item. Useful for dashboards and real-time status updates.
  • onBackpressureError: fail fast when demand is exceeded. Useful when losing data is unacceptable and buffering would be dangerous.
  • limitRate: request data upstream in smaller batches.
Flux<PaymentEvent> events = paymentEvents
        .onBackpressureBuffer(1_000)
        .limitRate(100)
        .flatMap(this::processPaymentEvent, 20);

The flatMap concurrency limit protects downstream systems by allowing only a fixed number of payment events to process at the same time.

Reactor is safer than plain async code because demand is explicit, flow is controlled, and overload behavior can be designed. In many non-reactive async systems, producers push blindly and queues grow without bounds.

Backpressure is a mechanism that allows a reactive consumer to signal demand to a producer, ensuring that data is emitted only as fast as it can be processed. This prevents overwhelming consumers and avoids memory and stability issues in asynchronous systems.

Big Picture

Reactive programming is about composing asynchronous tasks, controlling threads explicitly, avoiding blocking, handling backpressure, and handling failures declaratively. The goal is not to make code look fancy. The goal is to keep services responsive when they are waiting on databases, payment providers, event streams, and other remote systems.

Reference Answer

Reactor does not create a new thread for every operation. Work runs on the subscribing thread until an asynchronous boundary or scheduler changes it. I use boundedElastic for unavoidable blocking I/O, parallel for CPU-bound work, and avoid blocking event-loop threads in WebFlux. Errors are terminal signals unless handled with operators such as onErrorResume or onErrorMap. Reactor Context carries cross-cutting metadata like trace IDs through the pipeline. Backpressure lets subscribers control demand so fast producers do not overwhelm slower consumers, which is critical for reliable reactive and event-driven systems.

Spring WebFlux Fundamentals

Spring WebFlux is Spring's reactive web framework. It lets backend services handle HTTP requests using non-blocking I/O and reactive types such as Mono and Flux.

What Spring WebFlux Is

Spring WebFlux is an alternative to Spring MVC for building web APIs. Instead of tying one request to one blocking thread, WebFlux is designed around asynchronous, non-blocking request handling. Controller methods can return Mono<T> for one result or Flux<T> for many results.

@RestController
@RequestMapping("/api/reservations")
public class ReservationWebFluxController {
    private final ReservationService reservationService;

    public ReservationWebFluxController(ReservationService reservationService) {
        this.reservationService = reservationService;
    }

    @GetMapping("/{id}")
    public Mono<ReservationResponse> getReservation(@PathVariable String id) {
        return reservationService.findById(id);
    }
}

Real-life analogy: Spring MVC is like assigning one crew member to one guest until the entire request is finished. WebFlux is like a small coordination team that starts work, waits for async responses, and keeps helping other guests instead of standing still.

Spring MVC vs Spring WebFlux

Topic Spring MVC Spring WebFlux
Execution model Servlet-based, usually one request per thread while work is active Reactive, event-loop based, non-blocking request handling
Return types Objects, ResponseEntity, Callable, async wrappers Mono, Flux, reactive ResponseEntity
Common server Tomcat, Jetty, Undertow Netty by default in many Spring Boot WebFlux apps
Best fit Traditional CRUD APIs, blocking stacks, servlet ecosystem High-concurrency I/O, streaming, non-blocking clients and databases
Blocking tolerance Blocking is expected, within thread-pool limits Blocking event-loop threads is dangerous

Spring MVC is not obsolete. It is still an excellent choice for many backend APIs, especially when the application uses blocking libraries such as JDBC. WebFlux is most valuable when the stack is non-blocking end to end or when streaming/high concurrency is central to the service.

WebFlux Execution Model

WebFlux does not create one thread per request. Instead, it uses a small number of event-loop threads. Each request builds a reactive pipeline, and threads are released while waiting for I/O.

// Spring MVC mental model:
Request -> Thread -> Block -> Response

// Spring WebFlux mental model:
Request -> Event loop -> Reactive pipeline -> Callback -> Response

The key difference is what happens while the application waits for a database, payment provider, or another service. In a blocking model, the thread waits. In WebFlux, the event loop can keep handling other work while the asynchronous operation completes.

Netty and the Event Loop

Many WebFlux applications run on Reactor Netty by default. Netty uses a small number of event-loop threads, non-blocking sockets, and asynchronous callbacks to handle many connections. These threads are designed to stay free and react to events quickly: request received, bytes read, response ready, connection writable.

Client request
  -> Netty event loop receives request
  -> WebFlux invokes controller
  -> Controller returns Mono or Flux
  -> Non-blocking work continues
  -> Netty writes response when data is ready

Never block Netty event-loop threads. If one event-loop thread is blocked, every request depending on that thread can be delayed.

Event-loop threads are like a cruise operations desk with a few coordinators handling many radio calls. They should delegate slow work and keep moving. If one coordinator goes to physically search every cabin, the radio desk stops responding.

Why Blocking Is Dangerous in WebFlux

Blocking means a thread waits and does nothing useful. In WebFlux, blocking an event-loop thread can hurt many requests because those threads are few and shared.

@GetMapping("/bad")
public Mono<String> bad() {
    return Mono.just(blockingDbCall()); // blocks event loop
}

This blocks the Netty thread, prevents other requests from being handled efficiently, and kills scalability under load.

// Dangerous in WebFlux request handling:
public Mono<ReservationResponse> getReservation(String id) {
    Reservation reservation = blockingRepository.findById(id);
    return Mono.just(mapper.toResponse(reservation));
}

This blocks before the Mono is even returned. Under load, this can cause thread starvation, latency spikes, timeouts, and a service that appears frozen.

@GetMapping("/good")
public Mono<String> good() {
    return Mono.fromCallable(this::blockingDbCall)
            .subscribeOn(Schedulers.boundedElastic());
}

This keeps the event loop free, isolates blocking work, and allows the system to scale more safely.

// Safer if the blocking call cannot be replaced yet:
public Mono<ReservationResponse> getReservation(String id) {
    return Mono.fromCallable(() -> blockingRepository.findById(id))
            .subscribeOn(Schedulers.boundedElastic())
            .map(mapper::toResponse);
}

The better long-term option is to use non-blocking libraries when possible, such as WebClient for HTTP and reactive database drivers like R2DBC or reactive MongoDB.

When to Use WebFlux

WebFlux does not automatically mean faster raw execution. It is mainly about scalability and resource efficiency for I/O-heavy systems.

  • Use WebFlux when the service makes many non-blocking remote calls and needs high concurrency.
  • Use WebFlux for streaming responses, server-sent events, WebSocket-style flows, and event-heavy systems.
  • Use WebFlux when the database/client stack is reactive end to end.
  • Use WebFlux when backpressure-aware processing matters.
  • Use WebFlux for microservices that spend significant time waiting on other services.
  • Do not choose WebFlux only because it sounds newer. If most dependencies are blocking, Spring MVC may be simpler and more appropriate.

Do not use WebFlux when the application is mostly blocking, CPU-bound, or simple CRUD with low concurrency. In those cases, Spring MVC is often simpler and more appropriate.

Basic Reactive Controllers

A WebFlux controller should return the reactive pipeline. It should not call block() or manually call subscribe() to force execution.

GET One

@GetMapping("/{id}")
public Mono<ResponseEntity<ReservationResponse>> getById(@PathVariable String id) {
    return reservationService.findById(id)
            .map(ResponseEntity::ok)
            .switchIfEmpty(Mono.just(ResponseEntity.notFound().build()));
}

Payment System Example

This WebFlux endpoint authorizes a payment without blocking the request thread. The controller returns the pipeline, and Spring subscribes.

@PostMapping("/reservations/{id}/payments")
public Mono<ResponseEntity<PaymentResponse>> pay(
        @PathVariable String id,
        @Valid @RequestBody PaymentRequest request) {
    return paymentService.authorize(id, request)
            .map(response -> ResponseEntity.status(HttpStatus.CREATED).body(response))
            .onErrorResume(ReservationNotFoundException.class, error ->
                    Mono.just(ResponseEntity.notFound().build()));
}

The service can compose repository calls, payment-provider calls, validation, and saving without blocking.

This endpoint streams boarding pass previews as they are produced. A Flux is a good fit because there may be many reservations for one sailing.

Instead of waiting to build one giant response, the service can emit items as they become available.

Controller Rules

  • Return Mono or Flux from controllers.
  • Do not call block() in request-handling code.
  • Do not manually call subscribe() in controllers or services.
  • Use map for synchronous DTO transformations.
  • Use flatMap when calling another reactive operation.
  • Use switchIfEmpty for not-found cases.
  • Use onErrorResume for controlled fallback or response mapping.

Spring Boot

Spring Boot helps build production-ready Java services by providing auto-configuration, embedded servers, dependency injection, and integrations for web APIs, persistence, security, monitoring, and testing.

Embedded Server

A Spring Boot REST API usually runs with an embedded server such as Tomcat. Instead of deploying a WAR file to an external server, the application can often be started with:

java -jar reservation-service.jar

DispatcherServlet

The DispatcherServlet is the central entry point for Spring MVC requests. It receives the HTTP request, uses handler mappings to find the matching controller method, invokes that method, and coordinates the response.

Controller

The controller owns the HTTP boundary: routes, path variables, query parameters, request bodies, validation trigger, and response status. Controllers should stay thin and delegate business rules to services.

@RestController
@RequestMapping("/api/reservations")
public class ReservationController {

}

Service

The service layer owns the business workflow. It applies business rules, coordinates repositories and external clients, manages transactions, handles domain-level exceptions, and decides what should happen for a use case.

@Service
public class ReservationService {
    private final ReservationRepository reservationRepository;

    public ReservationService(ReservationRepository reservationRepository) {
        this.reservationRepository = reservationRepository;
    }

    public ReservationResponse getReservation(Long id) {

                reservation.getId(),
                reservation.getGuestName(),
                reservation.getStatus()
        );
    }
}

}

Most Spring beans are singleton by default, meaning one instance per Spring container. Since the same service instance can handle many requests concurrently, request-specific mutable data should stay in method parameters or local variables, not service fields.

Avoid this pattern: storing currentReservationId or similar request data as a field in a singleton service. Concurrent requests can overwrite each other's data and cause race conditions.

REST API Design

Core question: how do you design a clean, reliable REST API in Spring Boot?

Resource-Oriented URLs

REST APIs usually model URLs around resources, not actions. The URL identifies the thing, and the HTTP method expresses the action.

Good

GET /api/reservations/123
POST /api/reservations
PATCH /api/reservations/123
DELETE /api/reservations/123

Less Ideal

GET /api/getReservation?id=123
POST /api/createReservation
POST /api/updateReservation
POST /api/deleteReservation

HTTP Methods

  • GET: read a resource.
  • POST: create a resource or trigger a non-idempotent operation.
  • PUT: replace a resource.
  • PATCH: partially update a resource.
  • DELETE: delete or cancel a resource.

Status Codes

  • 200 OK: successful read or update.
  • 201 Created: resource created, often with a Location header.
  • 202 Accepted: request accepted for asynchronous processing.
  • 204 No Content: successful operation with no response body.
  • 400 Bad Request: invalid request syntax or validation failure.
  • 401 Unauthorized: missing or invalid authentication.
  • 403 Forbidden: authenticated caller is not allowed.
  • 404 Not Found: resource does not exist.
  • 409 Conflict: state conflict or duplicate business operation.
  • 429 Too Many Requests: rate limit exceeded.
  • 500 Internal Server Error: unexpected server failure.
  • 503 Service Unavailable: temporary outage or dependency unavailable.

DTOs

Use DTOs for request and response contracts instead of exposing entities directly. DTOs separate the API contract from the persistence model, prevent leaking internal fields or sensitive data, and let the API evolve without forcing every database change to become a client-facing change.

public record CreateReservationRequest(
        @NotBlank String guestName,
        @NotNull Long cruiseId,
        @Min(1) int partySize
) {}

public record ReservationResponse(
        Long id,
        String guestName,
        Long cruiseId,
        int partySize,
        String status
) {}

Validation

@Valid tells Spring to apply validation rules on the request DTO before the controller method continues. If validation fails, Spring raises a validation exception and the service layer is not called.

@PostMapping
public ResponseEntity<ReservationResponse> createReservation(
        @Valid @RequestBody CreateReservationRequest request
) {
    ReservationResponse response = reservationService.createReservation(request);
    URI location = URI.create("/api/reservations/" + response.id());
    return ResponseEntity.created(location).body(response);
}

@RestControllerAdvice centralizes exception handling across controllers. It keeps controllers clean, maps exceptions to proper HTTP status codes, and returns consistent error responses.

@RestControllerAdvice
public class ApiExceptionHandler {
    @ExceptionHandler(ReservationNotFoundException.class)
    public ResponseEntity<ApiError> handleNotFound(ReservationNotFoundException ex) {
        return ResponseEntity.status(HttpStatus.NOT_FOUND)
                .body(new ApiError("RESERVATION_NOT_FOUND", ex.getMessage()));
    }
}

Idempotency

Core question: how do you prevent duplicate side effects when a request or event is retried?

Definition

Idempotency means making the same operation once or multiple times has the same final effect. The first call may change state, but repeated calls should not create additional side effects.

DELETE /api/reservations/123

First call:  CONFIRMED -> CANCELLED
Second call: still CANCELLED

Why Retries Are Dangerous

Distributed systems retry after timeouts, dropped connections, gateway issues, service restarts, and slow downstream dependencies. The client may not know whether the server failed before processing or processed successfully but failed to return a response.

Risk: retrying a non-idempotent operation can create duplicate payments, duplicate reservations, duplicate inventory holds, duplicate loyalty points, or duplicate notifications.

HTTP Method Nuance

GET, PUT, and DELETE are usually designed to be idempotent. POST is often non-idempotent because it commonly creates a new resource or triggers a side effect. The method alone does not guarantee safety; the implementation determines the real behavior.

PUT /api/counter/increment

This is a bad design because every call increments again, even though it uses PUT.

Idempotency Key

An idempotency key is a unique value, usually generated by the client, that identifies one intended operation. If the same key is received again for the same request, the server returns the stored result instead of executing the side effect again.

POST /api/payments
Idempotency-Key: 7b9f9a3e-2e4d-4d40-9b97-9177e742ef31

The server commonly stores the idempotency key, request hash, processing status, response body, and creation time. If the same key is reused with a different request body, the server should reject it, commonly with 409 Conflict or 400 Bad Request.

Unique Constraints and Conditional Writes

A database unique constraint is stronger than a check in application code because it protects against concurrent requests. Two threads can both check for existing data at the same time and both think it does not exist. A unique constraint or conditional write is the final guard.

CREATE UNIQUE INDEX unique_reservation_deposit
ON payments (reservation_id, payment_type);

In DynamoDB, the equivalent idea is a conditional write, such as putting an item only if the idempotency key does not already exist.

Robust Processing Flow

  1. Request arrives with an idempotency key.
  2. Server tries to insert an idempotency record with status IN_PROGRESS.
  3. If insert succeeds, this request owns processing.
  4. If insert fails because the key already exists, load the existing record.
  5. If existing record is COMPLETED, return the stored response.
  6. If existing record is IN_PROGRESS, return 202 Accepted, 409 Conflict, or wait briefly depending on API design.
  7. After business processing succeeds, store the response and mark the idempotency record COMPLETED.

Event Consumers

Kafka, Kinesis, RabbitMQ, and Lambda-based consumers often operate with at-least-once delivery. That means the same event may be delivered more than once. Consumers should be idempotent by tracking event IDs, using unique constraints, using conditional writes, or making state transitions safe to repeat.

{
  "eventId": "evt-123",
  "type": "ReservationCreated",
  "reservationId": "R123"
}

Timeouts and Retries

Core question: how do you prevent a slow or unhealthy dependency from taking down your service?

Timeouts

A timeout is a limit on how long your service is willing to wait for a dependency. It prevents unbounded waiting and protects threads, memory, connection pools, and request latency.

Cascading failure: if Payment Service becomes slow and Reservation Service waits forever, Reservation Service threads can become stuck, queues grow, latency rises, and callers of Reservation Service may also start failing.

Connection Timeout vs Read Timeout

  • Connection timeout: how long the client waits to establish a connection to the dependency.
  • Read timeout: how long the client waits for the dependency to send a response after the connection is established.
Connection timeout: 500ms
Read timeout:       2s

Request Deadline

Timeouts should fit inside the overall request budget. If the client or gateway will give up after three seconds, a downstream timeout of ten seconds is not useful. Downstream timeouts should align with the caller's deadline and leave room for error handling.

Retries

A retry means trying an operation again after a failure. Retries help with temporary failures, but they can make outages worse if they add traffic to a service that is already unhealthy.

  • Good retry candidates: temporary timeouts, connection resets, 503, 504, and sometimes 429 while respecting Retry-After.
  • Bad retry candidates: 400, 401, 403, 404, validation errors, and business-rule failures.

Retry Safety

Before retrying, check whether the operation is safe. Reads are usually safe. Operations with side effects, such as payments, reservations, refunds, or inventory holds, need idempotency protection such as an idempotency key, unique constraint, or conditional write.

Retry Storms

A retry storm happens when many callers retry at the same time against a dependency that is already overloaded. The retry traffic increases pressure and can delay recovery.

Exponential Backoff and Jitter

Exponential backoff waits longer between each retry, such as 100ms, 200ms, and 400ms. Jitter adds randomness to those waits so many clients do not retry at exactly the same time.

Without jitter:
1000 clients retry at 100ms, then 200ms, then 400ms

With jitter:
some retry at 85ms, some at 117ms, some at 263ms

Practical Policy

A practical retry policy should limit attempts, use exponential backoff with jitter, respect the request deadline, retry only transient failures, and only retry operations that are safe to repeat.

Circuit Breakers

Core question: how do you stop repeated calls to a failing dependency, and how do you decide whether degraded behavior is safe?

Problem

When a dependency is slow or unavailable, repeated calls and retries can consume threads, connections, CPU, memory, and network capacity. A circuit breaker protects the caller and gives the dependency time to recover.

States

  • Closed: normal state. Calls are allowed, and the breaker records successes, failures, and slow calls.
  • Open: failure state. Calls are blocked immediately, so the service fails fast or uses a safe fallback.
  • Half-open: recovery test state. A small number of trial calls are allowed. If they succeed, the breaker closes. If they fail, it opens again.
CLOSED -> OPEN -> HALF_OPEN -> CLOSED
                   or
                   HALF_OPEN -> OPEN

Fail Fast

Fail fast means the service does not wait for a call that is likely to fail. When the circuit is open, the call is blocked immediately and returns a controlled failure or safe fallback. This keeps latency bounded and releases resources quickly.

Circuit Breaker vs Retry

Retries try again because a failure may be temporary. Circuit breakers stop trying temporarily because the dependency appears unhealthy. A common reliability pattern is timeout, limited retry, circuit breaker, then controlled failure or safe fallback.

Fallback Behavior

A fallback is an alternative response when the normal dependency call fails. Fallbacks are useful only when they are truthful and safe.

Safer Fallbacks

  • Return popular cruise activities when recommendations are unavailable.
  • Return cached non-critical content if freshness is acceptable.
  • Queue a confirmation email for retry later.
  • Accept a request as pending with 202 Accepted when asynchronous processing is appropriate.

Dangerous Fallbacks

  • Assume payment succeeded when Payment Service is unavailable.
  • Assume inventory is available when Inventory Service is unavailable.
  • Allow a request when authorization cannot be verified.
  • Return stale pricing as if it were guaranteed current pricing.

Configuration Concepts

Circuit breakers are usually configured with a failure threshold, slow-call threshold, sliding window, minimum number of calls, wait duration in open state, and permitted test calls in half-open state.

slidingWindowSize: 20
minimumNumberOfCalls: 10
failureRateThreshold: 50%
waitDurationInOpenState: 30s
permittedNumberOfCallsInHalfOpenState: 3

Observability

Circuit breaker state should be visible in metrics and logs. Useful signals include circuit state, failure rate, slow call rate, blocked calls, fallback count, dependency latency, trace ID, dependency name, and failure reason.

Error Handling and Observability

Core question: how do you return useful errors to clients while giving engineers enough data to debug production issues?

Good API Errors

A good API error response should be clear for the client, safe for security, stable for integrations, useful for debugging, and consistent across endpoints.

{
  "code": "PAYMENT_SERVICE_UNAVAILABLE",
  "message": "Payment service is temporarily unavailable",
  "traceId": "7f4a91c3"
}

Business Errors vs Technical Errors

  • Business errors: expected domain outcomes, such as payment declined, reservation not found, cabin unavailable, duplicate request, or reservation cannot be cancelled.
  • Technical errors: bugs, infrastructure failures, or dependency failures, such as timeouts, connection failures, database outages, null pointer exceptions, or Kafka publish failures.

Business and client errors usually map to 4xx. Unexpected server and dependency failures usually map to 5xx.

Stable Error Codes

Clients should not parse human-readable messages. They should rely on stable error codes like RESERVATION_NOT_FOUND, VALIDATION_ERROR, or PAYMENT_SERVICE_UNAVAILABLE. Messages can change; codes should remain stable.

Do Not Leak Internals

API responses should not expose stack traces, SQL queries, table names, internal hostnames, internal service URLs, raw library exceptions, secrets, or tokens. Keep internal details in logs and traces, linked by trace ID.

Spring Exception Handling

@RestControllerAdvice centralizes exception handling, keeps controllers clean, maps exceptions to appropriate status codes, and returns consistent error bodies.

@RestControllerAdvice
public class ApiExceptionHandler {
    @ExceptionHandler(ReservationNotFoundException.class)
    public ResponseEntity<ApiError> handleNotFound(ReservationNotFoundException ex) {
        return ResponseEntity.status(HttpStatus.NOT_FOUND)
                .body(new ApiError(
                        "RESERVATION_NOT_FOUND",
                        "Reservation was not found",
                        getTraceId()
                ));
    }
}

Logs, Metrics, Traces

  • Logs: tell what happened in a specific execution path.
  • Metrics: show health and trends over time, such as latency, error rate, throughput, memory, consumer lag, or dependency failures.
  • Traces: show where time was spent across services in a distributed request.

Useful Log Fields

Structured logs should include fields such as timestamp, level, service, operation, trace ID, span ID, safe business identifiers, dependency name, status code, duration, error code, and exception class.

{
  "level": "ERROR",
  "service": "reservation-service",
  "operation": "createReservation",
  "traceId": "abc-123",
  "reservationId": "R123",
  "dependency": "payment-service",
  "durationMs": 2050,
  "errorCode": "PAYMENT_SERVICE_TIMEOUT",
  "exception": "ReadTimeoutException"
}

Latency Investigation

  1. Check dashboards for p95/p99 latency, error rate, throughput, and affected endpoints.
  2. Check dependency metrics for payment, inventory, database, queues, streams, and external APIs.
  3. Inspect traces for slow requests and identify the slow span.
  4. Search logs by trace ID.
  5. Check recent deploys or configuration changes.
  6. Check resource saturation: CPU, memory, thread pools, database pools, and connection pools.
  7. Choose mitigation: rollback, scale, open circuit, disable feature, queue work, or increase capacity.

Synchronous vs Asynchronous Communication

Core question: how do you decide whether one service should call another directly or publish an event for later processing?

Synchronous Communication

Synchronous communication means the caller waits for the callee to respond before continuing. REST and gRPC calls are common examples.

Client
  -> Reservation Service
  -> Payment Service
  -> Reservation Service
  -> Client response

Synchronous calls are useful when the caller needs an immediate answer, such as whether payment was authorized, whether a reservation exists, or whether a user is allowed to access a resource.

Synchronous Tradeoffs

  • Benefits: simple request/response model, easier to reason about, immediate result, natural fit for user-facing reads and validations.
  • Risks: tighter coupling, dependency latency affects caller latency, failures can cascade, and every dependency needs timeouts, retries, circuit breakers, and observability.

Asynchronous Communication

Asynchronous communication means the caller publishes a message or event and does not wait for the downstream work to complete inside the same request. Kafka, RabbitMQ, Kinesis, SQS, SNS, and Lambda triggers are common examples.

Reservation Service
  -> publishes ReservationCreated event
  -> returns response

Other consumers later:
  -> Email Service sends confirmation
  -> Loyalty Service awards points
  -> Analytics Service records activity

Asynchronous Tradeoffs

  • Benefits: decouples services, absorbs traffic spikes, improves resilience, supports replay, and lets non-critical work happen in the background.
  • Risks: eventual consistency, duplicate messages, ordering issues, harder debugging, schema evolution, and more complex failure handling.

When To Use Synchronous

  • The user or caller needs an immediate answer.
  • The next step depends on the result.
  • The operation is a read or direct validation.
  • The workflow cannot honestly continue without the dependency response.

Example: a reservation service may need a synchronous payment authorization before confirming a booking.

When To Use Asynchronous

  • The work can happen later.
  • The caller does not need the final result immediately.
  • The system needs to absorb high-volume events.
  • Multiple consumers need to react to the same event.
  • The system benefits from replay, buffering, or decoupling.

Example: after a reservation is confirmed, sending emails, updating analytics, awarding loyalty points, or syncing downstream reporting can happen asynchronously.

Eventual Consistency

Asynchronous systems are often eventually consistent. One service may update immediately while another service catches up later. This is acceptable when the business can tolerate short delays, but it must be visible in product behavior and support workflows.

Senior Design Rule

Use synchronous communication when correctness or user experience requires an immediate answer. Use asynchronous communication when work can be decoupled, retried, replayed, or processed in the background. Do not make everything synchronous by default, and do not make everything event-driven if the user needs a clear immediate result.

Checkpoint Notes

  • Choose synchronous communication when the caller needs the result immediately or the next step cannot proceed without it.
  • Choose asynchronous communication when the work can happen later, the user does not need the final result immediately, or multiple consumers need to react to the same event.
  • Eventual consistency means different parts of the system may temporarily show different states, but they should converge after background processing completes.
  • Async consumers need idempotency because messages may be retried or delivered more than once.
  • A Travel-platform synchronous example is buying or confirming cruise tickets after checking payment and availability. A Travel-platform asynchronous example is sending notifications or park news updates after an event is published.

Spring Security, OAuth2, and JWT

Core question: how does a Spring Boot API authenticate and authorize a request using OAuth2 and JWT?

Authentication vs Authorization

  • Authentication: verifies who the caller is.
  • Authorization: verifies what the authenticated caller is allowed to do.

A simple way to remember it: authentication is identity; authorization is permission.

OAuth2 Roles

  • Resource owner: usually the user.
  • Client: the application requesting access, such as a mobile app, web app, or backend service.
  • Authorization server: authenticates users or clients and issues tokens, such as Okta, Auth0, Cognito, Azure AD, or Ping Identity.
  • Resource server: the protected API. A Spring Boot API commonly plays this role.

JWT Structure

A JWT is commonly used as an access token and has three parts: header, payload, and signature.

header.payload.signature
  • Header: token type and signing algorithm.
  • Payload: claims such as subject, issuer, audience, expiration, scopes, and roles.
  • Signature: proves the token was signed by a trusted issuer and was not modified.

Important: a normal JWT payload is encoded, not encrypted. Do not put secrets, credentials, or sensitive data in JWT claims unless there is a specific encrypted-token design.

Resource Server Flow

  1. Request enters the Spring Security filter chain.
  2. Bearer token filter extracts the token from the Authorization header.
  3. JWT decoder validates signature and claims such as issuer, expiration, and audience.
  4. Spring creates an authenticated principal.
  5. Scopes or roles are mapped to authorities.
  6. Authorization rules are checked.
  7. The controller is called only if access is allowed.

401 vs 403

  • 401 Unauthorized: the caller is not authenticated. Common causes include missing token, expired token, invalid signature, wrong issuer, or malformed Authorization header.
  • 403 Forbidden: the caller is authenticated but not allowed. Common causes include missing scope, wrong role, or failing a business authorization rule.

Scopes, Roles, and Business Authorization

Scopes usually describe permissions, such as reservation:read or payment:authorize. Roles usually describe who the caller is, such as GUEST, ADMIN, or SERVICE_ACCOUNT.

Endpoint-level authorization checks whether the caller can access an operation. Business authorization checks whether the caller can access this specific resource.

Endpoint permission:
Can this caller use GET /api/reservations/{id}?

Business permission:
Does reservation 123 belong to this authenticated guest?

Spring Security Configuration Concept

@Bean
SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
    return http
            .authorizeHttpRequests(auth -> auth
                    .requestMatchers(HttpMethod.GET, "/api/reservations/**")
                    .hasAuthority("SCOPE_reservation:read")
                    .requestMatchers(HttpMethod.POST, "/api/reservations")
                    .hasAuthority("SCOPE_reservation:write")
                    .anyRequest().authenticated()
            )
            .oauth2ResourceServer(oauth2 -> oauth2.jwt())
            .build();
}

Checkpoint Notes

  • Authentication verifies identity; authorization verifies permission.
  • A Spring Boot API usually acts as an OAuth2 resource server.
  • A JWT has a header, payload, and signature.
  • Do not put secrets in a normal JWT payload because it is encoded, not encrypted.
  • 401 means missing or invalid authentication; 403 means authenticated but not permitted.
  • Endpoint-level authorization is not enough when access depends on the specific resource, such as whether a reservation belongs to the authenticated guest.

Gateway and Load Balancing

Core question: how does traffic flow from a client through a gateway and load balancer into backend microservices?

Common Traffic Flow

Client
  -> DNS
  -> CDN / WAF
  -> API Gateway
  -> Load Balancer
  -> Backend Service Instance
  -> Database / Cache / Event System

API Gateway

An API gateway is the front door for API traffic. It routes requests to the right backend service and often handles cross-cutting concerns such as authentication, TLS termination, rate limiting, request limits, CORS, logging, metrics, API versioning, and request or response transformation.

Load Balancer

A load balancer distributes requests across healthy instances of a service. It supports scalability, availability, fault tolerance, rolling deployments, and traffic distribution.

Gateway vs Load Balancer

Conceptually, the gateway decides which service should handle a request, while the load balancer decides which healthy instance of that service should receive it.

/api/reservations/** -> reservation-service
reservation-service -> instance 1, 2, or 3

TLS Termination

TLS termination means the HTTPS connection ends at a layer such as the gateway, load balancer, or ingress controller. Internal traffic may then continue as HTTP or be re-encrypted with TLS or mTLS depending on the security model.

Rate Limiting

Rate limiting protects services from excessive traffic, abuse, and traffic spikes. If a caller exceeds the configured limit, the API commonly returns 429 Too Many Requests.

Health Checks

A load balancer should only send traffic to healthy instances. Spring Boot Actuator commonly exposes endpoints such as /actuator/health, but health checks need careful design so non-critical dependency failures do not remove every instance from service.

  • Liveness: asks whether the process is alive or should be restarted.
  • Readiness: asks whether the instance is ready to receive traffic.

Horizontal Scaling

Horizontal scaling means adding more service instances. Backend services should usually be stateless or externalize state to a database, cache, token, or external store so any healthy instance can handle any request.

Gateway Security vs Service Security

The gateway can enforce coarse-grained security such as token validation and scopes, but services still own fine-grained business authorization. For example, the gateway may know a caller has reservation:read, while the reservation service must check whether the reservation belongs to that authenticated guest.

Checkpoint Notes

  • The gateway routes traffic to the correct service and handles API-level policies.
  • The load balancer chooses a healthy instance of that service.
  • Gateway routing chooses the service; load balancing chooses the instance.
  • Horizontally scaled services should be stateless because requests may go to different instances, and in-memory session state is not shared reliably.
  • Liveness checks whether the process should be restarted. Readiness checks whether the instance should receive traffic.
  • Gateway-level authorization is not enough for resource-specific business rules.

JUnit 5 and Mockito

Core question: how do you unit test Spring service behavior without starting the full application or calling real dependencies?

Unit Test vs Integration Test

  • Unit test: tests one class or small unit in isolation. It is fast and usually practices repositories, external clients, publishers, or other boundaries.
  • Integration test: tests multiple components working together, such as controller, service, repository, Spring configuration, database mappings, or HTTP behavior.

JUnit 5

JUnit provides the test structure and assertions. Common annotations include @Test, @BeforeEach, @AfterEach, @DisplayName, and @ParameterizedTest.

@Test
void calculatesTotalPrice() {
    BigDecimal total = priceCalculator.calculate(2, new BigDecimal("50.00"));

    assertEquals(new BigDecimal("100.00"), total);
}

Mockito

Mockito creates fake versions of dependencies called mocks. mocks let a service be tested without a real database, real API call, real network, or real message broker.

ReservationRepository repository = practice(ReservationRepository.class);
PaymentClient paymentClient = practice(PaymentClient.class);
ReservationService service = new ReservationService(repository, paymentClient);

Stubbing

Stubbing defines what a practice should return or throw when called in a test scenario.

when(repository.findById(123L))
        .thenReturn(Optional.of(reservation));

when(paymentClient.authorize(any()))
        .thenThrow(new PaymentServiceUnavailableException());

Verification

Verification checks whether a dependency was called as expected. It can also prove that something was not called when a business rule fails.

verify(repository).findById(123L);
verify(paymentClient).authorize(any(PaymentRequest.class));
verify(reservationRepository, never()).save(any());

Mockito Annotations

@ExtendWith(MockitoExtension.class)
class ReservationServiceTest {

    @practice
    private ReservationRepository reservationRepository;

    @practice
    private PaymentClient paymentClient;

    @Injectpractices
    private ReservationService reservationService;
}
  • @practice creates mock dependencies.
  • @Injectpractices creates the class under test and injects the practices.
  • @ExtendWith(MockitoExtension.class) enables Mockito in JUnit 5.

Failure Paths

Good tests cover more than the happy path. For service methods, test not found, validation or business-rule failures, declined payments, dependency failures, duplicate/idempotency cases, and cases where a downstream call must not happen.

@Test
void doesNotCancelDepartedReservation() {
    Reservation reservation = new Reservation(123L, "DEPARTED");

    when(reservationRepository.findById(123L))
            .thenReturn(Optional.of(reservation));

    assertThrows(
            ReservationCannotBeCancelledException.class,
            () -> reservationService.cancelReservation(123L)
    );

    verify(reservationRepository, never()).save(any());
}

ArgumentCaptor

ArgumentCaptor lets a test inspect the object passed to a practice, such as the entity built by a service before saving.

ArgumentCaptor<Reservation> captor = ArgumentCaptor.forClass(Reservation.class);

verify(reservationRepository).save(captor.capture());

Reservation saved = captor.getValue();
assertEquals("CONFIRMED", saved.getStatus());

Constructor Injection and Testing

Constructor injection makes unit testing easier because dependencies are explicit. A test can create the service directly with mocks and does not need to start the Spring context or rely on field injection.

Checkpoint Notes

  • A unit test checks a small unit in isolation; an integration test checks multiple components working together.
  • Mockito mocks simulate boundaries such as repositories, external APIs, publishers, and other dependencies.
  • Stubbing defines what a practice returns or throws for a scenario.
  • Verification checks whether a practice method was called, how many times, or not called at all.
  • Failure paths matter because production failures often happen in edge cases, dependency failures, and invalid state transitions.
  • Constructor injection makes tests easier because practices can be passed directly into the class under test.

Reference Answers

What happens when a request reaches a Spring Boot service?

When a request reaches a Spring Boot service, the embedded server receives it and passes it to Spring MVC. The DispatcherServlet routes it to the matching controller method based on the HTTP method and path. The controller handles HTTP-specific concerns and delegates to a service. The service contains the business workflow and may call repositories, external services, or publish events. The repository handles persistence. The result comes back up the stack, and Spring uses Jackson to serialize the response DTO to JSON.

What is a Spring bean?

A Spring bean is an object managed by the Spring container. Spring creates it, injects its dependencies, manages its lifecycle, and can apply framework features around it. Beans can be discovered through annotations like @Service, @Repository, and @Component, or declared manually with @Bean.

Why is constructor injection preferred?

Constructor injection is preferred because dependencies are explicit, fields can be final, the object cannot be partially initialized, and the class is easy to test without Spring. It supports loose coupling and makes required collaborators visible in the class API.

What problem does Qualifier solve?

@Qualifier solves ambiguity when multiple beans match the same dependency type. If two classes implement PaymentClient, and a constructor asks for PaymentClient, Spring needs to know which implementation to inject.

Why avoid mutable request fields in services?

Most Spring beans are singleton by default, so the same service instance may handle many requests concurrently. Request-specific data should stay in method parameters or local variables. Mutable service fields can be overwritten by concurrent requests and create race conditions.

How do you design a reliable REST API?

I design REST APIs around resources, so URLs are nouns and HTTP methods express actions. I use DTOs for request and response contracts instead of exposing entities, because the API contract should be separate from the database model. I validate input at the boundary using annotations and @Valid, so invalid requests fail before business logic runs. I centralize exception handling with @RestControllerAdvice to keep controllers clean and return consistent error responses. For reliability, I think about idempotency, pagination, timeouts, retries, error codes, trace IDs, authentication, authorization, and observability. When calling another service, I make sure the call has a timeout and that retries are safe, especially for operations like payments or reservations.

What is idempotency and why does it matter?

Idempotency means that performing the same operation once or multiple times has the same final effect. It matters in distributed systems because clients, gateways, or services may retry after timeouts or network failures. If the original request succeeded but the response was lost, a retry can create duplicate side effects like duplicate payments or bookings. For risky operations, I use idempotency keys, request hashes, unique database constraints, or conditional writes. For event consumers, I assume at-least-once delivery and make handlers idempotent using event IDs or business keys.

How do you handle timeouts and retries between services?

I configure explicit timeouts for every outbound dependency call so my service does not wait indefinitely and exhaust threads, memory, or connection pools. I distinguish connection timeouts from read timeouts and align them with the overall request deadline. For retries, I only retry failures that are likely transient, such as timeouts, 503, 504, or sometimes 429 while respecting Retry-After. I avoid retrying validation, authentication, authorization, and business-rule errors. I also make sure the operation is safe to retry, either naturally idempotent or protected by an idempotency key, unique constraint, or conditional write. To avoid retry storms, I use limited attempts, exponential backoff, jitter, and eventually circuit breakers or asynchronous recovery.

How do circuit breakers and fallbacks improve reliability?

A circuit breaker prevents repeated calls to a dependency that appears unhealthy. In the closed state, calls flow normally and the breaker records successes, failures, and slow calls. If failures exceed a threshold, it opens and fails fast instead of continuing to consume resources. After a wait period, it moves to half-open and allows a small number of test calls. If they succeed, it closes; if they fail, it opens again. For fallback behavior, I only use alternatives that are truthful and safe, such as cached non-critical data, default recommendations, or queuing work for later. I would not use fallback to pretend that a payment, authorization, or inventory operation succeeded.

How do you handle errors and observability in a Spring Boot microservice?

I centralize error handling with @RestControllerAdvice so controllers stay clean and API errors are consistent. I separate expected business or client errors from unexpected server and dependency failures, map them to appropriate 4xx or 5xx status codes, and return stable error codes with safe messages and trace IDs. I avoid leaking stack traces, SQL details, tokens, or internal hostnames in API responses. For observability, I use structured logs, metrics, and distributed tracing. Logs tell me what happened, metrics show health and trends, and traces show where time was spent across services. I make sure trace or correlation IDs are propagated across service boundaries and included in logs and error responses, so production issues can be debugged quickly.

How do you choose between synchronous and asynchronous communication?

I use synchronous communication when the caller needs an immediate answer or the next step cannot proceed without the result, such as authorization, reads, validation, or payment authorization before confirming a booking. I use asynchronous communication when work can happen later, multiple consumers need to react to the same event, or the system needs buffering, replay, and decoupling. Synchronous calls are simpler but can create tight coupling and cascading failures, so they need timeouts, retries, circuit breakers, and observability. Asynchronous systems improve resilience and scalability, but require idempotent consumers, schema management, duplicate handling, ordering decisions, and acceptance of eventual consistency.

How does OAuth2/JWT work in a Spring Boot API?

In this setup, the Spring Boot API acts as an OAuth2 resource server. A client obtains an access token from an authorization server such as Okta, Cognito, or Azure AD, then sends it to the API in the Authorization: Bearer header. Spring Security's filter chain extracts the bearer token, validates the JWT signature and claims such as issuer, expiration, and audience, then creates an authenticated principal. Scopes or roles from the token are mapped to authorities and checked against endpoint rules. For finer-grained authorization, the service still needs business checks, such as whether the authenticated guest owns the reservation. If the token is missing or invalid, the API returns 401. If the token is valid but lacks permission, it returns 403.

What are the roles of a gateway and load balancer?

An API gateway is the front door for API traffic. It routes requests to the right backend service and often handles cross-cutting concerns like authentication, rate limiting, TLS termination, CORS, request limits, logging, and metrics. A load balancer distributes traffic across healthy instances of a service so the system can scale horizontally and tolerate instance failures. Conceptually, the gateway decides which service should handle the request, and the load balancer decides which instance should receive it. The gateway may enforce coarse-grained checks like token validation and scopes, but each backend service still owns fine-grained business authorization.

How do you test Spring Boot services with JUnit and Mockito?

I use JUnit 5 for test structure and assertions, and Mockito to isolate the class under test from dependencies like repositories, external clients, and publishers. For service unit tests, I usually do not start the Spring context. I instantiate the service with mocked dependencies, stub expected dependency responses, execute the method, assert the result or exception, and verify important interactions. I cover both happy paths and failure paths, such as not found, validation or business rule failures, declined payments, and dependency errors. I avoid over-mocking domain objects and prefer constructor injection because it makes unit tests simple and explicit.

Production Support

Core question: how do you investigate and stabilize a production issue without guessing?

Senior mindset: assess impact, stabilize customer/business impact first, then continue root cause analysis and prevention work.

Incident Flow

  1. Detect the issue through alerts, dashboards, logs, or user reports.
  2. Triage scope: affected endpoints, users, regions, versions, workflows, and time window.
  3. Mitigate if impact is high: rollback, feature flag off, scale, rate limit, open circuit, route traffic, or degrade non-critical functionality.
  4. Investigate using logs, metrics, traces, dependency dashboards, and recent change history.
  5. Resolve the root issue and verify recovery.
  6. Prevent recurrence with tests, alerts, dashboards, runbooks, guardrails, or code changes.

Golden Signals

Latency

How long requests or dependency calls take. Watch p50, p95, p99, database query time, and dependency latency.

Traffic

How much load the system receives: requests per second, transactions per minute, events per second, and consumer throughput.

Errors

Failure counts and rates: 4xx, 5xx, exceptions, timeouts, dependency failures, and publish failures.

Saturation

Resource pressure: CPU, memory, GC, thread pools, connection pools, queue depth, consumer lag, and database connections.

Latency Spike Checklist

  • Check whether one endpoint, all endpoints, one region, one version, or one customer group is affected.
  • Check traffic volume and retry behavior. Retry storms can double or triple load.
  • Check error rates and timeout counts.
  • Use traces to find the slow span: controller, service logic, downstream API, database, cache, or event publishing.
  • Check dependency dashboards: payment, inventory, database, Redis, Kafka/Kinesis, and third-party APIs.
  • Check saturation: CPU, memory, GC pauses, thread pool usage, HTTP/database connection pools.
  • Check recent deploys, configuration changes, feature flags, schema changes, and dependency releases.

Database Bottleneck Signs

Common symptoms include slow query logs, high database CPU, table scans, missing indexes, N+1 queries, lock waits, deadlocks, exhausted connection pools, long-running transactions, and query timeouts.

Important: increasing a database connection pool can make things worse if the database is already saturated. More concurrent queries can add pressure instead of improving throughput.

JVM and Thread Issues

For memory or GC issues, check heap usage, non-heap usage, allocation rate, GC pause duration, object retention, container restarts, and recent code changes. For thread pool exhaustion, check active thread count, queue size, blocked calls, missing timeouts, deadlocks, and slow downstream dependencies.

Root Cause Analysis

  • Timeline: when it started, when detected, actions taken, and when mitigated.
  • Impact: users, endpoints, regions, error rate, latency, and business workflows affected.
  • Root cause: what failed, why it failed, and why safeguards did not catch it.
  • Corrective actions: tests, monitoring, alerts, runbooks, retry/circuit policies, capacity changes, and deployment guardrails.

Kinesis Deep Dive

Core question: how do you process high-volume real-time events with ordering, replay, and reliability?

Mental Model

Amazon Kinesis Data Streams is a managed streaming service. Producers put records into a stream. The stream is divided into shards. Consumers read records from shards and process them in near real time.

Producer -> Kinesis Stream -> Shards -> Consumers/Lambda -> Downstream systems

Key Concepts

  • Record: one event, such as ReservationCreated or GuestCheckedIn.
  • Partition key: decides which shard receives the record.
  • Shard: unit of ordering and throughput.
  • Sequence number: position of a record inside a shard.
  • Retention: how long records remain available for replay.
  • Consumer: application, Lambda, or service that reads records.

Ordering

Kinesis preserves ordering within a shard, not globally across all shards. Records with the same partition key go to the same shard, so choose partition keys based on the ordering you need.

Partition Key Design

A good partition key spreads traffic evenly while preserving required ordering. For reservation events, reservationId may preserve ordering per reservation. A bad key like eventType can create hot shards if most events share the same type.

Scaling and Hot Shards

If one shard receives too much traffic, it becomes hot and throttles writes or reads. Fixes include better partition key distribution, increasing shard count, on-demand mode where appropriate, batching, and reducing per-record size.

Consumers and Failure Handling

  • Consumers checkpoint progress after successful processing.
  • If processing fails before checkpointing, records may be read again.
  • Consumers must be idempotent because delivery is effectively at least once.
  • Poison records need a strategy: retries, skip with alert, DLQ pattern, or quarantine storage.

Kinesis vs Kafka

Kinesis is AWS-managed and shard-based, with AWS-native integrations like Lambda and CloudWatch. Kafka is broker/partition-based and often gives more ecosystem control, but requires operating a cluster unless using a managed service. Both need partition-key design, consumer lag monitoring, replay strategy, and idempotent consumers.

Reference Answer

I would use Kinesis for high-volume real-time events when AWS-native streaming, retention, replay, and Lambda integration are useful. I design partition keys around ordering and even distribution, monitor shard throughput and iterator age, and make consumers idempotent because records can be processed more than once. If lag grows, I check consumer speed, downstream dependencies, shard count, hot shards, throttling, poison messages, and batch configuration.

DynamoDB Deep Dive

Core question: how do you design DynamoDB tables from access patterns instead of relational habits?

Mental Model

DynamoDB is a managed NoSQL key-value/document database. It is designed for predictable low-latency access at scale, but it requires modeling around queries you need to support.

Primary Key

  • Partition key: determines where data is stored and is required for efficient lookups.
  • Sort key: orders related items within the same partition and supports range queries.
PK = GUEST#123
SK = RESERVATION#2026-06-20#R789

Access-Pattern-First Design

Start by listing queries: get reservation by id, list reservations by guest, list reservations by cruise/date, find active payment by reservation, or load itinerary events by reservation. Then design keys and indexes for those queries.

GSIs and LSIs

  • GSI: alternate partition/sort key for different query patterns. It is eventually consistent.
  • LSI: alternate sort key under the same partition key, created with the table.

Capacity and Hot Partitions

Hot partitions happen when too many reads/writes hit the same partition key. Avoid low-cardinality keys like status=ACTIVE for high-volume writes. Use high-cardinality keys and distribute load.

Conditional Writes and Idempotency

Conditional writes are critical for correctness. They can enforce put only if item does not exist, implement optimistic locking, and prevent duplicate processing with idempotency keys.

Put payment record only if paymentId does not already exist.
Put processed event only if eventId does not already exist.

TTL and Streams

TTL automatically expires items such as idempotency records or temporary sessions. DynamoDB Streams emit item-level changes, commonly consumed by Lambda for downstream processing.

Reference Answer

With DynamoDB, I start from access patterns rather than normalized relational design. I choose partition and sort keys that support the main queries and distribute load, then add GSIs for alternate lookups. I watch for hot partitions, large items, and inefficient scans. For correctness, I use conditional writes for idempotency, uniqueness, and optimistic locking. I also consider TTL for temporary data and DynamoDB Streams when downstream systems need to react to changes.

Lambda Deep Dive

Core question: when is Lambda appropriate, and how do you make serverless processing reliable?

Mental Model

AWS Lambda runs code in response to events without managing servers. It is a good fit for event processing, glue logic, scheduled tasks, lightweight APIs, stream processing, and background jobs.

Common Event Sources

  • API Gateway for HTTP APIs.
  • Kinesis for streaming records.
  • DynamoDB Streams for table change events.
  • SQS for queued work and buffering.
  • S3 for object-created events.
  • EventBridge for scheduled or business events.

Cold Starts

A cold start happens when AWS initializes a new execution environment before invoking the function. It can add latency, especially with large packages, VPC networking, heavy frameworks, or low traffic. Mitigations include smaller packages, lighter initialization, provisioned concurrency for critical paths, and avoiding unnecessary startup work.

Concurrency

Lambda scales by running concurrent executions. Reserved concurrency can protect downstream systems and isolate critical functions. Too much concurrency can overwhelm databases, APIs, or streams.

Retries and DLQs

Retry behavior depends on the event source. Async invokes may retry automatically. Streams retry batches until success or until records expire unless configured with partial batch handling and failure destinations. SQS can use visibility timeout and dead-letter queues.

Idempotency

Lambda handlers must be idempotent because events can be retried. Use event IDs, idempotency tables, conditional writes, and safe state transitions to avoid duplicate side effects.

When Not To Use Lambda

  • Long-running workloads beyond Lambda limits.
  • Very latency-sensitive APIs where cold starts are unacceptable without mitigation.
  • Complex stateful workflows better handled by services or Step Functions.
  • Heavy continuous compute where containers may be more cost-effective.

Reference Answer

I use Lambda when event-driven, bursty, or background processing fits the problem, such as Kinesis consumers, DynamoDB Stream handlers, scheduled jobs, and lightweight APIs. I design handlers to be idempotent, monitor errors and duration, control concurrency to protect downstream systems, and understand retry behavior for each event source. For critical latency paths, I consider cold starts, package size, initialization work, and provisioned concurrency.

Event-Driven Architecture

Core question: how do you design an event-driven backend that handles real-time data safely?

Core Ideas

  • Event: a fact that happened, such as ReservationCreated.
  • Command: a request to do something, such as CreateReservation.
  • Producer: publishes events.
  • Consumer: reacts to events.
  • Broker/stream: Kafka, RabbitMQ, Kinesis, SNS/SQS, or EventBridge.

Reliability Rules

  • Assume at-least-once delivery and make consumers idempotent.
  • Use stable event IDs and business keys.
  • Design schemas carefully and evolve them backward-compatibly.
  • Have a retry and poison-message strategy.
  • Monitor lag, error rate, processing time, DLQ count, and downstream dependency health.

Outbox Pattern

The outbox pattern avoids losing events when database updates and event publishing must happen together. Save the business entity and an outbox event in the same database transaction. A separate worker publishes the event and marks it as published.

1. Save reservation and outbox row in one transaction.
2. Worker reads unpublished outbox rows.
3. Worker publishes ReservationCreated.
4. Worker marks outbox row as published.

Saga Pattern

A saga coordinates a multi-step distributed workflow without a single database transaction. Each step has a compensating action if later steps fail. Example: reserve cabin, authorize payment, confirm booking. If payment fails, release the cabin hold.

Kafka vs RabbitMQ vs Kinesis

  • Kafka: durable log, partitions, replay, high-throughput event streaming.
  • RabbitMQ: queue/message routing, work queues, flexible routing patterns.
  • Kinesis: AWS-managed stream, shards, retention, replay, Lambda integration.

Reference Answer

For event-driven systems, I treat events as facts and design consumers for at-least-once delivery. That means stable event IDs, idempotent handlers, duplicate detection, retry limits, poison-message handling, and observability around lag and errors. I use the outbox pattern when a database change and event publish must stay consistent. I also design event schemas to evolve safely and choose Kafka, RabbitMQ, or Kinesis based on throughput, replay, routing, cloud integration, and operational needs.
