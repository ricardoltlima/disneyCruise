Backend Engineering Reference Guide

Platform Delivery

Docker, Kubernetes, and CI/CD turn backend code into a repeatable production system. This section moves from day-to-day analogies to production-grade deployment patterns.

Docker

Core question: how do you package a backend service so it runs the same way on a laptop, in CI, and in production?

Simple Mental Model

Docker is like packing a meal kit with the exact recipe, ingredients, tools, and serving instructions. Instead of telling someone to install Java, Maven, environment variables, and system packages by hand, you ship a container image that already describes what the service needs.

A container is not a full virtual machine. It shares the host operating system kernel, but it runs the application in an isolated process environment with its own filesystem, network namespace, and runtime configuration.

Image vs Container

Image: a read-only package or blueprint, such as reservation-api:1.4.2.

Container: a running instance of that image, with process state, logs, networking, and optional mounted storage.

Day-to-Day Analogy

An image is a cake recipe plus packaged ingredients. A container is the cake being baked right now. You can bake many cakes from the same recipe, and each cake is separate.

Why Backend Teams Use Docker

  • Local development becomes closer to production.
  • CI can run tests in a consistent environment.
  • Deployment units are immutable and versioned.
  • Services can be rolled back by running a previous image tag.
  • Dependencies such as Java versions are explicit instead of hidden on a server.

Why Docker Exists

Before containers, teams often deployed applications directly onto long-lived servers. Over time, those servers drifted: one had a different Java patch version, another had an older system library, another had a manual configuration change nobody remembered. This created the classic problem: it works on my machine but fails in test or production.

Docker exists to make the application runtime explicit and portable. The source code is not the only thing that matters; the Java runtime, operating system packages, startup command, exposed port, and filesystem layout matter too. Docker captures those runtime assumptions in an image so the deployment unit is repeatable.

In software architecture terms, Docker standardizes the boundary between the application and the platform. The application team publishes an image. The platform team, Kubernetes cluster, ECS service, or CI runner knows how to run that image without understanding the build details of the application.

How Docker Fits Java

Java already packages code into JARs, but a JAR alone does not answer every runtime question. It does not guarantee which JDK runs it, how memory is configured, which port is exposed, what user runs the process, or how environment-specific settings are injected. Docker wraps the JAR with those operational decisions.

JAR Responsibility

The JAR contains compiled application code, dependencies, resources, and Spring Boot startup logic.

Image Responsibility

The image contains the runtime environment: JRE, filesystem layout, startup command, exposed port, and default runtime behavior.

For Spring Boot, Docker works especially well because the service is usually a single process with an embedded server. The container starts one Java process, exposes one port, and lets the platform restart or replace it if it fails.

Container Features That Matter

  • Layered filesystem: each Dockerfile step creates a reusable layer. If dependencies do not change, builds can reuse cached layers.
  • Image registry: images are pushed to a registry such as Docker Hub, ECR, GCR, ACR, or an internal registry.
  • Tags and digests: tags are human-friendly labels; digests identify exact immutable image content.
  • Port publishing: a container can listen on an internal port while the host maps traffic into it.
  • Volumes: external storage can be mounted into a container, but stateless backend services should avoid relying on local container state.
  • Networks: containers can communicate through virtual networks, useful in Compose or local integration environments.

Dockerfile for a Spring Boot Service

A Dockerfile is the recipe for building an image. For Java services, a common production pattern is to build the JAR separately in CI, then copy only the final artifact into a small runtime image.

FROM eclipse-temurin:21-jre
WORKDIR /app

COPY target/disney-cruise-api.jar app.jar

EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]

Multi-Stage Build

A multi-stage Dockerfile can compile the application and then copy only the final JAR into the runtime image. This keeps Maven caches and source files out of the production image.

FROM maven:3.9-eclipse-temurin-21 AS build
WORKDIR /workspace
COPY pom.xml .
COPY src ./src
RUN mvn -DskipTests package

FROM eclipse-temurin:21-jre
WORKDIR /app
COPY --from=build /workspace/target/*.jar app.jar
ENTRYPOINT ["java", "-jar", "app.jar"]

Java Memory in Containers

Java services must respect container memory limits. Modern JVMs are container-aware, but senior engineers still pay attention to heap, metaspace, thread stacks, direct buffers, and native memory. A container with a 512 MiB limit cannot safely use a 512 MiB Java heap because the JVM needs memory outside the heap too.

ENTRYPOINT ["java",
  "-XX:MaxRAMPercentage=75",
  "-XX:+ExitOnOutOfMemoryError",
  "-jar",
  "app.jar"]

MaxRAMPercentage tells the JVM to size the heap as a percentage of available container memory. ExitOnOutOfMemoryError makes the process exit on OOM so the platform can restart it instead of leaving it in a damaged state.

Layered Spring Boot Images

Spring Boot can split an executable JAR into layers: dependencies, Spring Boot loader, snapshot dependencies, and application classes. This improves Docker build caching because dependencies usually change less often than application code.

java -Djarmode=layertools -jar app.jar extract

FROM eclipse-temurin:21-jre
WORKDIR /app
COPY dependencies/ ./
COPY spring-boot-loader/ ./
COPY snapshot-dependencies/ ./
COPY application/ ./
ENTRYPOINT ["java", "org.springframework.boot.loader.launch.JarLauncher"]

This matters in CI/CD because smaller changed layers can make builds and pushes faster.

Running a Container

docker build -t disney-cruise-api:local .
docker run --rm -p 8080:8080 disney-cruise-api:local

-p 8080:8080 maps the host port to the container port. The left side is the laptop/server port; the right side is the port inside the container.

Configuration and Environment Variables

Images should be reusable across environments. Put environment-specific values outside the image, such as database URLs, log levels, and feature flags.

docker run --rm -p 8080:8080 \
  -e SPRING_PROFILES_ACTIVE=local \
  -e DATABASE_URL=jdbc:postgresql://host.docker.internal:5432/cruise \
  disney-cruise-api:local

Do not bake secrets into a Dockerfile or commit them into the image. Secrets should come from the runtime platform, such as Kubernetes Secrets, AWS Secrets Manager, or a CI secret store.

Docker Compose for Local Dependencies

Compose is useful when a developer needs the API plus local dependencies such as Postgres, Redis, or Kafka. It is not the same as Kubernetes, but it is productive for local development.

services:
  api:
    build: .
    ports:
      - "8080:8080"
    environment:
      SPRING_PROFILES_ACTIVE: local
      DATABASE_URL: jdbc:postgresql://postgres:5432/cruise
    depends_on:
      - postgres

  postgres:
    image: postgres:16
    environment:
      POSTGRES_DB: cruise
      POSTGRES_USER: cruise
      POSTGRES_PASSWORD: cruise
    ports:
      - "5432:5432"

Production Practices

  • Use specific image tags, not only latest.
  • Keep images small and remove build tools from runtime images.
  • Run as a non-root user when possible.
  • Expose health endpoints and let the platform decide if the container is healthy.
  • Send logs to stdout/stderr so the platform can collect them.
  • Scan images for known vulnerabilities in CI.

Docker and Cloud Architecture

Cloud platforms like containers because containers provide a standard scheduling unit. Whether the target is Kubernetes, AWS ECS, Azure Container Apps, Google Cloud Run, or a platform-as-a-service layer, the common contract is similar: give the platform an image, environment variables, resource requirements, health checks, and networking rules.

Docker also supports microservice architecture by making each service independently buildable and deployable. The reservation API, payment API, notification worker, and event consumer can each have their own image, release cadence, and scaling profile.

Common Mistakes

  • Putting secrets in the Dockerfile.
  • Depending on files that exist on one developer machine but not in CI.
  • Using mutable tags like latest for production rollouts.
  • Running database migrations in every container replica without coordination.
  • Writing application state inside the container filesystem and expecting it to survive replacement.

Reference Answer

Docker packages an application and its runtime dependencies into an image so the service runs consistently across environments. For a Spring Boot service, I build a JAR, copy it into a Java runtime image, inject environment-specific configuration at runtime, and publish a versioned image tag. In production I avoid baking secrets into images, keep images small, run as non-root where possible, log to stdout, expose health endpoints, and scan images in CI. Docker gives me the repeatable unit that Kubernetes or another platform can deploy.

Kubernetes

Core question: how do you run many containers reliably across a cluster while handling traffic, scaling, rollouts, failures, and configuration?

Simple Mental Model

Kubernetes is like the operations manager for a busy restaurant chain. Docker gives you a boxed meal that can be prepared consistently. Kubernetes decides how many kitchens should prepare it, where they should run, how customers reach them, what happens if a kitchen fails, and how a new recipe rolls out without closing the restaurant.

Why Kubernetes Exists

Containers solve packaging, but they do not solve operating a fleet. Once a system has many services and many containers, teams need answers to harder questions: where should each container run, how many copies should exist, how does traffic find them, what happens when a node fails, how do we deploy without downtime, how do we scale during traffic spikes, and how do we keep configuration separate from images?

Kubernetes exists as a control plane for those operational problems. Instead of manually starting containers on servers, engineers declare the desired state. Kubernetes watches the cluster and continuously works to make reality match that desired state.

In architecture terms, Kubernetes is the runtime substrate for containerized systems. It gives microservices a standard model for deployment, discovery, configuration, scaling, and failure recovery.

Main Objects

  • Pod: smallest deployable unit, usually one application container.
  • Deployment: desired state for replicated pods and rollouts.
  • Service: stable network name and load balancing for pods.
  • Ingress: HTTP routing from outside the cluster.
  • ConfigMap and Secret: runtime configuration.

Desired State

You tell Kubernetes what should be true: three replicas of this API image should be running. Kubernetes continuously reconciles reality with that desired state.

Cluster Architecture

A Kubernetes cluster has a control plane and worker nodes. The control plane stores desired state and makes scheduling decisions. Worker nodes run pods.

  • API server: front door for commands and automation. Tools like kubectl, Helm, and CI/CD systems talk to it.
  • etcd: strongly consistent store for cluster state.
  • Scheduler: chooses which node should run a new pod based on resources, constraints, and policies.
  • Controller manager: runs reconciliation loops, such as ensuring the desired number of replicas exists.
  • Kubelet: node agent that starts and monitors containers on each worker node.
  • Container runtime: runs containers, commonly through containerd.

The important mindset is reconciliation. Kubernetes is not a one-time script. Controllers keep watching and correcting drift.

Pod

A pod wraps one or more closely related containers. For backend APIs, one pod usually contains one app container. Pods are replaceable. If a pod dies, a controller can create another one.

apiVersion: v1
kind: Pod
metadata:
  name: reservation-api
spec:
  containers:
    - name: api
      image: registry.example.com/reservation-api:1.4.2
      ports:
        - containerPort: 8080

Deployment

A Deployment manages replicas and rolling updates. You rarely create standalone pods for applications because a pod alone will not replace itself if it disappears.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: reservation-api
spec:
  replicas: 3
  selector:
    matchLabels:
      app: reservation-api
  template:
    metadata:
      labels:
        app: reservation-api
    spec:
      containers:
        - name: api
          image: registry.example.com/reservation-api:1.4.2
          ports:
            - containerPort: 8080

Service

Pods are temporary and get new IP addresses when replaced. A Service gives other callers a stable name and load balances traffic across healthy pods.

apiVersion: v1
kind: Service
metadata:
  name: reservation-api
spec:
  selector:
    app: reservation-api
  ports:
    - port: 80
      targetPort: 8080

Other services can call http://reservation-api instead of tracking individual pod IPs.

Networking and Service Discovery

Kubernetes gives each pod its own IP address, but pods are temporary. Services provide stable virtual addresses and DNS names. This is why service-to-service calls should target a Service name, not a pod IP.

http://reservation-api.default.svc.cluster.local

In a backend architecture, a payment service might call a reservation service through its Service name, while external users reach the system through an ingress controller, gateway, or cloud load balancer.

Namespaces and Multi-Environment Design

Namespaces partition cluster resources. Teams often use namespaces for environments, teams, or bounded contexts.

kubectl get pods -n dev
kubectl get pods -n staging
kubectl get pods -n production

Namespaces are not a hard security boundary by themselves, but they are useful with RBAC, network policies, quotas, and deployment automation.

Ingress

Ingress routes external HTTP traffic to services. A common setup is an external load balancer pointing to an ingress controller, which routes paths or hosts to internal services.

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: reservation-api
spec:
  rules:
    - host: api.example.com
      http:
        paths:
          - path: /reservations
            pathType: Prefix
            backend:
              service:
                name: reservation-api
                port:
                  number: 80

ConfigMaps and Secrets

Configuration should vary by environment without rebuilding the image. ConfigMaps hold ordinary settings; Secrets hold sensitive values. Secrets still need careful handling because Kubernetes stores them in the cluster and exposes them to pods that are allowed to read them.

env:
  - name: SPRING_PROFILES_ACTIVE
    valueFrom:
      configMapKeyRef:
        name: reservation-api-config
        key: springProfile
  - name: DATABASE_PASSWORD
    valueFrom:
      secretKeyRef:
        name: reservation-db-secret
        key: password

Health Probes

Kubernetes needs to know if a container is alive and ready for traffic. Liveness probes restart broken containers. Readiness probes remove pods from traffic until they are ready.

livenessProbe:
  httpGet:
    path: /actuator/health/liveness
    port: 8080
  initialDelaySeconds: 30
  periodSeconds: 10

readinessProbe:
  httpGet:
    path: /actuator/health/readiness
    port: 8080
  initialDelaySeconds: 10
  periodSeconds: 5

A common mistake is using the same health check for liveness and readiness. A temporary database outage may mean the pod is not ready, but killing every pod can make the outage worse.

Spring Boot Health Integration

Spring Boot Actuator can expose liveness and readiness endpoints that map naturally to Kubernetes probes. This is one of the most important integrations between Java services and Kubernetes.

management:
  endpoint:
    health:
      probes:
        enabled: true
  health:
    livenessstate:
      enabled: true
    readinessstate:
      enabled: true

A readiness endpoint should answer whether the pod should receive traffic. A liveness endpoint should answer whether the process is fundamentally broken and needs a restart. Keeping that distinction clear prevents Kubernetes from making an outage worse.

Resource Requests and Limits

Requests tell Kubernetes how much CPU and memory a pod needs for scheduling. Limits cap usage. Without requests and limits, noisy services can starve neighbors or be scheduled onto nodes that cannot realistically support them.

resources:
  requests:
    cpu: "250m"
    memory: "512Mi"
  limits:
    cpu: "1"
    memory: "1Gi"

Scaling

Scaling can be manual or automatic. Horizontal Pod Autoscaler can increase replica count based on metrics such as CPU, memory, or custom application metrics.

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: reservation-api
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: reservation-api
  minReplicas: 3
  maxReplicas: 12
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70

Scheduling Features

Scheduling is more than placing pods randomly. Kubernetes can use labels, taints, tolerations, affinity, anti-affinity, and topology spread constraints to influence placement.

  • Node selector: run pods only on nodes with specific labels.
  • Taints and tolerations: keep general workloads away from special nodes unless they explicitly tolerate them.
  • Pod anti-affinity: avoid putting all replicas of the same service on the same node.
  • Topology spread: distribute replicas across zones or nodes for resilience.

For a critical API, spreading replicas across availability zones helps avoid a single-node or single-zone failure taking down every replica.

Storage and Stateful Workloads

Stateless services are easiest to run in Kubernetes. If a reservation API pod dies, another pod can replace it because persistent data lives in a database, not inside the pod. Stateful workloads need more care.

  • PersistentVolume: storage resource in the cluster.
  • PersistentVolumeClaim: a pod's request for storage.
  • StatefulSet: controller for workloads that need stable identity or stable storage.

Many teams run stateless Java services in Kubernetes and use managed cloud databases such as RDS, DynamoDB, Cloud SQL, or managed Redis outside the cluster.

Rolling Updates and Rollbacks

A Deployment can roll out a new image gradually. Kubernetes starts new pods, waits for readiness, and terminates old pods. If the new version fails readiness checks, rollout can pause and be rolled back.

kubectl set image deployment/reservation-api \
  api=registry.example.com/reservation-api:1.4.3

kubectl rollout status deployment/reservation-api
kubectl rollout undo deployment/reservation-api

Security Features

  • RBAC: controls who can read or change cluster resources.
  • Service accounts: give workloads an identity inside the cluster.
  • Network policies: restrict which pods can talk to each other.
  • Security contexts: control Linux-level settings such as running as non-root and read-only root filesystems.
  • Admission controllers: enforce policies before resources are accepted by the API server.
securityContext:
  runAsNonRoot: true
  readOnlyRootFilesystem: true
  allowPrivilegeEscalation: false

Kubernetes in the Cloud

Managed Kubernetes services such as Amazon EKS, Azure AKS, and Google GKE reduce the burden of running the control plane. The team still owns application manifests, workload security, scaling settings, observability, deployment strategy, and cost control.

Cloud integration commonly includes load balancers, IAM integration, managed secrets, container registries, autoscaling node groups, persistent volumes backed by cloud disks, and observability tools. Kubernetes becomes the application runtime layer sitting above cloud infrastructure.

How Kubernetes Fits Software Architecture

Kubernetes encourages services to be horizontally scalable, stateless where possible, observable, and disposable. A service should start quickly, expose health, handle termination gracefully, and externalize configuration. These are architectural qualities, not just deployment details.

server:
  shutdown: graceful

spring:
  lifecycle:
    timeout-per-shutdown-phase: 30s

Graceful shutdown matters because Kubernetes may terminate a pod during rolling updates, scaling events, or node maintenance. A Java service should stop accepting new work, finish in-flight requests where possible, and exit cleanly.

Production Practices

  • Use readiness and liveness probes based on meaningful application health endpoints.
  • Set resource requests and limits.
  • Use namespaces and RBAC to separate environments and permissions.
  • Keep secrets out of images and source control.
  • Use rolling updates, canaries, or blue/green deployments for safer releases.
  • Collect logs, metrics, and traces from pods and cluster components.
  • Use PodDisruptionBudgets for services that need minimum availability during node maintenance.

Common Mistakes

  • Confusing Docker with Kubernetes. Docker packages and runs containers; Kubernetes orchestrates them across a cluster.
  • Using only one replica for a critical API.
  • Forgetting readiness probes and sending traffic to pods before startup completes.
  • Setting memory limits too low and causing repeated OOM kills.
  • Putting environment-specific values directly in deployment YAML copied across environments.

Reference Answer

Kubernetes orchestrates containers across a cluster. I usually deploy a Spring Boot service as a Deployment with multiple replicas, expose it through a Service, route external traffic through Ingress or a gateway, and provide configuration through ConfigMaps and Secrets. I define readiness and liveness probes, resource requests and limits, and rollout strategy. Kubernetes helps with self-healing, service discovery, scaling, and rolling deployments, but it still requires careful operational design around health checks, secrets, observability, network policy, and safe release practices.

CI/CD

Core question: how do you move code from commit to production safely, repeatably, and with fast feedback?

Simple Mental Model

CI/CD is like an assembly line with quality gates. A code change enters the line. The line compiles it, tests it, packages it, scans it, and promotes it. If a station finds a problem, the line stops before the bad change reaches customers.

Continuous Integration means changes are merged frequently and validated automatically. Continuous Delivery means the application is always in a deployable state. Continuous Deployment means approved changes can automatically reach production without a manual deploy step.

Why CI/CD Exists

Without CI/CD, releases depend on manual steps, tribal knowledge, and local machines. One engineer may know how to build the service, another may know how to deploy it, and a third may know which tests to run. That process is slow, inconsistent, hard to audit, and risky during incidents.

CI/CD exists to turn delivery into a repeatable system. The pipeline becomes the documented path from source code to running service. It gives the team fast feedback, reduces manual error, creates deployment traceability, and makes production changes easier to reason about.

In architecture terms, CI/CD is the control system around the application lifecycle. It enforces quality gates, produces trusted artifacts, promotes those artifacts through environments, and connects code changes to operational outcomes.

Typical Pipeline

  1. Checkout source.
  2. Compile and run unit tests.
  3. Run static analysis and security checks.
  4. Build the application artifact.
  5. Build and scan a Docker image.
  6. Push image to a registry.
  7. Deploy to a test environment.
  8. Run integration and smoke tests.
  9. Promote to staging or production.

Senior-Level Goal

A good pipeline is not just automation. It protects production, shortens feedback loops, creates traceability, makes rollback practical, and reduces the chance that deployment depends on one person's laptop.

How CI/CD Fits Java

Java backend pipelines usually start with deterministic builds. Maven or Gradle compiles the code, runs tests, packages a JAR, and may publish artifacts. The pipeline should use a known JDK version so developers, CI, and production agree on the Java baseline.

./mvnw clean verify

verify is often better than only test because it can include integration test phases, static checks, generated sources, and packaging validation depending on the Maven configuration.

For Spring Boot, the output may be an executable JAR, a Docker image, or both. The JAR is the application artifact; the image is the deployable runtime artifact.

Simple GitHub Actions Example

name: build

on:
  pull_request:
  push:
    branches: [ main ]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: '21'
      - run: ./mvnw test

Maven Pipeline Stages

validate   -> check project structure and configuration
compile    -> compile main code
test       -> run unit tests
package    -> build JAR
verify     -> run additional checks and integration tests
install    -> publish to local Maven repository
deploy     -> publish artifact to remote repository

A CI pipeline does not always run every phase for every branch. Pull requests might run compile, unit tests, and static analysis. Main branch builds might also publish images and deploy to a lower environment.

Build, Package, and Publish an Image

jobs:
  package:
    runs-on: ubuntu-latest
    needs: test
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: '21'
      - run: ./mvnw -DskipTests package
      - run: docker build -t registry.example.com/reservation-api:${{ github.sha }} .
      - run: docker push registry.example.com/reservation-api:${{ github.sha }}

Using the commit SHA as an image tag creates traceability. If production is running image abc123, the team can identify exactly which commit produced it.

Artifact Repository and Container Registry

CI/CD separates source code from built artifacts. Source code lives in Git. Built JARs may live in a Maven repository such as Nexus, Artifactory, or GitHub Packages. Container images live in a registry such as ECR, GCR, ACR, Docker Hub, or an internal registry.

This matters because production should deploy a known artifact, not rebuild from source at deployment time. Rebuilding later can produce a different artifact due to dependency changes, plugin changes, or environment drift.

Deployment Step

A deployment step updates the runtime platform, often Kubernetes. The exact mechanism varies: Helm, Kustomize, Argo CD, Flux, Terraform, or direct kubectl.

kubectl set image deployment/reservation-api \
  api=registry.example.com/reservation-api:${GIT_SHA}

kubectl rollout status deployment/reservation-api

Pipeline Features That Matter

  • Triggers: pull request, merge to main, tag creation, scheduled run, or manual approval.
  • Stages: logical groups such as build, test, scan, package, deploy, and verify.
  • Artifacts: files or images produced by one stage and consumed by later stages.
  • Approvals: human gates for production, regulated environments, or risky changes.
  • Secrets: protected values injected into jobs without committing them to source control.
  • Caching: reuse Maven dependencies, Gradle caches, or Docker layers to speed up builds.
  • Matrix builds: test multiple Java versions, operating systems, or dependency variants.
  • Environments: dev, QA, staging, and production with different variables and approvals.

Quality Gates

  • Unit tests: fast checks for service logic and edge cases.
  • Integration tests: validate database, messaging, or external client behavior.
  • Contract tests: protect APIs between services.
  • Static analysis: catches code smells and risky patterns.
  • Dependency scanning: finds vulnerable libraries.
  • Container scanning: finds vulnerable OS packages in images.
  • Smoke tests: verify a deployed environment is basically healthy.

Test Pyramid in CI

A strong Java pipeline uses different test levels for different feedback speeds.

  • Unit tests: fast, many, run on every pull request.
  • Slice tests: focused Spring tests such as MVC, repository, or JSON serialization tests.
  • Integration tests: verify database, messaging, or HTTP clients, often with Testcontainers.
  • Contract tests: protect service-to-service API compatibility.
  • End-to-end tests: fewer, slower tests that validate critical user journeys.

The goal is not to put every possible test in every stage. The goal is fast feedback early and high confidence before production.

Environment Promotion

Build once, promote the same artifact. Do not rebuild different images for dev, staging, and production because each rebuild can produce a different result. The image should stay the same while configuration changes by environment.

Commit abc123
  -> build image reservation-api:abc123
  -> deploy same image to dev
  -> promote same image to staging
  -> promote same image to production

CI/CD and Cloud Architecture

In cloud systems, CI/CD often becomes the bridge between application code and cloud runtime. The pipeline may authenticate to a cloud provider, push an image to a cloud registry, update Kubernetes manifests, deploy to EKS or ECS, run database migrations, invalidate a CDN cache, or publish deployment metadata.

For AWS-oriented Java services, a pipeline might build a Spring Boot image, push it to ECR, update an EKS Deployment, run smoke tests through an API Gateway URL, and publish deployment status to Slack or a change-management system.

GitOps

GitOps is a deployment model where Git stores the desired runtime state. Instead of a pipeline directly changing the cluster, the pipeline updates a manifest repository. A tool such as Argo CD or Flux watches that repository and reconciles the cluster to match it.

Application repo:
  builds image reservation-api:abc123

Manifest repo:
  updates image tag from abc122 to abc123

GitOps controller:
  applies desired state to Kubernetes

This improves auditability because the deployment history is visible as Git commits. It also matches Kubernetes' desired-state model.

Deployment Strategies

Rolling Deployment

Replace old instances gradually. This is common, simple, and works well when versions are backward-compatible.

Blue/Green

Run old and new environments side by side, then switch traffic. Rollback is switching traffic back.

Canary

Send a small percentage of traffic to the new version, watch metrics, then increase traffic gradually.

Feature Flags

Deploy code separately from releasing behavior. This reduces risk for large changes and makes rollback faster.

Rollback and Database Changes

Rollback is easy when only application code changes. It gets harder with database schema changes. Safer migrations are backward-compatible:

  1. Add a nullable column or new table.
  2. Deploy code that writes both old and new shapes if needed.
  3. Backfill data.
  4. Switch reads to the new shape.
  5. Remove old columns only after all running versions no longer need them.

Feature Flags and Architecture

Feature flags let teams deploy code before exposing behavior. This is valuable in microservices because it separates technical deployment from product release. It also lets teams disable a risky path quickly without rebuilding or redeploying.

Flags should be treated as production configuration and eventually cleaned up. Old flags become hidden complexity if nobody removes them.

Secrets and Permissions

Pipelines often need credentials to push images and deploy. Those credentials should live in the CI secret store or cloud identity system, not in source code. Use least privilege: a build job may push images, but it should not have broad production admin access unless required.

Supply Chain Security

Modern CI/CD also protects the software supply chain. That means knowing what dependencies are in the build, who changed the code, which artifact was produced, whether the image was scanned, and whether the deployment used the approved artifact.

  • SBOM: software bill of materials listing dependencies.
  • Image signing: prove an image came from the expected pipeline.
  • Provenance: metadata showing how and where an artifact was built.
  • Protected branches: prevent unreviewed changes from reaching release branches.
  • Least privilege tokens: reduce blast radius if a pipeline secret is exposed.

Observability After Deployment

A mature pipeline does not stop after deploy. It watches health metrics, error rate, latency, logs, and traces. If smoke tests fail or error rate spikes, the pipeline or release process should stop promotion and make rollback obvious.

Common Mistakes

  • Manual production deployment steps that are not documented or repeatable.
  • Skipping tests to make the pipeline faster.
  • Building separate artifacts per environment.
  • Deploying without smoke tests or monitoring.
  • Letting pipeline credentials become overly broad.
  • Making database migrations that cannot support rollback.

Reference Answer

CI/CD automates the path from code change to deployed service. In CI, I compile the service, run tests, analyze code, and build a versioned artifact or Docker image. In CD, I promote the same artifact through environments, deploy with a controlled strategy, run smoke tests, and monitor production health. I treat the pipeline as a safety system: it should catch defects early, scan dependencies and images, protect secrets, provide traceability from deployment to commit, and support rollback. For database changes, I prefer backward-compatible migrations so old and new application versions can run safely during rolling deployments.
