Backend Engineering Reference Guide

Platform Delivery

Docker, Kubernetes, and CI/CD turn backend code into a repeatable production system. This section moves from day-to-day analogies to production-grade deployment patterns.

Docker

Core question: how do you package a backend service so it runs the same way on a laptop, in CI, and in production?

Simple Mental Model

Docker is like packing a meal kit with the exact recipe, ingredients, tools, and serving instructions. Instead of telling someone to install Java, Maven, environment variables, and system packages by hand, you ship a container image that already describes what the service needs.

A container is not a full virtual machine. It shares the host operating system kernel, but it runs the application in an isolated process environment with its own filesystem, network namespace, and runtime configuration.

Image vs Container

Image: a read-only package or blueprint, such as reservation-api:1.4.2.

Container: a running instance of that image, with process state, logs, networking, and optional mounted storage.

Day-to-Day Analogy

An image is a cake recipe plus packaged ingredients. A container is the cake being baked right now. You can bake many cakes from the same recipe, and each cake is separate.

Why Backend Teams Use Docker

  • Local development becomes closer to production.
  • CI can run tests in a consistent environment.
  • Deployment units are immutable and versioned.
  • Services can be rolled back by running a previous image tag.
  • Dependencies such as Java versions are explicit instead of hidden on a server.

Dockerfile for a Spring Boot Service

A Dockerfile is the recipe for building an image. For Java services, a common production pattern is to build the JAR separately in CI, then copy only the final artifact into a small runtime image.

FROM eclipse-temurin:21-jre
WORKDIR /app

COPY target/disney-cruise-api.jar app.jar

EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]

Multi-Stage Build

A multi-stage Dockerfile can compile the application and then copy only the final JAR into the runtime image. This keeps Maven caches and source files out of the production image.

FROM maven:3.9-eclipse-temurin-21 AS build
WORKDIR /workspace
COPY pom.xml .
COPY src ./src
RUN mvn -DskipTests package

FROM eclipse-temurin:21-jre
WORKDIR /app
COPY --from=build /workspace/target/*.jar app.jar
ENTRYPOINT ["java", "-jar", "app.jar"]

Running a Container

docker build -t disney-cruise-api:local .
docker run --rm -p 8080:8080 disney-cruise-api:local

-p 8080:8080 maps the host port to the container port. The left side is the laptop/server port; the right side is the port inside the container.

Configuration and Environment Variables

Images should be reusable across environments. Put environment-specific values outside the image, such as database URLs, log levels, and feature flags.

docker run --rm -p 8080:8080 \
  -e SPRING_PROFILES_ACTIVE=local \
  -e DATABASE_URL=jdbc:postgresql://host.docker.internal:5432/cruise \
  disney-cruise-api:local

Do not bake secrets into a Dockerfile or commit them into the image. Secrets should come from the runtime platform, such as Kubernetes Secrets, AWS Secrets Manager, or a CI secret store.

Docker Compose for Local Dependencies

Compose is useful when a developer needs the API plus local dependencies such as Postgres, Redis, or Kafka. It is not the same as Kubernetes, but it is productive for local development.

services:
  api:
    build: .
    ports:
      - "8080:8080"
    environment:
      SPRING_PROFILES_ACTIVE: local
      DATABASE_URL: jdbc:postgresql://postgres:5432/cruise
    depends_on:
      - postgres

  postgres:
    image: postgres:16
    environment:
      POSTGRES_DB: cruise
      POSTGRES_USER: cruise
      POSTGRES_PASSWORD: cruise
    ports:
      - "5432:5432"

Production Practices

  • Use specific image tags, not only latest.
  • Keep images small and remove build tools from runtime images.
  • Run as a non-root user when possible.
  • Expose health endpoints and let the platform decide if the container is healthy.
  • Send logs to stdout/stderr so the platform can collect them.
  • Scan images for known vulnerabilities in CI.

Common Mistakes

  • Putting secrets in the Dockerfile.
  • Depending on files that exist on one developer machine but not in CI.
  • Using mutable tags like latest for production rollouts.
  • Running database migrations in every container replica without coordination.
  • Writing application state inside the container filesystem and expecting it to survive replacement.

Reference Answer

Docker packages an application and its runtime dependencies into an image so the service runs consistently across environments. For a Spring Boot service, I build a JAR, copy it into a Java runtime image, inject environment-specific configuration at runtime, and publish a versioned image tag. In production I avoid baking secrets into images, keep images small, run as non-root where possible, log to stdout, expose health endpoints, and scan images in CI. Docker gives me the repeatable unit that Kubernetes or another platform can deploy.

Kubernetes

Core question: how do you run many containers reliably across a cluster while handling traffic, scaling, rollouts, failures, and configuration?

Simple Mental Model

Kubernetes is like the operations manager for a busy restaurant chain. Docker gives you a boxed meal that can be prepared consistently. Kubernetes decides how many kitchens should prepare it, where they should run, how customers reach them, what happens if a kitchen fails, and how a new recipe rolls out without closing the restaurant.

Main Objects

  • Pod: smallest deployable unit, usually one application container.
  • Deployment: desired state for replicated pods and rollouts.
  • Service: stable network name and load balancing for pods.
  • Ingress: HTTP routing from outside the cluster.
  • ConfigMap and Secret: runtime configuration.

Desired State

You tell Kubernetes what should be true: three replicas of this API image should be running. Kubernetes continuously reconciles reality with that desired state.

Pod

A pod wraps one or more closely related containers. For backend APIs, one pod usually contains one app container. Pods are replaceable. If a pod dies, a controller can create another one.

apiVersion: v1
kind: Pod
metadata:
  name: reservation-api
spec:
  containers:
    - name: api
      image: registry.example.com/reservation-api:1.4.2
      ports:
        - containerPort: 8080

Deployment

A Deployment manages replicas and rolling updates. You rarely create standalone pods for applications because a pod alone will not replace itself if it disappears.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: reservation-api
spec:
  replicas: 3
  selector:
    matchLabels:
      app: reservation-api
  template:
    metadata:
      labels:
        app: reservation-api
    spec:
      containers:
        - name: api
          image: registry.example.com/reservation-api:1.4.2
          ports:
            - containerPort: 8080

Service

Pods are temporary and get new IP addresses when replaced. A Service gives other callers a stable name and load balances traffic across healthy pods.

apiVersion: v1
kind: Service
metadata:
  name: reservation-api
spec:
  selector:
    app: reservation-api
  ports:
    - port: 80
      targetPort: 8080

Other services can call http://reservation-api instead of tracking individual pod IPs.

Ingress

Ingress routes external HTTP traffic to services. A common setup is an external load balancer pointing to an ingress controller, which routes paths or hosts to internal services.

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: reservation-api
spec:
  rules:
    - host: api.example.com
      http:
        paths:
          - path: /reservations
            pathType: Prefix
            backend:
              service:
                name: reservation-api
                port:
                  number: 80

ConfigMaps and Secrets

Configuration should vary by environment without rebuilding the image. ConfigMaps hold ordinary settings; Secrets hold sensitive values. Secrets still need careful handling because Kubernetes stores them in the cluster and exposes them to pods that are allowed to read them.

env:
  - name: SPRING_PROFILES_ACTIVE
    valueFrom:
      configMapKeyRef:
        name: reservation-api-config
        key: springProfile
  - name: DATABASE_PASSWORD
    valueFrom:
      secretKeyRef:
        name: reservation-db-secret
        key: password

Health Probes

Kubernetes needs to know if a container is alive and ready for traffic. Liveness probes restart broken containers. Readiness probes remove pods from traffic until they are ready.

livenessProbe:
  httpGet:
    path: /actuator/health/liveness
    port: 8080
  initialDelaySeconds: 30
  periodSeconds: 10

readinessProbe:
  httpGet:
    path: /actuator/health/readiness
    port: 8080
  initialDelaySeconds: 10
  periodSeconds: 5

A common mistake is using the same health check for liveness and readiness. A temporary database outage may mean the pod is not ready, but killing every pod can make the outage worse.

Resource Requests and Limits

Requests tell Kubernetes how much CPU and memory a pod needs for scheduling. Limits cap usage. Without requests and limits, noisy services can starve neighbors or be scheduled onto nodes that cannot realistically support them.

resources:
  requests:
    cpu: "250m"
    memory: "512Mi"
  limits:
    cpu: "1"
    memory: "1Gi"

Scaling

Scaling can be manual or automatic. Horizontal Pod Autoscaler can increase replica count based on metrics such as CPU, memory, or custom application metrics.

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: reservation-api
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: reservation-api
  minReplicas: 3
  maxReplicas: 12
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70

Rolling Updates and Rollbacks

A Deployment can roll out a new image gradually. Kubernetes starts new pods, waits for readiness, and terminates old pods. If the new version fails readiness checks, rollout can pause and be rolled back.

kubectl set image deployment/reservation-api \
  api=registry.example.com/reservation-api:1.4.3

kubectl rollout status deployment/reservation-api
kubectl rollout undo deployment/reservation-api

Production Practices

  • Use readiness and liveness probes based on meaningful application health endpoints.
  • Set resource requests and limits.
  • Use namespaces and RBAC to separate environments and permissions.
  • Keep secrets out of images and source control.
  • Use rolling updates, canaries, or blue/green deployments for safer releases.
  • Collect logs, metrics, and traces from pods and cluster components.
  • Use PodDisruptionBudgets for services that need minimum availability during node maintenance.

Common Mistakes

  • Confusing Docker with Kubernetes. Docker packages and runs containers; Kubernetes orchestrates them across a cluster.
  • Using only one replica for a critical API.
  • Forgetting readiness probes and sending traffic to pods before startup completes.
  • Setting memory limits too low and causing repeated OOM kills.
  • Putting environment-specific values directly in deployment YAML copied across environments.

Reference Answer

Kubernetes orchestrates containers across a cluster. I usually deploy a Spring Boot service as a Deployment with multiple replicas, expose it through a Service, route external traffic through Ingress or a gateway, and provide configuration through ConfigMaps and Secrets. I define readiness and liveness probes, resource requests and limits, and rollout strategy. Kubernetes helps with self-healing, service discovery, scaling, and rolling deployments, but it still requires careful operational design around health checks, secrets, observability, network policy, and safe release practices.

CI/CD

Core question: how do you move code from commit to production safely, repeatably, and with fast feedback?

Simple Mental Model

CI/CD is like an assembly line with quality gates. A code change enters the line. The line compiles it, tests it, packages it, scans it, and promotes it. If a station finds a problem, the line stops before the bad change reaches customers.

Continuous Integration means changes are merged frequently and validated automatically. Continuous Delivery means the application is always in a deployable state. Continuous Deployment means approved changes can automatically reach production without a manual deploy step.

Typical Pipeline

  1. Checkout source.
  2. Compile and run unit tests.
  3. Run static analysis and security checks.
  4. Build the application artifact.
  5. Build and scan a Docker image.
  6. Push image to a registry.
  7. Deploy to a test environment.
  8. Run integration and smoke tests.
  9. Promote to staging or production.

Senior-Level Goal

A good pipeline is not just automation. It protects production, shortens feedback loops, creates traceability, makes rollback practical, and reduces the chance that deployment depends on one person's laptop.

Simple GitHub Actions Example

name: build

on:
  pull_request:
  push:
    branches: [ main ]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: '21'
      - run: ./mvnw test

Build, Package, and Publish an Image

jobs:
  package:
    runs-on: ubuntu-latest
    needs: test
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: '21'
      - run: ./mvnw -DskipTests package
      - run: docker build -t registry.example.com/reservation-api:${{ github.sha }} .
      - run: docker push registry.example.com/reservation-api:${{ github.sha }}

Using the commit SHA as an image tag creates traceability. If production is running image abc123, the team can identify exactly which commit produced it.

Deployment Step

A deployment step updates the runtime platform, often Kubernetes. The exact mechanism varies: Helm, Kustomize, Argo CD, Flux, Terraform, or direct kubectl.

kubectl set image deployment/reservation-api \
  api=registry.example.com/reservation-api:${GIT_SHA}

kubectl rollout status deployment/reservation-api

Quality Gates

  • Unit tests: fast checks for service logic and edge cases.
  • Integration tests: validate database, messaging, or external client behavior.
  • Contract tests: protect APIs between services.
  • Static analysis: catches code smells and risky patterns.
  • Dependency scanning: finds vulnerable libraries.
  • Container scanning: finds vulnerable OS packages in images.
  • Smoke tests: verify a deployed environment is basically healthy.

Environment Promotion

Build once, promote the same artifact. Do not rebuild different images for dev, staging, and production because each rebuild can produce a different result. The image should stay the same while configuration changes by environment.

Commit abc123
  -> build image reservation-api:abc123
  -> deploy same image to dev
  -> promote same image to staging
  -> promote same image to production

Deployment Strategies

Rolling Deployment

Replace old instances gradually. This is common, simple, and works well when versions are backward-compatible.

Blue/Green

Run old and new environments side by side, then switch traffic. Rollback is switching traffic back.

Canary

Send a small percentage of traffic to the new version, watch metrics, then increase traffic gradually.

Feature Flags

Deploy code separately from releasing behavior. This reduces risk for large changes and makes rollback faster.

Rollback and Database Changes

Rollback is easy when only application code changes. It gets harder with database schema changes. Safer migrations are backward-compatible:

  1. Add a nullable column or new table.
  2. Deploy code that writes both old and new shapes if needed.
  3. Backfill data.
  4. Switch reads to the new shape.
  5. Remove old columns only after all running versions no longer need them.

Secrets and Permissions

Pipelines often need credentials to push images and deploy. Those credentials should live in the CI secret store or cloud identity system, not in source code. Use least privilege: a build job may push images, but it should not have broad production admin access unless required.

Observability After Deployment

A mature pipeline does not stop after deploy. It watches health metrics, error rate, latency, logs, and traces. If smoke tests fail or error rate spikes, the pipeline or release process should stop promotion and make rollback obvious.

Common Mistakes

  • Manual production deployment steps that are not documented or repeatable.
  • Skipping tests to make the pipeline faster.
  • Building separate artifacts per environment.
  • Deploying without smoke tests or monitoring.
  • Letting pipeline credentials become overly broad.
  • Making database migrations that cannot support rollback.

Reference Answer

CI/CD automates the path from code change to deployed service. In CI, I compile the service, run tests, analyze code, and build a versioned artifact or Docker image. In CD, I promote the same artifact through environments, deploy with a controlled strategy, run smoke tests, and monitor production health. I treat the pipeline as a safety system: it should catch defects early, scan dependencies and images, protect secrets, provide traceability from deployment to commit, and support rollback. For database changes, I prefer backward-compatible migrations so old and new application versions can run safely during rolling deployments.
