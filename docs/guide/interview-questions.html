Interview Questions

Scenario-based Java, Spring Boot, microservices, Kafka, database, and AWS system design answers for senior backend interviews.

Java Concurrency

These answers focus on race conditions, shared state, JVM boundaries, thread explosions, and consistency under concurrent access.

Multiple threads access a HashMap. What can go wrong?

HashMap is not thread-safe. If several threads access it at the same time and at least one thread writes, the map can return stale data, lose updates, throw during iteration, or corrupt its internal structure.

  • Lost updates: two threads can read the same bucket state and one write can overwrite the other.
  • Non-atomic check-then-act: code such as containsKey followed by put can race.
  • Resize corruption: concurrent writes during rehashing can lose entries or corrupt buckets.
  • Visibility issues: without synchronization, one thread may not see another thread's writes.
  • ConcurrentModificationException: iteration while another thread mutates the map may throw, but the check is best effort.
if (!map.containsKey(k)) {
    map.put(k, v);        // two threads can both pass the check
}

map.put(k, map.get(k) + 1); // increments can be lost

Use ConcurrentHashMap for shared mutable maps and use its atomic methods for compound operations.

ConcurrentHashMap<String, Integer> counts = new ConcurrentHashMap<>();
counts.merge(key, 1, Integer::sum);
OptionWhen to use it
ConcurrentHashMapUsual choice for shared maps inside one JVM. Use putIfAbsent, computeIfAbsent, merge, and compute.
Collections.synchronizedMapSimple single-lock wrapper. Synchronize manually during iteration.
Immutable mapBest when data is built once and safely published for reads.
External lockingUseful when several map operations must be one atomic unit.

What if there is more than one instance of the app? Does ConcurrentHashMap still work?

No. ConcurrentHashMap protects shared state only inside one JVM. With multiple pods, servers, or containers, every instance has its own separate memory and its own map.

  • Inconsistent data: one instance may have a newer cache value than another.
  • Broken limits: a limit of 100 per instance becomes 100 multiplied by the number of instances.
  • No cross-instance locking: computeIfAbsent works only inside one process.
  • Lost state: in-memory data disappears on restart, crash, or scale-down.
NeedCommon solution
Shared cache or key-value stateRedis, Memcached, Hazelcast, Apache Ignite
Atomic counters and rate limitsRedis INCR, Lua scripts, Bucket4j with Redis
Distributed lockRedisson, ZooKeeper, etcd, or database row locks
Durable source of truthDatabase transactions, unique constraints, optimistic locking
Cluster-safe scheduled jobShedLock, Quartz clustered mode, leader election
SessionsSpring Session with Redis or JDBC

ConcurrentHashMap is still fine for local caches, static lookup data, or per-instance state such as local metrics.

A race condition caused a duplicate payment. How do you solve this?

Locks alone are not enough. The durable fix is idempotency: running the same payment request twice must have the same effect as running it once. Enforce that in the database and with the payment provider.

  1. Find and refund existing duplicates. Check charges with the same order, user, amount, and close timestamps.
  2. Create one idempotency key per payment intent and reuse it on every retry.
  3. Store that key under a database unique constraint.
  4. Send the same key to the payment provider.
  5. Use conditional state transitions, such as UNPAID to PAYING to PAID.
  6. Use reconciliation jobs to compare your payment records with provider reports.
CREATE TABLE payments (
  id               BIGSERIAL PRIMARY KEY,
  idempotency_key  VARCHAR(64) NOT NULL UNIQUE,
  order_id         BIGINT NOT NULL,
  amount           NUMERIC(12,2) NOT NULL,
  status           VARCHAR(20) NOT NULL,
  provider_ref     VARCHAR(100),
  created_at       TIMESTAMP NOT NULL DEFAULT now()
);
@Transactional
public Payment pay(String idemKey, long orderId, BigDecimal amount) {
    try {
        paymentRepo.insertPending(idemKey, orderId, amount);
    } catch (DuplicateKeyException e) {
        return paymentRepo.findByKey(idemKey);
    }

    // Call the provider with the same idempotency key,
    // then update status to SUCCEEDED or FAILED.
}

Do not keep a database transaction open during the provider call. Insert a pending payment and commit, call the provider with the idempotency key, then update the result. If the process crashes, a recovery job checks the provider status instead of blindly charging again.

Who is the payment provider?

The provider is the payment service provider or payment gateway that actually charges the card or bank account. Examples include Stripe, Adyen, PayPal, Braintree, Checkout.com, Square, Mollie, Razorpay, Worldpay, and Authorize.net.

To find the provider in an application, check dependencies such as stripe-java or adyen-java-api-library, configuration such as STRIPE_SECRET_KEY or api.stripe.com, and the payment client or service class that creates the charge.

Thousands of threads are created, and CPU usage spikes. What would you do?

Diagnose first, then contain, then fix. Thousands of threads plus high CPU usually means unbounded thread creation, busy waiting, heavy context switching, or a retry storm.

  1. Stabilize production: rate limit, scale out, restart only if needed, and pause retrying jobs or queue consumers.
  2. Capture evidence before restarting: thread dumps, JFR, GC logs, and process metrics.
  3. Find CPU-heavy threads with top -H -p <pid>, convert the OS thread id to hex, and search for nid=0x... in jstack.
  4. Take 3 to 5 thread dumps a few seconds apart and group by thread name prefix.

A REST API takes 30 seconds because of 3 downstream calls. How would you optimize it?

Measure first, then parallelize independent calls, reduce each call's cost, and move non-critical work off the request path.

Spring Boot Questions

These answers focus on startup diagnostics, bean cycles, JPA session boundaries, transactions, and memory failures.

Startup time increases from 15 seconds to 2 minutes. How would you investigate?

Treat it as a regression. Find which phase got slower, which bean or operation is blocking, and what changed.

  1. Compare deployments, commits, dependency upgrades, profiles, and environment variables.
  2. Use log timestamps to find big gaps in startup phases.
  3. Enable ApplicationStartup and expose Actuator /startup.
  4. Take thread dumps during startup if it appears stuck.
  5. Use JFR or wall-clock profiling if the slow phase is unclear.
public static void main(String[] args) {
    SpringApplication app = new SpringApplication(MyApp.class);
    app.setApplicationStartup(new BufferingApplicationStartup(10000));
    app.run(args);
}
management.endpoints.web.exposure.include=startup

Slow Flyway/LiquibaseHeavy migration or lockMove data migrations out of startup
Slow Hibernate initSchema validation or metadata lookupsTune Hibernate settings and schema management

Circular dependency appears after deployment. How do you solve it?

A circular dependency means bean A needs B and B needs A, directly or through a chain. If it appears only after deployment, compare Spring Boot version, active profiles, conditional beans, proxying, and dependency upgrades.

The best fix is to remove the cycle by separating responsibilities.

  • Extract shared logic into a third bean.
  • Use events if one service only needs to notify another.
  • Depend on an interface in the correct layer.
  • Merge the beans if they cannot work independently.
@Service
class OrderService {
    private final ApplicationEventPublisher events;

    void placeOrder(Order order) {
        events.publishEvent(new OrderPlacedEvent(order.getId()));
    }
}

@Service
class PaymentService {
    @EventListener
    void on(OrderPlacedEvent event) {
        // handle payment workflow
    }
}

Short-term workarounds include @Lazy, ObjectProvider, or spring.main.allow-circular-references=true, but those should be treated as temporary because the cycle is usually a design problem. Spring Boot 2.6 and later disallow circular references by default.

API works locally but fails in production with LazyInitializationException.

LazyInitializationException means code touched a lazy Hibernate association after the session closed. It often works locally because Open Session in View is enabled, while production disables it.

The fix is to fetch the data you need inside the transaction and return DTOs, not JPA entities.

@Service
class OrderService {
    @Transactional(readOnly = true)
    public OrderDto getOrder(Long id) {
        Order order = repo.findWithItemsById(id).orElseThrow();
        return OrderDto.from(order);
    }
}
@Query("select o from Order o left join fetch o.items where o.id = :id")
Optional<Order> findWithItemsById(@Param("id") Long id);

@EntityGraph(attributePaths = {"items", "customer"})
Optional<Order> findWithItemsById(Long id);

Avoid fixing this with FetchType.EAGER, open-in-view=true, hibernate.enable_lazy_load_no_trans=true, or @Transactional on controllers. Set spring.jpa.open-in-view=false in every environment so the problem appears during development.

Usually the transaction was not active where expected, the exception was not a rollback trigger, or part of the work happened outside the transaction.

Microservices Questions

These answers focus on preventing cascades, handling latency, tracing, and choosing communication patterns.

Service A calls B, B calls C, and C is down. How do you prevent cascade failure?

The danger is resource exhaustion. B's threads and connections wait on C, then A waits on B, and the failure spreads upstream. Prevent it with fast failure, isolation, fallbacks, and fewer synchronous dependencies.

PatternPurpose
TimeoutsCap how long any outbound call can wait.
Circuit breakerReject calls to C quickly after repeated failures.
BulkheadGive C its own small pool so it cannot consume all of B's resources.
Retries with backoff and jitterHandle brief glitches without flooding C.
FallbackReturn cached, default, partial, or queued results.
Rate limiting and load sheddingReject excess traffic instead of queueing until everything is slow.
Deadline propagationStop downstream work when the caller's time budget has expired.
 
resilience4j:
  circuitbreaker:
    instances:
      serviceC:
        sliding-window-size: 20
        failure-rate-threshold: 50
        slow-call-duration-threshold: 2s
        wait-duration-in-open-state: 30s
  bulkhead:
    instances:
      serviceC:
        max-concurrent-calls: 20
  timelimiter:
    instances:
      serviceC:
        timeout-duration: 2s

Long term, use async messaging and local read models so B does not need C to be available synchronously.

One microservice becomes slow and affects the entire system. What patterns would you use?

A slow service is often worse than a dead one. It holds resources for longer, which grows queues and causes retry storms.

  • Set aggressive timeouts based on p99 latency.
  • Propagate deadlines so downstream services do not continue useless work.
  • Use circuit breakers with slow-call detection, not only error-rate thresholds.
  • Use bulkheads and bounded queues.
  • Use load shedding, adaptive concurrency, and retry budgets.
  • Use fallbacks, stale cache, partial responses, and graceful degradation.
  • Use async messaging or local read models for long-running dependencies.

Monitor p95 and p99 latency, queue depth, pool saturation, circuit breaker state, and bulkhead rejections. Averages hide tail latency.

How would you trace a request across 15 microservices?

Use distributed tracing. A trace ID is created at the entry point, each service creates spans, and the trace context is propagated through HTTP headers, gRPC metadata, and message headers.

ConceptMeaning
TraceThe full journey of one request.
SpanOne operation, such as an HTTP call, DB query, or Kafka publish.
Trace IDShared by every span in the trace.
Context propagationPassing trace context between services.
SamplingChoosing which traces to retain.

Use OpenTelemetry instrumentation, send spans to the OpenTelemetry Collector, and store them in Jaeger, Grafana Tempo, Zipkin, Datadog, New Relic, Honeycomb, or Dynatrace.

     -Dotel.service.name=order-service \

Put trace IDs in log lines, preserve context across async executors and Kafka, and use tail-based sampling to keep all slow and failed traces.

REST, Kafka, or gRPC: which would you choose and why?

They solve different communication problems. REST and gRPC are synchronous request/response. Kafka is asynchronous event streaming. Mature systems often use all three.

ChoiceBest forTrade-off
RESTPublic APIs, browser/mobile clients, simple CRUD, broad toolingJSON overhead and looser contracts
gRPCInternal low-latency service calls, strict contracts, streamingHarder debugging and browser support
KafkaEvents, fan-out, decoupling, replay, load absorptionEventual consistency, ordering limits, operational cost

Decision rule: if the caller needs an answer now, use REST or gRPC. If the service is announcing a fact that many consumers may react to, publish an event with Kafka.

Kafka Questions

These answers focus on duplicates, hot partitions, consumer lag, poison messages, and ordering guarantees.

Kafka consumer processes the same message twice. How would you handle it?

Duplicate delivery is normal with at-least-once messaging. Design the consumer to be idempotent so processing the same message twice has the same result as once.

CREATE TABLE processed_messages (
  message_id VARCHAR(64) PRIMARY KEY,
  processed_at TIMESTAMP NOT NULL
);
@KafkaListener(topics = "payments")
@Transactional
public void handle(PaymentEvent event) {
    try {
        processedRepo.insert(event.getEventId());
    } catch (DuplicateKeyException e) {
        log.info("Duplicate {} skipped", event.getEventId());
        return;
    }

    paymentService.apply(event);
}

Keep the dedup insert and the business update in one database transaction. Use upserts, conditional state transitions, version checks, and provider idempotency keys for external side effects. Kafka exactly-once transactions help Kafka-to-Kafka flows, but they do not make database or HTTP side effects exactly once.

One partition has much higher traffic than others. How do you fix it?

A hot partition is usually a key distribution problem. Kafka sends the same key to the same partition, so a low-cardinality key or one heavy key overloads one partition.

  1. Confirm skew with per-partition throughput and lag.
  2. Sample message keys to find hot keys.
  3. Ask what ordering is actually required.
  4. Choose a better key, such as orderId instead of tenantId, if the ordering requirement allows it.
  5. Salt hot keys when strict order for that key is not required.
  6. Move heavy tenants or event types to a separate topic if they need isolation.
String key = hotKeys.contains(tenantId)
    ? tenantId + "-" + ThreadLocalRandom.current().nextInt(8)
    : tenantId;

Adding partitions does not fix a single hot key because that key still maps to one partition. It also remaps existing keys, so use it carefully.

Consumer lag keeps increasing. How would you investigate?

Lag grows when consumers process more slowly than producers write, or when consumers are not processing at all.

PatternLikely meaning
Lag rising on all partitionsThroughput problem, slow processing, or traffic spike
Lag rising on one partitionHot key, poison message, or stuck consumer
Lag flat but highConsumers keep up but have backlog
Offsets not movingConsumer stuck, dead, or failing commits
Sawtooth lagFrequent rebalances or batch commits

Compare produce rate with consume rate, verify the consumer group is stable, check for rebalance storms, commit failures, poison messages, pod restarts, OOMKills, CPU throttling, slow DB calls, pool saturation, and blocking retries.

Fixes include batching, faster downstreams, more consumers up to the partition count, in-partition parallelism, cooperative rebalancing, static membership, dead letter topics, and better partition keys.

A message fails repeatedly during processing. What should happen next?

Do not retry forever. One poison message can block the whole partition.

Failure typeResponse
Transient timeout or 503Retry with bounded exponential backoff.
Validation or schema errorDo not retry. Send to DLT.
Consumer bugDLT, fix code, replay later.
 
@Bean
public DefaultErrorHandler errorHandler(KafkaTemplate<Object, Object> template) {
    var recoverer = new DeadLetterPublishingRecoverer(template,
        (rec, ex) -> new TopicPartition(rec.topic() + ".DLT", rec.partition()));

    var backoff = new ExponentialBackOffWithMaxRetries(3);
    backoff.setInitialInterval(1000);
    backoff.setMultiplier(2.0);

    var handler = new DefaultErrorHandler(recoverer, backoff);
    handler.addNotRetryableExceptions(
        DeserializationException.class,
        ValidationException.class,
        IllegalArgumentException.class);
    return handler;
}

The DLT should include original topic, partition, offset, key, headers, exception, attempts, and timestamps. Alert on DLT volume and provide a safe replay path. Make consumers idempotent so retries and replays are safe.

How would you guarantee message ordering for a customer?

Kafka guarantees order only within a partition. Key all customer events by customerId, keep producer retries ordered, and process sequentially per customer.

kafkaTemplate.send("customer-events", customerId, event);
enable.idempotence=true
acks=all
retries=2147483647
max.in.flight.requests.per.connection=5
  • Use the Outbox pattern so Kafka event order matches database commit order.
  • Do not hand records to an unordered thread pool inside the listener.
  • Use blocking retries if strict order matters.
  • For strict per-key recovery, pause the partition or park later events for the affected customer.
  • Add per-customer sequence numbers and apply only the next expected version.
UPDATE customer_state
SET status = :status, version = :newVersion
WHERE customer_id = :id
  AND version = :newVersion - 1;

Avoid changing partition count on a live keyed topic unless you understand the remapping impact.

Database Questions

These answers focus on slow queries, peak CPU, row-level concurrency, and very large tables.

A query that took 50 ms now takes 10 seconds. How would you troubleshoot it?

Find out whether the query is running slowly, waiting on locks or I/O, or paying for changed data volume or changed plans.

  1. Scope it: always slow or intermittent, all parameters or only some, one query or the whole database.
  2. Check whether it is waiting with pg_stat_activity, pg_locks, SHOW PROCESSLIST, or database-specific wait views.
  3. Compare the actual execution plan with the old plan.
  4. Look for stale statistics, missing indexes, predicate changes, data growth, skew, bloat, lock contention, and ORM query changes.
EXPLAIN (ANALYZE, BUFFERS) SELECT ...;
EXPLAIN ANALYZE SELECT ...;

The cheapest fix is often refreshing statistics after a bulk load. Other fixes include restoring indexes, making predicates index-friendly, adding composite indexes, rewriting joins, archiving old data, or using an emergency plan override as a stopgap.

Database CPU reaches 100% during peak hours. What steps would you take?

High CPU usually means a few expensive queries or a flood of cheap queries. Rank by total cost, not just slowest single call.

  • Find top CPU queries with pg_stat_statements, Performance Schema, Query Store, or active session views.
  • Check whether connection count, retries, or batch jobs increased.
  • Kill runaway queries and pause reporting jobs if production is impacted.
  • Fix expensive queries with indexes, plan analysis, pagination, and query rewrites.
  • Fix chatty access with batching, caching, and eliminating N+1 queries.
  • Right-size connection pools and use PgBouncer or ProxySQL when appropriate.
  • Scale with read replicas or vertical capacity after optimizing the workload.

Prevent recurrence with per-query latency alerts, statement timeouts, realistic load tests, query history, and release comparisons.

Two transactions update the same row simultaneously. How would you handle concurrency?

The risk is a lost update. The right fix depends on the data and contention level.

ScenarioApproach
Counters, stock, balancesAtomic SQL update with a guard condition
Rare conflictsOptimistic locking with @Version
High contention or moneySELECT ... FOR UPDATE with short transactions
Status transitionsConditional update on current state
Complex multi-row invariantsSERIALIZABLE isolation with retry
 
UPDATE account
SET balance = balance - 20
WHERE id = 1 AND balance >= 20;
SELECT * FROM account WHERE id = 1 FOR UPDATE;

Do not rely on synchronized or JVM locks in a multi-instance system. The consistency rule belongs in the database.

A table has hundreds of millions of records. How would you improve performance?

Stop touching most of the table. Read fewer rows, keep less hot data in the OLTP table, and move analytics or expensive reads elsewhere.

  • Identify top queries and access patterns.
  • Add composite, covering, partial, or BRIN indexes that match real queries.
  • Use keyset pagination instead of large OFFSET.
  • Keep predicates index-friendly and avoid SELECT *.
  • Partition by the key most queries filter on, usually date or tenant.
  • Archive cold data and drop old partitions instead of deleting millions of rows.
  • Use read replicas, Redis/Caffeine caches, materialized views, summary tables, CDC, Elasticsearch, ClickHouse, or a warehouse for read-heavy analytics.
  • Tune statistics, vacuum, bloat management, and storage.
  • Shard only after indexing, partitioning, archiving, and read scaling are not enough.

System Design and AWS

These answers focus on scaling APIs, rate limiting, Redis failure modes, and safe rollback after latency regressions.

API receives 100,000 requests per minute. How would you scale it?

100,000 requests per minute is about 1,700 requests per second on average. Plan for peaks of 5,000 to 8,000 RPS depending on traffic shape. The API layer is usually easier to scale than the database and downstream dependencies.

Clients Route 53 CloudFront + AWS WAF API Gateway or ALB Stateless services on ECS Fargate or EKS across multiple AZs ElastiCache Redis Aurora with read replicas or DynamoDB SQS, Kinesis, or MSK for async work
  • Clarify read/write ratio, p99 target, traffic pattern, geography, auth, and payload size.
  • Cache aggressively with CloudFront, Redis, and local Caffeine where safe.
  • Keep services stateless and auto-scale by CPU, request count, queue depth, or latency.
  • Use Aurora with read replicas and RDS Proxy, or DynamoDB for high-scale key-value workloads.
  • Move long-running work to queues and return 202 Accepted.
  • Protect with rate limiting, timeouts, circuit breakers, retries with jitter, idempotency keys, and load shedding.
  • Load test at multiple times expected peak and watch p99 latency and error rate.

Users are abusing your API. How would you implement rate limiting?

Rate limit in layers. Use edge protection for floods and app-aware limits for user, API key, tenant, or endpoint behavior. In a multi-instance app, counters need a shared store such as Redis.

AlgorithmUse
Fixed windowSimplest, but allows bursts at window boundaries.
Sliding window logExact but memory-heavy.
Sliding window counterAccurate enough and cheap.
Token bucketMost common; supports controlled bursts.
Leaky bucketSmooths output but can add latency.

Default to token bucket. Limit by IP for anonymous abuse, API key for partners, user ID for logged-in users, and endpoint plus key for expensive operations.

Return 429 Too Many Requests with Retry-After and rate-limit headers. Roll out new limits in shadow mode first, then enforce.

Redis crashes unexpectedly. How should your application behave?

The app should degrade gracefully. If Redis is only a cache, treat failures as misses. If Redis protects correctness, fail closed or fall back to a database guarantee.

Redis roleBehavior when down
CacheBypass and read from source of truth, with DB protection.
Rate limitingFail open with local fallback for most APIs; fail closed for login, OTP, and payments.
SessionsPrefer JWTs; otherwise users may need to log in again.
Distributed locksFail closed or use DB locks.
Idempotency keysFall back to DB unique constraints or reject.
Queues or streamsUse durable broker behavior, buffering, or retry.

Use short Redis timeouts, a bounded pool, a circuit breaker, local Caffeine cache, request coalescing, bulkheads, and load shedding so losing Redis does not overload the database.

Liveness checks should not depend on Redis unless the application truly cannot run without it. Use Multi-AZ Redis with automatic failover and test Redis outages in staging.

A deployment causes increased latency. How would you find the root cause and roll back safely?

Mitigate first, investigate second. If the deployment correlates with a latency regression and users are impacted, roll back or shift traffic away quickly, then use saved evidence to find the cause.

  1. Confirm the regression lines up with the deploy using version-labeled metrics and deploy markers.
  2. Compare old and new pods side by side during canary or rolling deployment.
  3. If only the new version is slow and SLOs are breached, roll back immediately.
  4. Check rollback safety: database migrations, event formats, cache keys, config changes, and backwards compatibility.
  5. Save evidence before killing bad pods: slow traces, thread dumps, JFR, logs, and metrics.

DatabaseN+1 queries, missing indexes, changed ORM fetches, migration locks

Use canaries, blue-green deployment, feature flags, GitOps rollback, and expand/contract database migrations so rollback remains safe. After fixing, redeploy gradually with automated canary analysis on p99 latency and error rate.
