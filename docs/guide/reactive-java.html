Reactive Java

Project Reactor fundamentals, deeper Reactor patterns, reactive Kafka, and reactive MongoDB.

Project Reactor Fundamentals

Project Reactor is a reactive programming library for Java. It lets backend code describe asynchronous data pipelines using Mono and Flux, instead of blocking a thread while waiting for work to finish.

What Reactive Programming Is

Reactive programming is a style where code reacts to data as it becomes available. Instead of saying "call this method, wait here, then continue", the code builds a pipeline that says "when a value arrives, transform it, validate it, maybe call another service, handle errors, and return the final result."

Reactive programming is about asynchronous execution, non-blocking processing, event-driven data flows, and backpressure-aware streams.

// Pulling data in a blocking style:
User user = repository.findById(id);

// Describing non-blocking data that will arrive later:
Mono<User> userMono = repository.findById(id);

Nothing happens until someone subscribes. In WebFlux, the framework subscribes for you when it handles the HTTP request.

Real-life analogy: a restaurant does not make one waiter stand frozen while the kitchen prepares food. The waiter takes the order, the kitchen works, and the waiter can handle other tables until the food is ready. Reactive systems follow the same idea: do not block threads while waiting for databases, APIs, queues, or files.

Mono<ReservationResponse> response = reservationRepository.findById(id)
        .filter(reservation -> reservation.status().equals("CONFIRMED"))
        .flatMap(paymentService::loadPayment)
        .map(payment -> new ReservationResponse(id, payment.status()));

The code describes the work. It does not immediately execute the work just because the pipeline was created.

Mono vs Flux

This distinction is very important: Mono is for zero or one value, and Flux is for zero to many values.

Mono<T>

A Mono represents zero or one value. It is similar to Optional<T>, but asynchronous. Use it when the operation returns one thing, or possibly nothing.

Mono<Reservation> reservation =
        reservationRepository.findById("R123");

Mono<PaymentReceipt> receipt =
        paymentService.authorize(paymentRequest);

Mono<User> userMono =
        Mono.just(new User("1"));

Examples: find by ID, make an HTTP request returning one object, authorize one payment, save one record, fetch one profile, return one HTTP response, or complete an operation with no value using Mono<Void>.

Flux<T>

A Flux represents zero to N values. It is an asynchronous stream of elements. Use it when the operation can emit multiple items.

Flux<Reservation> reservations =
        reservationRepository.findByGuestId("G123");

Flux<PaymentEvent> events =
        paymentEventConsumer.receive();

Flux<User> usersFlux =
        Flux.just(user1, user2, user3);

Examples: list users, list reservations, stream payment events, consume a Kafka topic, process Kinesis records, handle WebSocket messages, return multiple search results, or send server-sent events.

Plain rule: use Mono for one answer and Flux for many answers. A single cruise reservation lookup is Mono. A stream of all reservations for a sailing is Flux.

Mono represents an asynchronous stream that emits zero or one element, while Flux represents an asynchronous stream that can emit zero to many elements. Mono is typically used for operations like finding a user by ID or saving an entity, where only one result is expected. Flux is used for streams of data such as fetching all users, consuming messages from Kafka, or handling continuous event streams. Both represent reactive pipelines that emit data and then complete.

Mono Creation Methods

Short version:

  • Mono.fromSupplier(...): for synchronous code that returns a value.
  • Mono.fromCallable(...): for synchronous code that returns a value and may throw checked exceptions.
  • Mono.fromFuture(...): for async code that already gives you a CompletableFuture.
  • Mono.defer(...): for delaying creation of another Mono until subscription time.

Mono.fromSupplier

Use this when you have a simple synchronous function:

Mono<LocalDateTime> now = Mono.fromSupplier(LocalDateTime::now);

This runs when someone subscribes:

now.subscribe(System.out::println); // current time
now.subscribe(System.out::println); // fresh current time

Equivalent bad version:

Mono<LocalDateTime> now = Mono.just(LocalDateTime.now());

That captures the time immediately.

In your code, this could replace:

Mono.just(request)
        .map(mapper::toCruiseEntity)

with:

Mono.fromSupplier(() -> mapper.toCruiseEntity(request))

So saveCruise could start like this:

return Mono.fromSupplier(() -> mapper.toCruiseEntity(request))
        .flatMap(repository::save)
        .map(mapper::toCruiseResponse);

That is slightly cleaner because the pipeline starts with the actual work: create an entity from the request.

Mono.fromCallable

Use this when the synchronous function may throw, especially checked exceptions:

Mono<String> fileContent = Mono.fromCallable(() ->
        Files.readString(Path.of("cruise.json"))
);

Files.readString(...) can throw IOException, which is checked. fromCallable handles that and converts the exception into a Reactor error signal.

Difference from fromSupplier:

  • Supplier<T> cannot throw checked exceptions.
  • Callable<T> can throw checked exceptions.

In the current CruiseService, you probably do not need fromCallable. Mapper calls do not throw checked exceptions, and the repository is already reactive.

You could technically write:

Mono.fromCallable(() -> mapper.toCruiseEntity(request))

but fromSupplier is more accurate unless checked exceptions are involved.

Mono.fromFuture

Use this when some API gives you a CompletableFuture.

Example:

CompletableFuture<CruiseEntity> future = someAsyncClient.saveCruise(entity);

Mono<CruiseEntity> mono = Mono.fromFuture(future);

This bridges Java future-based async code into Reactor.

Example use case:

return Mono.fromSupplier(() -> mapper.toCruiseEntity(request))
        .flatMap(entity -> Mono.fromFuture(externalPricingClient.enrichPrice(entity)))
        .flatMap(repository::save)
        .map(mapper::toCruiseResponse);

In the current service, you do not need fromFuture because repository.save(...) already returns a Mono. If you wrapped it in fromFuture, that would be wrong unless the repository returned CompletableFuture.

Mono.defer

Use this when you want to delay the creation of a Mono itself.

Example:

Mono<CruiseEntity> mono = Mono.defer(() -> repository.save(entity));

That means repository.save(entity) is not even called until subscription time.

This is different from:

Mono<CruiseEntity> mono = repository.save(entity);

Usually Spring reactive repositories are already lazy, so this is often fine. But defer is useful when the method call itself should be delayed, or when you need fresh state per subscription.

Example:

Mono<String> token = Mono.defer(() -> {
    String currentToken = tokenProvider.getCurrentToken();
    return authClient.validate(currentToken);
});

Recommendation for CruiseService

Use Mono.defer if you want the logging and mapper work to happen only at subscription time. Use Mono.fromSupplier for the mapper step if you want to be explicit that mapping is synchronous work inside the reactive pipeline. You do not need fromCallable or fromFuture here right now.

Main Reason to Change from Mono.just to Mono.fromSupplier

The main reason is when you want the value to be created at subscription time instead of pipeline creation time.

This:

Mono.just(LocalDateTime.now())

runs LocalDateTime.now() immediately and stores that value.

This:

Mono.fromSupplier(LocalDateTime::now)

stores the function and calls it later, every time someone subscribes.

So:

Mono<LocalDateTime> justMono = Mono.just(LocalDateTime.now());
Mono<LocalDateTime> supplierMono = Mono.fromSupplier(LocalDateTime::now);

If you subscribe 5 seconds later:

  • justMono: old timestamp from when the Mono was created.
  • supplierMono: fresh timestamp from subscription time.

In your service, changing this:

Mono.just(request)
        .map(mapper::toCruiseEntity)

to this:

Mono.fromSupplier(() -> mapper.toCruiseEntity(request))

means the mapper call itself is clearly modeled as a deferred synchronous operation.

But in your current code, mapper.toCruiseEntity(request) is already inside .map(...), so it already runs at subscription time. The benefit is not huge there.

The stronger reason would be avoiding this kind of mistake:

Mono.just(mapper.toCruiseEntity(request))

That calls the mapper immediately.

Better:

Mono.fromSupplier(() -> mapper.toCruiseEntity(request))

That calls the mapper on subscription.

Rule:

  • Use Mono.just(value) when the value already exists.
  • Use Mono.fromSupplier(() -> createValue()) when creating the value involves code you want to run later, lazily, inside the reactive flow.

Lazy Execution

Reactor pipelines are lazy. Creating a Mono or Flux usually describes work, but the work does not start until something subscribes.

Project Reactor is considered lazy because a reactive pipeline is not executed until a Subscriber subscribes to a Publisher. Defining a Mono or Flux only describes how data should flow, but no work is done upfront.

When a subscriber subscribes, it also signals demand, which allows Reactor to control the flow of data through backpressure. This laziness avoids unnecessary computation, gives the subscriber control over consumption, and is essential for building efficient, non-blocking systems.

Mono<String> guestName = Mono.fromCallable(() -> {
    System.out.println("Loading guest");
    return "Ana";
});

// Nothing printed yet.

guestName.subscribe(System.out::println);
// Now "Loading guest" runs, then "Ana" is printed.

In Spring WebFlux controllers, you normally do not call subscribe() yourself. You return the Mono or Flux, and Spring subscribes as part of handling the HTTP request.

@GetMapping("/reservations/{id}")
public Mono<ReservationResponse> getReservation(@PathVariable String id) {
    return reservationService.getReservation(id);
}

Most Important Reactor Operators

Operator Purpose
map Transform data
filter Keep matching data
flatMap Async composition
defaultIfEmpty Fallback value
switchIfEmpty Alternate publisher
doOnNext Side effects, such as logging

map

Use map for synchronous one-to-one transformations.

Mono<ReservationResponse> response =
        reservationMono.map(reservation ->
                new ReservationResponse(
                        reservation.id(),
                        reservation.guestName(),
                        reservation.status()));

flatMap

Use flatMap when the next step returns another Mono or Flux, usually an asynchronous operation.

Mono<PaymentReceipt> receipt =
        reservationMono.flatMap(reservation ->
                paymentService.authorize(reservation.id()));

If the function returns Mono<PaymentReceipt>, flatMap keeps the result as Mono<PaymentReceipt> instead of creating Mono<Mono<PaymentReceipt>>.

flatMap is used when composing asynchronous operations. If the mapping function returns another reactive type like Mono or Flux, using map would result in a nested publisher such as Mono<Mono<T>>. flatMap flattens this structure and keeps the pipeline as a single reactive stream, allowing the pipeline to continue correctly.

filter

Use filter to keep only values that pass a rule. If a Mono value does not pass, it becomes empty.

Mono<Reservation> activeReservation =
        reservationMono.filter(reservation ->
                !reservation.status().equals("CANCELLED"));

switchIfEmpty

Use switchIfEmpty when no value was emitted. It is common for 404-style behavior.

Mono<Reservation> reservation = repository.findById(id)
        .switchIfEmpty(Mono.error(
                new ReservationNotFoundException(id)));

onErrorResume

Use onErrorResume to recover from an error with another publisher.

Mono<PaymentStatus> status = paymentClient.getStatus(paymentId)
        .onErrorResume(TimeoutException.class, error ->
                Mono.just(PaymentStatus.UNKNOWN));

Use fallbacks only when they are truthful. Do not pretend a payment succeeded if the payment provider failed.

onErrorMap

Use onErrorMap to translate one exception into another.

Mono<PaymentReceipt> receipt = paymentClient.authorize(request)
        .onErrorMap(WebClientException.class, error ->
                new PaymentProviderException("Payment provider failed", error));

doOnNext and doOnError

Use doOnNext and doOnError for observation such as logging or metrics. Avoid putting core business changes there.

Mono<Reservation> reservation = repository.findById(id)
        .doOnNext(value -> log.info("Loaded reservation {}", value.id()))
        .doOnError(error -> log.warn("Reservation load failed", error));

then and thenReturn

Use then when you care that one operation completes before another starts, but you do not need the previous value.

Mono<Void> result = repository.deleteById(id)
        .then(auditService.recordDeletion(id));

Mono<ResponseEntity<Void>> deleted = repository.deleteById(id)
        .thenReturn(ResponseEntity.noContent().build());

Cold Publishers

A cold publisher starts producing data for each subscriber. Each subscriber gets its own execution of the pipeline.

  • It starts emitting when a subscriber subscribes.
  • Each subscriber gets the full sequence.
  • Each subscriber usually triggers a separate execution of the source.
Flux<Integer> cold = Flux.range(1, 3);
Flux<Integer> coldNumbers = Flux.range(1, 3)
        .doOnNext(number -> System.out.println("Producing " + number));

coldNumbers.subscribe(number -> System.out.println("A: " + number));
coldNumbers.subscribe(number -> System.out.println("B: " + number));

Each subscriber receives 1, 2, 3. Real-life analogy: a recorded training video starts from the beginning for every person who presses play.

Hot Publishers

A hot publisher is a reactive stream that produces data independently of subscribers. It emits data whether or not anyone is listening, and new subscribers may miss previously emitted values.

  • It emits continuously or independently of individual subscribers.
  • Subscribers share the same stream.
  • Subscribers may miss data if they arrive late.

Think of it like live radio. If you tune in late, you do not hear what was already broadcast.

Common Examples of Hot Publishers

  • Kafka topic: messages are produced whether consumers are connected or not.
  • WebSocket messages: clients only receive messages after connecting.
  • Mouse or UI events: events happen regardless of listeners.
  • Shared interval streams: Flux.interval() can become hot when shared.
Flux<Long> hotTicks = Flux.interval(Duration.ofSeconds(1))
        .share();

hotTicks.subscribe(tick -> System.out.println("First: " + tick));

// A later subscriber sees only future ticks.
hotTicks.subscribe(tick -> System.out.println("Second: " + tick));

Real-life analogy: a live show on the ship keeps going whether or not someone is in the theater. If a guest walks in halfway through, they do not see the beginning.

Simple Hot Publisher Example

Flux<Long> hot = Flux.interval(Duration.ofSeconds(1))
        .share();

hot.subscribe(v -> System.out.println("Subscriber 1: " + v));

Thread.sleep(3000);

hot.subscribe(v -> System.out.println("Subscriber 2: " + v));
Subscriber 1: 0
Subscriber 1: 1
Subscriber 1: 2
Subscriber 2: 3   // missed 0, 1, 2

A hot publisher emits data independently of subscribers. It produces values continuously, and subscribers only receive items emitted after they subscribe. Examples include Kafka topics, WebSocket streams, UI events, and shared Flux.interval() streams.

Thinking in Reactive Pipelines

Imperative code often says: get a value, store it in a variable, check it, call something else, mutate another variable, return. Reactive code says: when the value arrives, apply this chain of operations.

Imperative Shape

Reservation reservation = repository.findById(id);

if (reservation == null) {
    throw new ReservationNotFoundException(id);
}

Payment payment = paymentClient.load(reservation.paymentId());

return mapper.toResponse(reservation, payment);

Reactive Shape

return repository.findById(id)
        .switchIfEmpty(Mono.error(
                new ReservationNotFoundException(id)))
        .flatMap(reservation ->
                paymentClient.load(reservation.paymentId())
                        .map(payment ->
                                mapper.toResponse(reservation, payment)));

The reactive version keeps the work inside the pipeline. It does not call block(), does not manually subscribe, and does not rely on mutable temporary state.

End-to-End Payment Example

This flow loads a reservation, validates that it can be paid, authorizes payment, saves the receipt, and returns a response.

public Mono<PaymentResponse> payReservation(String reservationId, PaymentRequest request) {
    return reservationRepository.findById(reservationId)
            .switchIfEmpty(Mono.error(
                    new ReservationNotFoundException(reservationId)))
            .filter(reservation -> reservation.status().equals("PENDING_PAYMENT"))
            .switchIfEmpty(Mono.error(
                    new InvalidReservationStateException(reservationId)))
            .flatMap(reservation ->
                    paymentClient.authorize(request)
                            .flatMap(receipt -> paymentRepository.save(receipt))
                            .map(savedReceipt -> new PaymentResponse(
                                    reservation.id(),
                                    savedReceipt.id(),
                                    savedReceipt.status())));
}

End-to-End Disney Cruise Example

This flow finds all confirmed reservations for a sailing, loads their payment status, keeps paid reservations, and creates boarding pass previews.

public Flux<BoardingPassPreview> previewBoardingPasses(String sailingId) {
    return reservationRepository.findBySailingId(sailingId)
            .filter(reservation -> reservation.status().equals("CONFIRMED"))
            .flatMap(reservation ->
                    paymentClient.getStatus(reservation.paymentId())
                            .filter(status -> status.equals(PaymentStatus.PAID))
                            .map(status -> new BoardingPassPreview(
                                    reservation.id(),
                                    reservation.guestName(),
                                    reservation.boardingGroup())));
}

Practical Rules

  • Use Mono for zero or one value.
  • Use Flux for zero to many values.
  • Use map for synchronous transformations.
  • Use flatMap for asynchronous composition.
  • Use switchIfEmpty for missing values.
  • Use onErrorResume for recovery and onErrorMap for translation.
  • Do not call block() inside WebFlux request handling.
  • Do not call subscribe() inside controllers or services just to make work happen.
  • Keep data immutable and avoid shared mutable state inside pipelines.

Reference Definition

Reactive programming is a way to build asynchronous, non-blocking data flows. In Project Reactor, Mono represents zero or one value, while Flux represents zero to many values. Reactor pipelines are lazy, so the work starts on subscription. Operators like map, filter, and flatMap compose small functions into a larger pipeline, allowing services to handle asynchronous work without blocking threads.

Reactor Deep Dive

Once the basic Mono, Flux, and operator model is clear, the next step is understanding execution: which thread runs the work, where blocking work belongs, how errors flow, how context travels, and how backpressure protects systems.

How Reactor Uses Threads

Reactor does not create threads unless the pipeline reaches an asynchronous boundary or code explicitly uses a Scheduler. By default, Reactor runs on the caller thread. There is no magic thread pool unless one is specified.

Mono.just("A")
        .map(value -> {
            System.out.println(Thread.currentThread().getName());
            return value;
        })
        .subscribe();
main

If this code is subscribed from the main thread, the simple synchronous work runs on the main thread. In WebFlux, request handling usually starts on an event-loop thread. That event-loop thread must not be blocked.

Real-life analogy: a cruise check-in employee can handle many guests efficiently if nobody makes them stand still waiting for a slow printer. If one guest blocks the employee for a long time, the whole line suffers. Event-loop threads are like those employees: keep them free and fast.

Why Threading Is Hard in Reactive Systems

Reactive systems are asynchronous, non-blocking, and concurrent. Problems happen when blocking code runs on non-blocking threads, when thread pools are exhausted, or when multiple threads share mutable state. Schedulers help by isolating different kinds of work onto thread pools designed for that purpose.

  • Blocking code on event-loop threads can create latency spikes.
  • Too many blocking calls can exhaust available threads.
  • Shared mutable state can create race conditions when work moves across threads.
  • Wrong scheduler choices can make a reactive service slower or less stable than imperative code.

Mono.fromCallable

Mono.fromCallable(...) means: create a Mono that will run this Callable later, then emit its result or emit an error signal if it throws.

A Callable<T> is similar to a Supplier<T>, but it is allowed to throw checked exceptions. That makes fromCallable useful when adapting imperative code into a reactive pipeline.

Reactive programming is non-blocking, but real systems still contain blocking code: JDBC, blocking REST clients, file I/O, legacy libraries, and calls such as Thread.sleep(...). These must be integrated without breaking the reactive system. That is where fromCallable is useful.

  • Blocking database calls such as JDBC.
  • Reading files.
  • Calling legacy libraries.
  • Any operation that returns a value and may throw.

Common Beginner Mistake

This looks innocent, but it is wrong when blockingCall() blocks:

Mono<String> mono =
        Mono.just(blockingCall());

blockingCall() is executed immediately, before any scheduler, before any subscription, and before any backpressure can apply. That can block the caller thread, the Netty event loop, or the whole application under load.

Key rule: never put blocking code inside Mono.just(). Use Mono.just(value) only when the value already exists.

Code Meaning
Mono.just(value) I already have the value.
Mono.fromCallable(fn) Call this later to get the value. 
Mono<String> mono = Mono.fromCallable(() -> {
    // This can block and can throw.
    return blockingCallThatReturnsString();
});

With fromCallable, you are not calling the method yet. You are describing how to call it later. Reactor will call it only on subscription and capture exceptions as error signals.

fromCallable is lazy. Nothing runs until someone subscribes.

Mono<String> mono = Mono.fromCallable(() -> {
    System.out.println("Calling...");
    Thread.sleep(1000);
    return "data";
});

// At this moment nothing is printed, blocked, or executed.

mono.subscribe();

fromCallable describes blocking work. subscribeOn decides where it runs. The safe pattern for unavoidable blocking code is:

Mono.fromCallable(() -> blockingCall())
        .subscribeOn(Schedulers.boundedElastic());

This runs the blocking call on a scheduler designed for blocking work, without tying up reactive event-loop threads.

Mono.fromCallable(() -> {
    throw new RuntimeException("boom");
})
.onErrorReturn("fallback");

If the callable throws, Reactor turns the exception into an error signal. That error can then be handled with operators such as onErrorReturn, onErrorResume, or onErrorMap.

Mono.fromCallable(this::blockingDbCall)
        .subscribeOn(Schedulers.boundedElastic())
        .publishOn(Schedulers.parallel())
        .map(this::cpuTransform)
        .subscribe();

Meaning: the blocking database call runs on boundedElastic, CPU work runs on parallel, and the pipeline keeps blocking work separated from reactive threads.

fromCallable defers blocking work until subscription and converts exceptions into reactive error signals. It should be paired with subscribeOn(Schedulers.boundedElastic()) to safely integrate blocking code into Reactor.

subscribeOn vs publishOn

subscribeOn controls where subscription and source-side work starts. publishOn changes the execution context for downstream operators after that point in the pipeline.

Classic rule: subscribeOn decides where the source runs; publishOn decides where downstream operators run.

subscribeOn

Use subscribeOn near a blocking or expensive source to move that source work onto the right scheduler.

Mono<PaymentStatus> status = Mono.fromCallable(() ->
        legacyPaymentClient.getStatus(paymentId))
        .subscribeOn(Schedulers.boundedElastic());

publishOn

Use publishOn when downstream processing should continue on another scheduler.

Flux<PaymentEvent> processed = paymentEvents
        .publishOn(Schedulers.parallel())
        .map(this::calculateRiskScore);
Mono.fromCallable(this::blockingCall)
        .subscribeOn(Schedulers.boundedElastic())
        .publishOn(Schedulers.parallel())
        .map(this::cpuTask)
        .subscribe();

In this example, the blocking source runs on boundedElastic. After publishOn, the CPU-oriented mapping runs on parallel.

Mono.fromCallable(() -> {
    System.out.println("source thread = " + Thread.currentThread().getName());
    return "data";
})
.subscribeOn(Schedulers.boundedElastic())
.publishOn(Schedulers.parallel())
.map(value -> {
    System.out.println("map thread = " + Thread.currentThread().getName());
    return value.toUpperCase();
})
.subscribe();

The source thread prints something like boundedElastic-.... The map thread prints something like parallel-.... That is the clean separation: source work on one scheduler, downstream CPU work on another.

Where publishOn appears matters. Only operators after publishOn move to the new scheduler.

Mono.just("x")
        .map(value -> {
            // Runs on the current thread.
            return value;
        })
        .publishOn(Schedulers.parallel())
        .map(value -> {
            // Runs on a parallel thread.
            return value;
        });

What Happens Without publishOn

If a pipeline uses subscribeOn(Schedulers.boundedElastic()) but never uses publishOn, the downstream operators continue on boundedElastic.

Mono.fromCallable(this::blockingDbCall)
        .subscribeOn(Schedulers.boundedElastic())
        .map(this::cpuTransform)
        .subscribe();

This means the blocking database call runs on boundedElastic, and cpuTransform also runs on boundedElastic. There is one scheduler and no handoff.

This is not wrong. It is safe because boundedElastic is allowed to block, and small CPU work can run there too. It may be suboptimal if the CPU work is heavy.

Mono.fromCallable(this::blockingDbCall)
        .subscribeOn(Schedulers.boundedElastic()) // I/O
        .publishOn(Schedulers.parallel())         // switch
        .map(this::cpuTransform)                  // CPU
        .subscribe();

Add publishOn(Schedulers.parallel()) when you want thread responsibility separation: boundedElastic for blocking I/O and parallel for CPU-heavy computation.

Aspect Without publishOn With publishOn
Correctness Safe Safe
Blocking safety Safe Safe
CPU efficiency Potentially suboptimal Better for heavy CPU work
Thread separation No Yes
Clarity of intent Less explicit Clearer

Common trap: you do not always need publishOn after subscribeOn(boundedElastic). It is only needed when you want to switch execution to a different scheduler. Without it, downstream operators continue on the same scheduler.

  • Use publishOn when CPU-heavy transformations follow blocking I/O.
  • Use publishOn when clear separation of responsibilities improves readability and performance under load.
  • Skip publishOn when the pipeline is short, CPU work is minimal, thread separation is unnecessary, and simplicity is preferred.

subscribeOn chooses where execution starts. publishOn is optional and only needed to change threads downstream. Missing publishOn means there is no thread switch; nothing breaks because of that alone.

Choosing the Right Scheduler

Schedulers define where work runs. Think of them as thread pools with specific purposes.

Scheduler Best For Example
Schedulers.boundedElastic() Blocking I/O or legacy blocking APIs; grows as needed within limits Mono.fromCallable(this::blockingCall).subscribeOn(Schedulers.boundedElastic())
Schedulers.parallel() CPU-bound work; fixed-size pool, usually based on CPU cores .publishOn(Schedulers.parallel()).map(this::cpuHeavyTask)
Schedulers.single() Ordered execution on one shared worker .publishOn(Schedulers.single())
Schedulers.immediate() Current thread; mostly useful for simple cases and tests No scheduling boundary 
public Mono<Reservation> loadFromBlockingLegacySystem(String id) {
    return Mono.fromCallable(() -> legacyReservationClient.findById(id))
            .subscribeOn(Schedulers.boundedElastic());
}

Use boundedElastic for unavoidable blocking work. If the whole stack is already non-blocking, such as WebClient plus R2DBC, do not add schedulers just because the code is reactive. Never run blocking work on parallel; it is meant for CPU work, not waiting on I/O.

Why Blocking Is Dangerous

Reactive threads are few, shared, and optimized for asynchronous work. Blocking them with database calls, blocking REST clients, Thread.sleep(), or file I/O can cause thread starvation, latency spikes, and eventually system instability. Blocking code must be isolated on Schedulers.boundedElastic() when it cannot be avoided.

// Correct for unavoidable blocking I/O:
Mono.fromCallable(this::blockingDbCall)
        .subscribeOn(Schedulers.boundedElastic());

// Wrong idea: parallel is for CPU work, not blocking I/O.
Mono.fromCallable(this::blockingDbCall)
        .subscribeOn(Schedulers.parallel());

Error Handling in Reactive Pipelines

In Reactor, errors are signals in the pipeline. An error is terminal unless the pipeline handles it and switches to another value or publisher.

Unlike normal imperative code, errors are not thrown down the stack in the usual try/catch style. A reactive stream communicates with three signal types:

  • onNext(value): emits a value.
  • onComplete(): completes successfully.
  • onError(error): fails and terminates the stream.

Once a stream emits onError, it is done unless an operator recovers by returning a fallback value or fallback publisher.

Operator Purpose
onErrorReturn Fallback value
onErrorResume Fallback publisher
doOnError Side effects such as logging or metrics
retry Retry immediately
retryWhen Retry with a strategy, such as delay or backoff 
Mono.fromCallable(this::callApi)
        .retry(3)
        .onErrorResume(error -> Mono.just("fallback"));

onErrorReturn

Return a fixed fallback value. Use this when the fallback is constant and the exception details do not matter.

Mono<String> status = paymentClient.status(id)
        .onErrorReturn("UNKNOWN");
Mono<String> result = Mono.fromCallable(this::callApi)
        .onErrorReturn("fallback");

onErrorResume

Recover with another reactive operation. This is the most common recovery operator because the fallback can depend on the error or call another async source.

Mono<PaymentStatus> status = paymentClient.status(id)
        .onErrorResume(TimeoutException.class, error ->
                paymentCache.lastKnownStatus(id));
Mono<String> result = Mono.fromCallable(this::callApi)
        .onErrorResume(error -> Mono.just("fallback"));

Mono<String> pathSpecific = Mono.fromCallable(this::callApi)
        .onErrorResume(TimeoutException.class, error ->
                Mono.just("timeout-fallback"))
        .onErrorResume(error ->
                Mono.just("generic-fallback"));

onErrorMap

Translate a low-level error into a domain exception. Use this when the service should expose consistent error types or hide low-level implementation details.

Mono<Receipt> receipt = paymentClient.authorize(request)
        .onErrorMap(WebClientException.class, error ->
                new PaymentProviderException("Authorization failed", error));
Mono<String> result = Mono.fromCallable(this::callApi)
        .onErrorMap(error ->
                new MyServiceException("API failed", error));

doOnError

Observe an error without recovering from it. Use it for side effects only, such as logging and metrics.

Mono<Receipt> receipt = paymentClient.authorize(request)
        .doOnError(error ->
                log.warn("Payment authorization failed", error));
mono.doOnError(error ->
        log.error("failed", error));

onErrorResume vs onErrorReturn

Operator Behavior Use When
onErrorReturn("fallback") Always returns the same fallback value. The fallback is simple, static, and does not need exception details.
onErrorResume(error -> ...) Chooses a dynamic fallback based on the exception. The fallback depends on exception type, or recovery needs another async operation. 
Mono.fromCallable(this::risky)
        .retry(2)
        .onErrorResume(error -> {
            if (error instanceof TimeoutException) {
                return Mono.just("timeout-fallback");
            }
            return Mono.error(new RuntimeException("wrapped", error));
        });

This is a common real-world pattern: retry transient failures first, use a fallback for known recoverable cases, and wrap or propagate unexpected failures.

Retry

retry(n) retries a fixed number of times immediately. The total attempts are the original attempt plus the retries.

Mono.fromCallable(this::callApi)
        .retry(2); // total attempts = 1 original + 2 retries = 3

If the operation keeps failing after retries, the stream emits onError.

retryWhen(...) retries with a strategy, such as delay, exponential backoff, or filtering which exceptions are retryable.

Mono.fromCallable(this::callApi)
        .retryWhen(Retry.backoff(2, Duration.ofMillis(200)));

Mono.fromCallable(this::callApi)
        .retryWhen(
                Retry.backoff(2, Duration.ofMillis(200))
                        .filter(error -> error instanceof TimeoutException)
        );

Production-Style Error Pattern

A common structure is: do the risky call, log if an error happens, retry if appropriate, and fall back if it still fails.

Mono.fromCallable(this::callApi)
        .doOnError(error -> log.warn("API call failed", error))
        .retryWhen(Retry.backoff(2, Duration.ofMillis(200)))
        .onErrorResume(error -> Mono.just("fallback"));

Error Operator Ordering

Ordering matters. retry must come before onErrorReturn or onErrorResume, because once the error is recovered, there is no error left to retry.

// Correct: retry first, then recover.
Mono.fromCallable(this::callApi)
        .retry(2)
        .onErrorReturn("fallback");

// Wrong: retry will not happen because the error is already handled.
Mono.fromCallable(this::callApi)
        .onErrorReturn("fallback")
        .retry(2);

Error Handling Mental Model

  • doOnError: log the crash.
  • onErrorReturn: if it crashes, use this default value.
  • onErrorResume: if it crashes, take another route.
  • retry: try again.
  • onErrorMap: rename or wrap the crash.

Be careful with blanket error mapping. If code creates a ReservationNotFoundException with switchIfEmpty, a later broad onErrorMap can accidentally convert that 404-style error into a 500-style error.

return repository.findById(id)
        .switchIfEmpty(Mono.error(new ReservationNotFoundException(id)))
        .onErrorMap(DatabaseException.class, error ->
                new ReservationDataAccessException(error));

This maps only database errors and preserves the not-found error.

Reactor Context

Reactor Context is an immutable per-subscriber key/value store that travels with the reactive chain. It is useful for metadata such as correlation IDs, trace IDs, tenant IDs, auth tokens, or request-scoped values that should not be passed manually through every method argument.

Mono<String> result = Mono.deferContextual(context ->
        Mono.just("traceId=" + context.get("traceId")))
        .contextWrite(Context.of("traceId", "abc-123"));
Mono.just("data")
        .contextWrite(context -> context.put("traceId", "123"))
        .flatMap(value ->
                Mono.deferContextual(context ->
                        Mono.just(context.get("traceId"))));

Real-life analogy: a guest wristband travels with the guest through the ship. Each station can read the wristband to know the guest's package, room, or permissions without asking them to carry separate paperwork for every activity.

public Mono<PaymentReceipt> authorize(PaymentRequest request) {
    return Mono.deferContextual(context -> {
        String correlationId = context.getOrDefault("correlationId", "missing");
        return paymentClient.authorize(request)
                .doOnNext(receipt ->
                        log.info("correlationId={} payment={}", correlationId, receipt.id()));
    });
}

Reactor Context is not ThreadLocal. It follows the reactive subscription, not a specific Java thread. Do not use Reactor Context as a replacement for domain parameters. If a value is part of the business operation, pass it normally. Use Context for cross-cutting metadata.

Backpressure

Backpressure means the consumer can control how fast the producer emits data. It is not buffering forever and it is not crashing when the consumer is slow. It is controlled flow.

Real-life analogy: imagine a factory and a delivery truck. The factory is the producer, and the truck is the consumer. Without backpressure, the factory keeps producing boxes as fast as possible even if trucks are slow and storage is limited. The warehouse fills up, boxes fall, and the system crashes. With backpressure, the truck says, "I can take 10 boxes at a time." The factory produces 10 and waits for the next request.

The Reactive Streams contract is simple: the subscriber requests n items, the publisher emits at most n items, and the subscriber requests more when it is ready. This is built in; most application code does not manually implement demand management.

Flux.range(1, 1_000)
        .doOnRequest(n -> System.out.println("Requested " + n))
        .subscribe(new BaseSubscriber<>() {
            @Override
            protected void hookOnSubscribe(Subscription subscription) {
                request(10);
            }

            @Override
            protected void hookOnNext(Integer value) {
                System.out.println(value);
                request(1);
            }
        });

What Happens by Default

For many Reactor sources and operators, backpressure is handled automatically. Reactor requests data in controlled batches instead of pulling everything into memory at once.

Flux.range(1, 1_000_000)
        .subscribe(value -> slowConsumer(value));

Behind the scenes, Reactor does not need to load all one million values into memory at the same time. Demand moves through the pipeline so memory stays safer.

When Backpressure Becomes Visible

You usually notice backpressure when the producer is much faster than the consumer, the consumer is slow, or the source is push-based, such as Kafka, WebSockets, sockets, UI events, or intervals.

Flux.interval(Duration.ofMillis(10)) // fast producer
        .doOnNext(value -> Thread.sleep(100)) // slow consumer
        .subscribe();

The producer emits every 10 ms, but the consumer takes 100 ms per item. Without demand control or an overflow strategy, memory can grow, latency can spike, and the process can fail with OutOfMemoryError.

When Backpressure Is Not Enough

Some sources cannot always be slowed down by the subscriber. Message brokers, sockets, UI events, and externally pushed streams may keep producing. In those cases, Reactor needs an explicit strategy: buffer, drop, keep latest, or fail.

Important clarification: backpressure is not buffering by default. Backpressure is demand signaling. Buffering is one possible reaction when demand is exceeded.

In real services, backpressure matters when processing event streams, WebSocket traffic, file streams, Kafka/Kinesis-like data, or any producer that can be faster than the consumer.

Flux.range(1, 100)
        .onBackpressureBuffer()
        .subscribe();

Without backpressure or a clear overflow strategy, fast producers can create memory pressure, OutOfMemoryError, high latency, and system instability.

Backpressure Strategies

  • onBackpressureBuffer: store extra items until the consumer catches up. Risk: memory growth if the consumer stays too slow.
  • onBackpressureDrop: drop items that cannot be handled. Useful for metrics, UI events, and lossy streams.
  • onBackpressureLatest: keep only the most recent item. Useful for dashboards and real-time status updates.
  • onBackpressureError: fail fast when demand is exceeded. Useful when losing data is unacceptable and buffering would be dangerous.
  • limitRate: request data upstream in smaller batches.
Flux<PaymentEvent> events = paymentEvents
        .onBackpressureBuffer(1_000)
        .limitRate(100)
        .flatMap(this::processPaymentEvent, 20);

The flatMap concurrency limit protects downstream systems by allowing only a fixed number of payment events to process at the same time.

Reactor is safer than plain async code because demand is explicit, flow is controlled, and overload behavior can be designed. In many non-reactive async systems, producers push blindly and queues grow without bounds.

Backpressure is a mechanism that allows a reactive consumer to signal demand to a producer, ensuring that data is emitted only as fast as it can be processed. This prevents overwhelming consumers and avoids memory and stability issues in asynchronous systems.

Big Picture

Reactive programming is about composing asynchronous tasks, controlling threads explicitly, avoiding blocking, handling backpressure, and handling failures declaratively. The goal is not to make code look fancy. The goal is to keep services responsive when they are waiting on databases, payment providers, event streams, and other remote systems.

Reference Answer

Reactor does not create a new thread for every operation. Work runs on the subscribing thread until an asynchronous boundary or scheduler changes it. I use boundedElastic for unavoidable blocking I/O, parallel for CPU-bound work, and avoid blocking event-loop threads in WebFlux. Errors are terminal signals unless handled with operators such as onErrorResume or onErrorMap. Reactor Context carries cross-cutting metadata like trace IDs through the pipeline. Backpressure lets subscribers control demand so fast producers do not overwhelm slower consumers, which is critical for reliable reactive and event-driven systems.

Reactive Kafka

Core question: how do you use Kafka from a reactive Spring application while preserving ordering, backpressure, retries, observability, and correct offset handling?

Mental Model

Kafka is a distributed event log. Producers append records to topics. Topics are split into partitions. Consumers read records from partitions and track progress with offsets. Reactive Kafka connects this model to Reactor, so producing and consuming records can be represented with Mono and Flux.

Producer
  -> Topic
  -> Partition 0: offset 0, 1, 2, 3
  -> Partition 1: offset 0, 1, 2, 3
  -> Consumer group
  -> Reactive processing pipeline

The important shift is that records flow through a reactive stream. The consumer can process records asynchronously, limit concurrency, acknowledge offsets after successful work, and apply backpressure instead of blindly pulling unlimited messages into memory.

Kafka Concepts You Must Know

Concept Meaning Why It Matters
Topic Named stream of records, such as reservation-created. Defines the business event channel.
Partition Ordered log within a topic. Kafka ordering is guaranteed inside a partition, not across the whole topic.
Key Value used to choose the partition. Use stable business keys when ordering matters, such as reservationId.
Offset Record position inside a partition. Consumers commit offsets to record progress.
Consumer group Set of consumers sharing work for a topic. Each partition is handled by one consumer in the group at a time.
Rebalance Partition assignment changes between consumers. Consumers must handle shutdown, in-flight work, and offset commits carefully.

Why Reactive Kafka

Reactive Kafka is useful when Kafka processing is part of a non-blocking system. For example, a WebFlux service may consume reservation events, call reactive HTTP clients, write to reactive MongoDB, and publish new events without blocking worker threads.

  • It fits naturally with Flux because Kafka topics are streams of many records.
  • It lets processing compose with reactive repositories and WebClient.
  • It supports controlled concurrency and backpressure-aware processing.
  • It avoids manual thread management when the rest of the stack is reactive.
  • It keeps side effects, acknowledgments, retries, and publishing in one observable pipeline.

Reactor Kafka Building Blocks

The common library is Reactor Kafka. Its main types are KafkaReceiver for consuming and KafkaSender for producing. A receiver exposes records as a Flux. A sender sends records from a reactive publisher.

KafkaReceiver<String, ReservationCreatedEvent>
KafkaSender<String, ReservationConfirmedEvent>

ReceiverRecord<K, V> includes:
  key
  value
  topic
  partition
  offset
  receiverOffset for acknowledgment

Producer Configuration

A reactive producer still uses normal Kafka producer properties: bootstrap servers, serializers, acknowledgments, retries, idempotence, and delivery timeout. Reactor wraps the send operation in a reactive API.

@Configuration
public class ReactiveKafkaProducerConfig {

    @Bean
    KafkaSender<String, ReservationCreatedEvent> reservationCreatedSender(
            KafkaProperties kafkaProperties) {

        Map<String, Object> props = new HashMap<>();
        props.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG,
                kafkaProperties.getBootstrapServers());
        props.put(ProducerConfig.KEY_SERIALIZER_CLASS_CONFIG,
                StringSerializer.class);
        props.put(ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG,
                JsonSerializer.class);
        props.put(ProducerConfig.ACKS_CONFIG, "all");
        props.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, true);

        SenderOptions<String, ReservationCreatedEvent> options =
                SenderOptions.create(props);

        return KafkaSender.create(options);
    }
}

acks=all and idempotent producer settings help improve durability and prevent duplicate sends caused by producer retries. They do not replace consumer idempotency.

Reactive Producer Example

Publishing should return a Mono so the caller can compose it into the larger workflow. Do not hide publishing behind an internal subscribe().

@Component
public class ReservationEventPublisher {
    private final KafkaSender<String, ReservationCreatedEvent> sender;

    public ReservationEventPublisher(
            KafkaSender<String, ReservationCreatedEvent> sender) {
        this.sender = sender;
    }

    public Mono<Void> publishReservationCreated(
            ReservationCreatedEvent event) {

        SenderRecord<String, ReservationCreatedEvent, String> record =
                SenderRecord.create(
                        "reservation-created",
                        null,
                        null,
                        event.reservationId(),
                        event,
                        event.eventId()
                );

        return sender.send(Mono.just(record))
                .single()
                .doOnNext(result ->
                        log.info(
                                "Published reservation event id={} topic={} partition={} offset={}",
                                result.correlationMetadata(),
                                result.recordMetadata().topic(),
                                result.recordMetadata().partition(),
                                result.recordMetadata().offset()
                        )
                )
                .then();
    }
}

The Kafka key is reservationId, so events for the same reservation go to the same partition and keep their relative order.

Consumer Configuration

For consumers, one of the most important choices is offset commit strategy. In production business workflows, prefer acknowledging after processing succeeds. That avoids marking records complete before the side effect actually happened.

@Configuration
public class ReactiveKafkaConsumerConfig {

    @Bean
    KafkaReceiver<String, ReservationCreatedEvent> reservationCreatedReceiver(
            KafkaProperties kafkaProperties) {

        Map<String, Object> props = new HashMap<>();
        props.put(ConsumerConfig.BOOTSTRAP_SERVERS_CONFIG,
                kafkaProperties.getBootstrapServers());
        props.put(ConsumerConfig.GROUP_ID_CONFIG,
                "reservation-notification-service");
        props.put(ConsumerConfig.KEY_DESERIALIZER_CLASS_CONFIG,
                StringDeserializer.class);
        props.put(ConsumerConfig.VALUE_DESERIALIZER_CLASS_CONFIG,
                JsonDeserializer.class);
        props.put(ConsumerConfig.ENABLE_AUTO_COMMIT_CONFIG, false);
        props.put(ConsumerConfig.AUTO_OFFSET_RESET_CONFIG, "earliest");

        ReceiverOptions<String, ReservationCreatedEvent> options =
                ReceiverOptions.<String, ReservationCreatedEvent>create(props)
                        .subscription(List.of("reservation-created"));

        return KafkaReceiver.create(options);
    }
}

Disabling auto-commit keeps control in the reactive pipeline. The consumer acknowledges only when processing has completed successfully.

Reactive Consumer Example

A reactive consumer typically starts a long-running subscription when the application starts. The stream receives Kafka records, processes each record, and acknowledges the offset after success.

@Component
public class ReservationCreatedConsumer {
    private final KafkaReceiver<String, ReservationCreatedEvent> receiver;
    private final NotificationService notificationService;

    public ReservationCreatedConsumer(
            KafkaReceiver<String, ReservationCreatedEvent> receiver,
            NotificationService notificationService) {
        this.receiver = receiver;
        this.notificationService = notificationService;
    }

    @PostConstruct
    void start() {
        receiver.receive()
                .flatMap(this::handleRecord, 16)
                .doOnError(error ->
                        log.error("Reservation consumer stopped", error)
                )
                .retryWhen(Retry.backoff(Long.MAX_VALUE, Duration.ofSeconds(1)))
                .subscribe();
    }

    private Mono<Void> handleRecord(
            ReceiverRecord<String, ReservationCreatedEvent> record) {

        ReservationCreatedEvent event = record.value();

        return notificationService.sendReservationCreatedEmail(event)
                .then(Mono.fromRunnable(() ->
                        record.receiverOffset().acknowledge()
                ));
    }
}

This is one place where subscribe() is normal: the application is intentionally starting a background Kafka listener. The mistake is calling subscribe() inside request/response business methods to hide side effects.

Offset Acknowledgment Rule

Rule: acknowledge the Kafka offset only after all required side effects for that record have completed successfully. If the app crashes before acknowledgment, Kafka can redeliver the record and the consumer must be idempotent.

At-Least-Once Delivery

Most Kafka business consumers should be designed for at-least-once delivery. A record can be processed more than once if processing succeeds but the app crashes before committing the offset, or if a rebalance happens during in-flight work.

Record received
  -> send email succeeds
  -> app crashes before offset commit
  -> record is delivered again
  -> email could be sent twice unless consumer is idempotent

Because of this, idempotency is not optional. It is part of the consumer design.

Idempotent Consumer Pattern

Use a stable event ID or business key to record that a message has already been processed. Conditional writes or unique constraints are the safest way to prevent duplicates under concurrency.

private Mono<Void> handleRecord(
        ReceiverRecord<String, ReservationCreatedEvent> record) {

    ReservationCreatedEvent event = record.value();

    return processedEventRepository.markProcessing(event.eventId())
            .flatMap(marked ->
                    notificationService.sendReservationCreatedEmail(event)
                            .then(processedEventRepository.markComplete(event.eventId()))
            )
            .onErrorResume(DuplicateEventException.class, duplicate ->
                    Mono.empty()
            )
            .then(Mono.fromRunnable(() ->
                    record.receiverOffset().acknowledge()
            ));
}

If the event was already processed, the consumer skips the side effect and acknowledges the offset. For payment, loyalty points, inventory, and notifications, this pattern prevents duplicate business actions.

Ordering and Partition Keys

Kafka preserves order only within a partition. If all events for one reservation must be processed in order, use reservationId as the key. If you use a random key, events for the same reservation can land on different partitions and be processed out of order.

Good key for reservation lifecycle:
  reservationId = "res-123"

Events stay ordered:
  ReservationCreated
  PaymentAuthorized
  ReservationConfirmed
  BoardingPassIssued

Do not use low-cardinality keys like eventType for high-volume topics. That can overload one partition because many records share the same key.

Concurrency Without Breaking Ordering

Plain flatMap across all records can process messages concurrently and complete them out of order. If ordering matters per partition, group or process partition streams carefully.

receiver.receive()
        .groupBy(record -> record.receiverOffset().topicPartition())
        .flatMap(partitionFlux ->
                partitionFlux.concatMap(this::handleRecord)
        );

This allows partitions to process in parallel, but records within each partition process sequentially. Use this when ordering is more important than maximum throughput.

Backpressure

Reactive Kafka can apply demand through the reactive chain, but Kafka consumers still fetch records in batches. You still need sensible limits: max poll records, flatMap concurrency, bounded queues, timeouts, and downstream protection.

receiver.receive()
        .flatMap(record ->
                process(record)
                        .timeout(Duration.ofSeconds(3)),
                32
        );

The concurrency number controls how many records are actively being processed. This is one of the most practical safety controls in a reactive Kafka consumer.

Retries

Retries should match the failure. A short network timeout from an email service may be retryable. A malformed event is not retryable. A failed payment side effect may require careful idempotency before retrying.

private Mono<Void> processWithRetry(
        ReceiverRecord<String, ReservationCreatedEvent> record) {

    return process(record)
            .retryWhen(Retry.backoff(3, Duration.ofMillis(250))
                    .filter(this::isTransientFailure))
            .then(Mono.fromRunnable(() ->
                    record.receiverOffset().acknowledge()
            ));
}

Do not retry forever inside one record handler unless that is an explicit operational decision. Infinite retries can block a partition and cause consumer lag to grow.

Dead Letter Topic Pattern

When a record cannot be processed after retries, publish it to a dead letter topic with error details, then acknowledge the original offset. This prevents one poison message from blocking the partition forever.

private Mono<Void> handleRecord(
        ReceiverRecord<String, ReservationCreatedEvent> record) {

    return process(record)
            .retryWhen(Retry.backoff(3, Duration.ofMillis(250))
                    .filter(this::isTransientFailure))
            .onErrorResume(error ->
                    deadLetterPublisher.publish(record, error)
            )
            .then(Mono.fromRunnable(() ->
                    record.receiverOffset().acknowledge()
            ));
}

The dead letter event should include the original topic, partition, offset, key, event ID, error type, safe error message, and timestamp. Do not include secrets or sensitive payload fields unless the topic is protected for that data.

Poison Message Strategy

Failure Example Strategy
Transient dependency failure Email service timeout Retry with backoff, then DLQ if still failing.
Bad payload Missing required reservation ID Do not retry. Publish to DLQ and alert.
Duplicate event Same eventId already processed Skip side effect and acknowledge.
Ordering conflict Payment event arrives before reservation created event Hold, retry later, or route to repair workflow depending on business rules.

Reactive Kafka with WebFlux

In a WebFlux API, Kafka publishing should be part of the request pipeline when the response depends on publishing. If publishing is best-effort, be explicit about that design and use an outbox instead of hiding the send.

@PostMapping
public Mono<ResponseEntity<CruiseReservationResponse>> create(
        @Valid @RequestBody CruiseReservationRequest request) {

    return reservationService.createReservation(request)
            .flatMap(response ->
                    eventPublisher.publishReservationCreated(
                            ReservationCreatedEvent.from(response)
                    )
                    .thenReturn(response)
            )
            .map(response ->
                    ResponseEntity.status(HttpStatus.CREATED).body(response)
            );
}

This means the API will fail if the event cannot be published. That may be correct for some workflows. For higher reliability, the service often saves an outbox row in the same transaction as the reservation and returns after the database commit.

Outbox Is Often Better Than Direct Publish

Direct publishing from a request can create a consistency problem: the database save can succeed and Kafka publish can fail, or Kafka publish can succeed and the database transaction can fail. The outbox pattern reduces that risk.

Request pipeline:
  1. Validate request
  2. Save reservation and outbox event in one transaction
  3. Return response

Background publisher:
  1. Read unpublished outbox events
  2. Publish to Kafka
  3. Mark outbox event as published

Reactive Kafka works well for the background publisher because unpublished events are a stream of work.

Reactive Outbox Publisher

@Component
public class OutboxKafkaPublisher {
    private final OutboxRepository outboxRepository;
    private final ReservationEventPublisher eventPublisher;

    public Flux<OutboxEvent> publishPendingEvents() {
        return outboxRepository.findPending()
                .flatMap(event ->
                        eventPublisher.publish(event)
                                .then(outboxRepository.markPublished(event.id()))
                                .thenReturn(event),
                        10
                );
    }
}

The concurrency limit protects Kafka and the database. If ordering is required by aggregate, use keys carefully and consider partition-aware processing.

Observability

Reactive Kafka systems need visibility into both Kafka and the reactive processing pipeline.

  • Consumer lag by group, topic, and partition.
  • Records processed per second.
  • Processing latency and end-to-end event age.
  • Retry count and DLQ count.
  • Partition assignment and rebalance events.
  • Dependency latency for calls made during processing.
  • Error rate by exception type and event type.
  • Correlation IDs, event IDs, topic, partition, offset, and consumer group in logs.
log.info(
        "Processed eventId={} topic={} partition={} offset={} reservationId={}",
        event.eventId(),
        record.topic(),
        record.partition(),
        record.offset(),
        event.reservationId()
);

Testing Reactive Kafka Logic

Keep business processing testable by putting the record handling logic in a method that returns Mono<Void>. Then use StepVerifier to test success, retryable failure, duplicate events, and DLQ behavior.

@Test
void handleRecordShouldSendEmailAndAcknowledgeOffset() {
    ReceiverRecord<String, ReservationCreatedEvent> record =
            testRecord("res-123", reservationCreatedEvent);

    when(notificationService.sendReservationCreatedEmail(reservationCreatedEvent))
            .thenReturn(Mono.empty());

    StepVerifier.create(consumer.handleRecord(record))
            .verifyComplete();

    verify(notificationService)
            .sendReservationCreatedEmail(reservationCreatedEvent);
    assertThat(record.receiverOffset().isAcknowledged()).isTrue();
}

For full integration tests, use an embedded Kafka broker or Testcontainers Kafka, but unit tests should still verify the pipeline decisions without needing a broker.

Common Mistakes

  • Acknowledging offsets before processing finishes.
  • Assuming Kafka gives global ordering across all partitions.
  • Using low-cardinality keys that create hot partitions.
  • Processing with unlimited flatMap and overwhelming downstream services.
  • Retrying poison messages forever and blocking a partition.
  • Publishing events with hidden internal subscribe() calls.
  • Forgetting idempotency because Kafka can redeliver records.
  • Logging payloads that contain sensitive guest, payment, or identity data.

Disney Cruise Example

A reservation service publishes ReservationCreated. A notification service consumes it, sends a confirmation email, and publishes ReservationNotificationSent. A loyalty service consumes the same original event and prepares points. Each consumer uses the same reservationId key for ordering and an eventId for idempotency.

reservation-created topic:
  key = reservationId
  value = {
    eventId,
    reservationId,
    guestId,
    shipCode,
    sailingDate,
    createdAt
  }

notification-service consumer:
  1. Check eventId was not processed
  2. Send email
  3. Mark eventId processed
  4. Acknowledge offset

loyalty-service consumer:
  1. Check eventId was not processed
  2. Prepare pending loyalty points
  3. Mark eventId processed
  4. Acknowledge offset

Interview Reference Answer

Reactive Kafka means using Kafka through Reactor types so consuming and producing records can be composed with non-blocking service logic. Kafka topics are split into partitions, ordering is guaranteed only within a partition, and consumers track progress with offsets. In a reactive consumer, I process records as a Flux, control concurrency with operators like flatMap(..., concurrency), preserve partition order with concatMap when needed, and acknowledge offsets only after processing succeeds. I design consumers for at-least-once delivery, so handlers must be idempotent using event IDs, conditional writes, or unique constraints. For failures, I retry only transient errors with backoff, send poison messages to a dead letter topic, and include topic, partition, offset, event ID, and correlation ID in logs and metrics. In WebFlux services, I avoid hidden subscribe() calls for publishing and often prefer an outbox pattern when database state and Kafka events must stay consistent.

Reactive MongoDB

Core question: how do you use MongoDB in a WebFlux service without blocking, while keeping queries efficient, writes correct, and pipelines testable?

Mental Model

Reactive MongoDB means using the non-blocking MongoDB driver through Spring Data reactive APIs. Repository methods return Mono for zero-or-one results and Flux for many results. The database call does not block the WebFlux event-loop thread while waiting for network I/O.

WebFlux controller
  -> service returns Mono or Flux
  -> ReactiveMongoRepository or ReactiveMongoTemplate
  -> MongoDB reactive driver
  -> MongoDB server
  -> response signal flows back through the pipeline

The architectural goal is an end-to-end reactive chain: HTTP request, service logic, MongoDB call, error handling, and response writing all compose without block().

Spring Data Reactive MongoDB Types

Type Purpose When To Use
ReactiveMongoRepository Repository abstraction with common CRUD methods. Most standard document access patterns.
ReactiveMongoTemplate Lower-level API for custom queries, updates, aggregations, and fine control. Complex query/update behavior that does not fit repository method names.
Mono<T> Zero or one document/result. Find by ID, save one document, update one document, delete result.
Flux<T> Many documents/results. Search, list, stream query results, process many reservations.

Document Model

MongoDB stores documents, not relational rows. In Spring Data, a document class usually maps to one MongoDB collection.

@Document(collection = "cruise_reservations")
public class CruiseReservationEntity {
    @Id
    private String id;

    @Indexed
    private String guestId;

    @Indexed
    private String shipCode;

    private OffsetDateTime sailingDate;
    private String cabinType;
    private int guestCount;
    private String reservationStatus;

    // constructors, getters, and domain methods
}

Use indexes for fields that appear in important queries. Without the right index, MongoDB may scan too many documents and the reactive pipeline will still be slow.

Reactive Repository

A reactive repository looks similar to a normal Spring Data repository, but every operation returns a reactive type.

public interface CruiseReservationRepository
        extends ReactiveMongoRepository<CruiseReservationEntity, String> {

    Flux<CruiseReservationEntity> findByGuestId(String guestId);

    Flux<CruiseReservationEntity> findByShipCodeAndSailingDateBetween(
            String shipCode,
            OffsetDateTime start,
            OffsetDateTime end
    );

    Mono<Boolean> existsByGuestIdAndShipCodeAndSailingDate(
            String guestId,
            String shipCode,
            OffsetDateTime sailingDate
    );
}

The method names declare queries. Spring Data creates the reactive query implementation at runtime.

Service Pattern

The service should compose repository calls with Reactor operators. It should not unwrap the value with block().

public Mono<CruiseReservationResponse> getReservation(String id) {
    return repository.findById(id)
            .switchIfEmpty(Mono.error(
                    new ReservationNotFoundException(id)
            ))
            .map(this::toResponse);
}

findById returns Mono.empty() when no document exists. Use switchIfEmpty to turn that empty result into a domain error when the API should return 404.

Create with Duplicate Protection

For writes, think about duplicate requests and concurrent calls. A pre-check alone is not enough under race conditions, but it is useful for a readable business flow when combined with a unique index or conditional write pattern.

public Mono<CruiseReservationResponse> createReservation(
        CruiseReservationRequest request) {

    return repository.existsByGuestIdAndShipCodeAndSailingDate(
                    request.guestId(),
                    request.shipCode(),
                    request.sailingDate()
            )
            .flatMap(exists -> {
                if (exists) {
                    return Mono.error(new DuplicateReservationException(
                            request.guestId(),
                            request.shipCode(),
                            request.sailingDate()
                    ));
                }

                return repository.save(toEntity(request));
            })
            .map(this::toResponse);
}

In production, enforce uniqueness with a MongoDB unique index when correctness matters. Application checks can race; database constraints are the final guard.

Unique Index for Idempotency

An idempotency key can prevent duplicate side effects when clients retry. Store the key with a unique index so only one request can claim it.

@Document(collection = "idempotency_records")
public class IdempotencyRecord {
    @Id
    private String id;

    @Indexed(unique = true)
    private String idempotencyKey;

    private String resourceId;
    private String status;
    private Instant createdAt;
}
public Mono<CruiseReservationResponse> createReservation(
        String idempotencyKey,
        CruiseReservationRequest request) {

    return idempotencyRepository.findByIdempotencyKey(idempotencyKey)
            .flatMap(record ->
                    repository.findById(record.getResourceId())
            )
            .switchIfEmpty(createNewReservation(idempotencyKey, request))
            .map(this::toResponse);
}

For full safety, the createNewReservation path must claim the idempotency key atomically. If two requests arrive at the same time, only one should create the reservation.

ReactiveMongoTemplate

Use ReactiveMongoTemplate when repository method names become awkward or when you need partial updates, custom criteria, projections, or aggregations.

public Flux<CruiseReservationEntity> searchReservations(
        String shipCode,
        OffsetDateTime start,
        OffsetDateTime end,
        String status) {

    Query query = new Query()
            .addCriteria(Criteria.where("shipCode").is(shipCode))
            .addCriteria(Criteria.where("sailingDate").gte(start).lt(end))
            .addCriteria(Criteria.where("reservationStatus").is(status))
            .with(Sort.by(Sort.Direction.ASC, "sailingDate"))
            .limit(100);

    return mongoTemplate.find(query, CruiseReservationEntity.class);
}

This gives explicit control over the MongoDB query while still returning a Flux.

Partial Update Pattern

For targeted updates, avoid loading and saving a full document when an atomic update is clearer.

public Mono<CruiseReservationEntity> markConfirmed(
        String reservationId,
        String paymentAuthorizationId) {

    Query query = Query.query(Criteria.where("_id").is(reservationId));

    Update update = new Update()
            .set("reservationStatus", "CONFIRMED")
            .set("paymentAuthorizationId", paymentAuthorizationId)
            .set("updatedAt", Instant.now());

    return mongoTemplate.findAndModify(
            query,
            update,
            FindAndModifyOptions.options().returnNew(true),
            CruiseReservationEntity.class
    )
    .switchIfEmpty(Mono.error(
            new ReservationNotFoundException(reservationId)
    ));
}

findAndModify can update and return the new document in one database operation.

Optimistic Locking

Use optimistic locking when multiple requests might update the same document. Spring Data MongoDB supports @Version.

@Document(collection = "cruise_reservations")
public class CruiseReservationEntity {
    @Id
    private String id;

    @Version
    private Long version;

    private String reservationStatus;
}

If two updates read the same version, the first save succeeds and increments the version. The second save fails because it is trying to save an old version. Map that failure to a conflict response.

return repository.save(reservation)
        .onErrorMap(OptimisticLockingFailureException.class, error ->
                new ReservationConflictException(reservation.getId(), error)
        );

Transactions

MongoDB supports transactions for replica sets and sharded clusters, but do not use them casually. Transactions add overhead and can reduce throughput. Prefer single-document atomic updates when the data model allows it.

public Mono<CruiseReservationResponse> createWithOutbox(
        CruiseReservationRequest request) {

    CruiseReservationEntity reservation = toEntity(request);
    OutboxEvent event = OutboxEvent.reservationCreated(reservation);

    return transactionalOperator.transactional(
            repository.save(reservation)
                    .then(outboxRepository.save(event))
                    .thenReturn(reservation)
    )
    .map(this::toResponse);
}

This pattern is useful when reservation state and the outbox event must be committed together.

Streaming Query Results

A MongoDB query that returns many documents should use Flux. Combine it with pagination, limits, or streaming responses so one request does not pull too much data.

@GetMapping(value = "/sailings/{sailingId}/reservations",
        produces = MediaType.APPLICATION_NDJSON_VALUE)
public Flux<CruiseReservationResponse> streamReservations(
        @PathVariable String sailingId) {

    return reservationService.streamReservationsForSailing(sailingId);
}
public Flux<CruiseReservationResponse> streamReservationsForSailing(
        String sailingId) {

    return repository.findBySailingId(sailingId)
            .limitRate(100)
            .map(this::toResponse);
}

limitRate helps control demand through the stream. It is not a replacement for good query filters and indexes.

Index Design

Reactive MongoDB does not make bad queries cheap. Index design is still critical.

  • Create indexes for fields used in frequent filters and sorts.
  • Use compound indexes for common query combinations, such as shipCode + sailingDate + reservationStatus.
  • Avoid unbounded collection scans in request paths.
  • Use limits and pagination for list endpoints.
  • Monitor slow queries and query execution plans.
@CompoundIndex(
        name = "ship_sailing_status_idx",
        def = "{'shipCode': 1, 'sailingDate': 1, 'reservationStatus': 1}"
)
@Document(collection = "cruise_reservations")
public class CruiseReservationEntity {
    // fields
}

Pagination Pattern

Offset pagination can become expensive for deep pages. Cursor-style pagination is often better for high-volume collections.

public Flux<CruiseReservationEntity> findNextPage(
        String shipCode,
        OffsetDateTime afterSailingDate,
        int limit) {

    Query query = Query.query(
            Criteria.where("shipCode").is(shipCode)
                    .and("sailingDate").gt(afterSailingDate)
    )
    .with(Sort.by(Sort.Direction.ASC, "sailingDate"))
    .limit(limit);

    return mongoTemplate.find(query, CruiseReservationEntity.class);
}

The next request passes the last seen sailingDate as the cursor.

Error Handling

Translate low-level MongoDB errors into domain exceptions. Do not leak raw database messages to API clients.

return repository.save(entity)
        .onErrorMap(DuplicateKeyException.class, error ->
                new DuplicateReservationException(
                        entity.getGuestId(),
                        entity.getShipCode(),
                        entity.getSailingDate(),
                        error
                )
        )
        .onErrorMap(DataAccessResourceFailureException.class, error ->
                new DatabaseUnavailableException(
                        "Reservation database unavailable",
                        error
                )
        );

The global WebFlux error handler can map duplicate reservation to 409 Conflict and database unavailable to 503 Service Unavailable.

Backpressure and Large Results

Backpressure helps the application avoid consuming faster than it can process, but MongoDB still has to execute the query. Design the query so the result set is bounded.

repository.findByShipCode("DREAM")
        .filter(reservation -> reservation.isActive())
        .flatMap(this::enrichReservation, 25)
        .limitRate(100);

Filtering in Java after loading too many documents is usually a design smell. Push filters into MongoDB queries whenever possible.

WebFlux Controller Example

@RestController
@RequestMapping("/api/reservations")
public class CruiseReservationController {
    private final CruiseReservationService service;

    @GetMapping("/{id}")
    public Mono<CruiseReservationResponse> getById(
            @PathVariable String id) {
        return service.getReservation(id);
    }

    @GetMapping
    public Flux<CruiseReservationResponse> findByGuest(
            @RequestParam String guestId) {
        return service.findByGuestId(guestId);
    }

    @PostMapping
    public Mono<ResponseEntity<CruiseReservationResponse>> create(
            @RequestHeader("Idempotency-Key") String idempotencyKey,
            @Valid @RequestBody CruiseReservationRequest request) {

        return service.createReservation(idempotencyKey, request)
                .map(response ->
                        ResponseEntity.status(HttpStatus.CREATED).body(response)
                );
    }
}

The controller stays reactive from HTTP input to MongoDB result.

Testing with StepVerifier

Service tests should assert emitted values, errors, and completion.

@Test
void getReservationShouldReturnNotFoundWhenMissing() {
    when(repository.findById("missing-id"))
            .thenReturn(Mono.empty());

    StepVerifier.create(service.getReservation("missing-id"))
            .expectErrorSatisfies(error -> {
                assertThat(error)
                        .isInstanceOf(ReservationNotFoundException.class);
                assertThat(error.getMessage())
                        .isEqualTo("Reservation not found: missing-id");
            })
            .verify();
}

For repository integration tests, use @DataMongoTest with reactive repositories and a real MongoDB test instance through Testcontainers when possible.

Common Mistakes

  • Using blocking MongoRepository inside a WebFlux service.
  • Calling block() to get a document inside service logic.
  • Assuming reactive MongoDB fixes missing indexes or bad query design.
  • Loading a huge collection and filtering in Java instead of querying with criteria.
  • Using application-only duplicate checks without a unique index.
  • Saving full documents when an atomic update would be clearer and safer.
  • Using multi-document transactions when a better document model would avoid them.
  • Returning raw database exception messages to API clients.

Interview Reference Answer

Reactive MongoDB in Spring means using the non-blocking MongoDB driver through Spring Data reactive APIs such as ReactiveMongoRepository and ReactiveMongoTemplate. Repository methods return Mono or Flux, so WebFlux services can compose database calls without blocking event-loop threads. I use switchIfEmpty for not-found cases, map for synchronous DTO mapping, and flatMap for additional reactive work. I still design MongoDB carefully: indexes for query patterns, bounded result sets, cursor-style pagination for large collections, unique indexes for idempotency, and optimistic locking or atomic updates for concurrent changes. Reactive does not make poor queries fast. For production reliability, I translate database exceptions into domain errors, avoid leaking raw database details, and test pipelines with StepVerifier plus integration tests against a real MongoDB test container.
