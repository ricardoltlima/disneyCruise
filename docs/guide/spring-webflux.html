Spring WebFlux

WebFlux fundamentals, error handling, reactive architecture patterns, and reservation code examples.

Spring WebFlux Fundamentals

Spring WebFlux is Spring's reactive web framework. It lets backend services handle HTTP requests using non-blocking I/O and reactive types such as Mono and Flux.

What Spring WebFlux Is

Spring WebFlux is an alternative to Spring MVC for building web APIs. Instead of tying one request to one blocking thread, WebFlux is designed around asynchronous, non-blocking request handling. Controller methods can return Mono<T> for one result or Flux<T> for many results.

@RestController
@RequestMapping("/api/reservations")
public class ReservationWebFluxController {
    private final ReservationService reservationService;

    public ReservationWebFluxController(ReservationService reservationService) {
        this.reservationService = reservationService;
    }

    @GetMapping("/{id}")
    public Mono<ReservationResponse> getReservation(@PathVariable String id) {
        return reservationService.findById(id);
    }
}

Real-life analogy: Spring MVC is like assigning one crew member to one guest until the entire request is finished. WebFlux is like a small coordination team that starts work, waits for async responses, and keeps helping other guests instead of standing still.

Spring MVC vs Spring WebFlux

Topic Spring MVC Spring WebFlux
Execution model Servlet-based, usually one request per thread while work is active Reactive, event-loop based, non-blocking request handling
Return types Objects, ResponseEntity, Callable, async wrappers Mono, Flux, reactive ResponseEntity
Common server Tomcat, Jetty, Undertow Netty by default in many Spring Boot WebFlux apps
Best fit Traditional CRUD APIs, blocking stacks, servlet ecosystem High-concurrency I/O, streaming, non-blocking clients and databases
Blocking tolerance Blocking is expected, within thread-pool limits Blocking event-loop threads is dangerous

Spring MVC is not obsolete. It is still an excellent choice for many backend APIs, especially when the application uses blocking libraries such as JDBC. WebFlux is most valuable when the stack is non-blocking end to end or when streaming/high concurrency is central to the service.

WebFlux Execution Model

WebFlux does not create one thread per request. Instead, it uses a small number of event-loop threads. Each request builds a reactive pipeline, and threads are released while waiting for I/O.

// Spring MVC mental model:
Request -> Thread -> Block -> Response

// Spring WebFlux mental model:
Request -> Event loop -> Reactive pipeline -> Callback -> Response

The key difference is what happens while the application waits for a database, payment provider, or another service. In a blocking model, the thread waits. In WebFlux, the event loop can keep handling other work while the asynchronous operation completes.

Netty and the Event Loop

Many WebFlux applications run on Reactor Netty by default. Netty uses a small number of event-loop threads, non-blocking sockets, and asynchronous callbacks to handle many connections. These threads are designed to stay free and react to events quickly: request received, bytes read, response ready, connection writable.

Client request
  -> Netty event loop receives request
  -> WebFlux invokes controller
  -> Controller returns Mono or Flux
  -> Non-blocking work continues
  -> Netty writes response when data is ready

Never block Netty event-loop threads. If one event-loop thread is blocked, every request depending on that thread can be delayed.

Event-loop threads are like a cruise operations desk with a few coordinators handling many radio calls. They should delegate slow work and keep moving. If one coordinator goes to physically search every cabin, the radio desk stops responding.

Why Blocking Is Dangerous in WebFlux

Blocking means a thread waits and does nothing useful. In WebFlux, blocking an event-loop thread can hurt many requests because those threads are few and shared.

@GetMapping("/bad")
public Mono<String> bad() {
    return Mono.just(blockingDbCall()); // blocks event loop
}

This blocks the Netty thread, prevents other requests from being handled efficiently, and kills scalability under load.

// Dangerous in WebFlux request handling:
public Mono<ReservationResponse> getReservation(String id) {
    Reservation reservation = blockingRepository.findById(id);
    return Mono.just(mapper.toResponse(reservation));
}

This blocks before the Mono is even returned. Under load, this can cause thread starvation, latency spikes, timeouts, and a service that appears frozen.

@GetMapping("/good")
public Mono<String> good() {
    return Mono.fromCallable(this::blockingDbCall)
            .subscribeOn(Schedulers.boundedElastic());
}

This keeps the event loop free, isolates blocking work, and allows the system to scale more safely.

// Safer if the blocking call cannot be replaced yet:
public Mono<ReservationResponse> getReservation(String id) {
    return Mono.fromCallable(() -> blockingRepository.findById(id))
            .subscribeOn(Schedulers.boundedElastic())
            .map(mapper::toResponse);
}

The better long-term option is to use non-blocking libraries when possible, such as WebClient for HTTP and reactive database drivers like R2DBC or reactive MongoDB.

When to Use WebFlux

WebFlux does not automatically mean faster raw execution. It is mainly about scalability and resource efficiency for I/O-heavy systems.

  • Use WebFlux when the service makes many non-blocking remote calls and needs high concurrency.
  • Use WebFlux for streaming responses, server-sent events, WebSocket-style flows, and event-heavy systems.
  • Use WebFlux when the database/client stack is reactive end to end.
  • Use WebFlux when backpressure-aware processing matters.
  • Use WebFlux for microservices that spend significant time waiting on other services.
  • Do not choose WebFlux only because it sounds newer. If most dependencies are blocking, Spring MVC may be simpler and more appropriate.

Do not use WebFlux when the application is mostly blocking, CPU-bound, or simple CRUD with low concurrency. In those cases, Spring MVC is often simpler and more appropriate.

Basic Reactive Controllers

A WebFlux controller should return the reactive pipeline. It should not call block() or manually call subscribe() to force execution.

GET One

@GetMapping("/{id}")
public Mono<ResponseEntity<ReservationResponse>> getById(@PathVariable String id) {
    return reservationService.findById(id)
            .map(ResponseEntity::ok)
            .switchIfEmpty(Mono.just(ResponseEntity.notFound().build()));
}

GET Many

@GetMapping
public Flux<ReservationResponse> getAll() {
    return reservationService.findAll();
}

POST

@PostMapping
public Mono<ResponseEntity<ReservationResponse>> create(
        @Valid @RequestBody CreateReservationRequest request) {
    return reservationService.create(request)
            .map(response -> ResponseEntity
                    .status(HttpStatus.CREATED)
                    .body(response));
}

DELETE

@DeleteMapping("/{id}")
public Mono<ResponseEntity<Void>> delete(@PathVariable String id) {
    return reservationService.delete(id)
            .thenReturn(ResponseEntity.noContent().build());
}

Annotation-Based Controllers

Annotation-based controllers are the most common WebFlux style. They look similar to Spring MVC controllers, but return Mono or Flux.

@RestController
class UserController {

    @GetMapping("/users/{id}")
    public Mono<User> getUser(@PathVariable String id) {
        return userService.findById(id);
    }

    @GetMapping("/users")
    public Flux<User> getUsers() {
        return userService.findAll();
    }
}

Functional Routing

Functional routing is an advanced WebFlux style where routes are defined as functions instead of controller annotations. It is less common in many enterprise codebases, but it is worth recognizing.

RouterFunction<ServerResponse> routes =
        route(GET("/users/{id}"),
                request -> ServerResponse.ok()
                        .body(
                                userService.findById(request.pathVariable("id")),
                                User.class
                        )
        );

Payment System Example

This WebFlux endpoint authorizes a payment without blocking the request thread. The controller returns the pipeline, and Spring subscribes.

@PostMapping("/reservations/{id}/payments")
public Mono<ResponseEntity<PaymentResponse>> pay(
        @PathVariable String id,
        @Valid @RequestBody PaymentRequest request) {
    return paymentService.authorize(id, request)
            .map(response -> ResponseEntity.status(HttpStatus.CREATED).body(response))
            .onErrorResume(ReservationNotFoundException.class, error ->
                    Mono.just(ResponseEntity.notFound().build()));
}

The service can compose repository calls, payment-provider calls, validation, and saving without blocking.

Disney Cruise Example

This endpoint streams boarding pass previews as they are produced. A Flux is a good fit because there may be many reservations for one sailing.

@GetMapping(value = "/sailings/{id}/boarding-passes",
        produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public Flux<BoardingPassPreview> streamBoardingPasses(@PathVariable String id) {
    return boardingService.previewBoardingPasses(id);
}

Instead of waiting to build one giant response, the service can emit items as they become available.

Controller Rules

  • Return Mono or Flux from controllers.
  • Do not call block() in request-handling code.
  • Do not manually call subscribe() in controllers or services.
  • Use map for synchronous DTO transformations.
  • Use flatMap when calling another reactive operation.
  • Use switchIfEmpty for not-found cases.
  • Use onErrorResume for controlled fallback or response mapping.

Reference Answer

Spring WebFlux is Spring's reactive web framework for building asynchronous, non-blocking APIs with Reactor types such as Mono and Flux. It differs from Spring MVC because WebFlux is event-loop based and designed for non-blocking I/O, often using Reactor Netty, while MVC commonly uses a servlet thread-per-request model. WebFlux is a good fit for high-concurrency I/O, streaming, WebSockets, and reactive end-to-end stacks. Blocking is dangerous because event-loop threads are few and shared, so blocking one thread can delay many requests. If blocking code cannot be avoided, isolate it with Mono.fromCallable(...).subscribeOn(Schedulers.boundedElastic()).

Error Handling in Spring WebFlux

Core question: how do you turn reactive failures into consistent HTTP responses without breaking the non-blocking pipeline?

Mental Model

In WebFlux, an error is a Reactor signal. A controller does not usually throw an exception directly to the caller after doing all the work. Instead, the controller returns a Mono or Flux, and an error may appear later while the pipeline is running.

Request
  -> Controller returns Mono
  -> Service calls repository or WebClient
  -> Pipeline emits value, completes empty, or emits error
  -> WebFlux writes HTTP response

That means WebFlux error handling must respect the reactive lifecycle. You handle errors inside the pipeline with Reactor operators, at the controller layer with exception handlers, or globally with WebFlux infrastructure.

Three Places Errors Are Handled

Layer Tool Best Use
Pipeline onErrorResume, onErrorMap, doOnError Translate dependency failures, fallback safely, add logging, or convert low-level exceptions into domain exceptions.
Controller ResponseEntity, switchIfEmpty, local @ExceptionHandler Return endpoint-specific HTTP statuses such as 404, 201, 204, or validation responses.
Global API @RestControllerAdvice or ErrorWebExceptionHandler Centralize consistent JSON error responses, stable error codes, safe messages, and trace IDs.

Empty Is Not the Same as Error

A common WebFlux mistake is treating Mono.empty() like an exception. Empty means the pipeline completed without a value. Error means the pipeline failed. They are different signals and should be mapped intentionally.

Empty Result

repository.findById(id)
        .switchIfEmpty(Mono.error(
                new ReservationNotFoundException(id)
        ));

Use switchIfEmpty when the repository returns no reservation and the API should respond with 404.

Error Result

paymentClient.authorize(request)
        .onErrorMap(WebClientResponseException.class, error ->
                new PaymentProviderException(
                        "Payment provider failed",
                        error
                ));

Use onErrorMap when the pipeline failed and you want to translate a technical exception into a domain exception.

Local Controller Mapping

For simple endpoints, the controller can map expected cases directly. This keeps the response behavior close to the endpoint, but too much error logic in controllers becomes repetitive.

@GetMapping("/{id}")
public Mono<ResponseEntity<CruiseReservationResponse>> getReservation(
        @PathVariable String id) {

    return reservationService.getReservation(id)
            .map(ResponseEntity::ok)
            .onErrorResume(ReservationNotFoundException.class, error ->
                    Mono.just(ResponseEntity.notFound().build()));
}

This is acceptable for a small example. In larger APIs, prefer the service to emit domain exceptions and a global handler to convert those exceptions into consistent HTTP responses.

Service-Level Error Translation

The service layer should know business meaning. It is a good place to translate empty repository results and dependency failures into domain exceptions.

@Service
public class CruiseReservationService {
    private final CruiseReservationRepository repository;
    private final PaymentClient paymentClient;

    public CruiseReservationService(
            CruiseReservationRepository repository,
            PaymentClient paymentClient) {
        this.repository = repository;
        this.paymentClient = paymentClient;
    }

    public Mono<CruiseReservationResponse> getReservation(String id) {
        return repository.findById(id)
                .switchIfEmpty(Mono.error(
                        new ReservationNotFoundException(id)
                ))
                .map(this::toResponse);
    }

    public Mono<CruiseReservationResponse> confirmPayment(
            String reservationId,
            PaymentRequest request) {

        return repository.findById(reservationId)
                .switchIfEmpty(Mono.error(
                        new ReservationNotFoundException(reservationId)
                ))
                .flatMap(reservation ->
                        paymentClient.authorize(reservation, request)
                                .thenReturn(reservation)
                )
                .map(reservation -> reservation.withStatus("CONFIRMED"))
                .flatMap(repository::save)
                .map(this::toResponse)
                .onErrorMap(WebClientResponseException.class, error ->
                        new PaymentProviderException(
                                "Payment provider unavailable",
                                error
                        ));
    }
}

Notice the operator choices: switchIfEmpty handles no reservation, flatMap calls another reactive dependency, map transforms data synchronously, and onErrorMap translates low-level HTTP client failures.

Global Error Response Shape

Production APIs should return consistent error JSON. Clients should not have to parse different structures from every endpoint.

public record ApiErrorResponse(
        String code,
        String message,
        String path,
        String traceId
) {}

A stable error shape helps frontend clients, QA tests, API documentation, logs, alerts, and production support.

Global Handler with RestControllerAdvice

WebFlux supports @RestControllerAdvice. Handler methods can return normal objects, ResponseEntity, Mono<T>, or Mono<ResponseEntity<T>>.

@RestControllerAdvice
public class ApiExceptionHandler {

    @ExceptionHandler(ReservationNotFoundException.class)
    public Mono<ResponseEntity<ApiErrorResponse>> handleNotFound(
            ReservationNotFoundException error,
            ServerWebExchange exchange) {

        ApiErrorResponse body = new ApiErrorResponse(
                "RESERVATION_NOT_FOUND",
                error.getMessage(),
                exchange.getRequest().getPath().value(),
                traceId(exchange)
        );

        return Mono.just(ResponseEntity.status(HttpStatus.NOT_FOUND).body(body));
    }

    @ExceptionHandler(PaymentProviderException.class)
    public Mono<ResponseEntity<ApiErrorResponse>> handlePaymentProvider(
            PaymentProviderException error,
            ServerWebExchange exchange) {

        ApiErrorResponse body = new ApiErrorResponse(
                "PAYMENT_PROVIDER_UNAVAILABLE",
                "Payment is temporarily unavailable",
                exchange.getRequest().getPath().value(),
                traceId(exchange)
        );

        return Mono.just(ResponseEntity.status(HttpStatus.BAD_GATEWAY).body(body));
    }

    @ExceptionHandler(Throwable.class)
    public Mono<ResponseEntity<ApiErrorResponse>> handleUnexpected(
            Throwable error,
            ServerWebExchange exchange) {

        ApiErrorResponse body = new ApiErrorResponse(
                "INTERNAL_ERROR",
                "Unexpected server error",
                exchange.getRequest().getPath().value(),
                traceId(exchange)
        );

        return Mono.just(ResponseEntity
                .status(HttpStatus.INTERNAL_SERVER_ERROR)
                .body(body));
    }

    private String traceId(ServerWebExchange exchange) {
        return exchange.getRequest()
                .getHeaders()
                .getFirst("X-Correlation-Id");
    }
}

The global handler keeps controllers clean and avoids leaking internal details. The response can include a safe message and a trace or correlation ID that lets support engineers connect the client error to logs and traces.

Validation Errors

When a WebFlux controller uses @Valid @RequestBody, invalid input may result in WebExchangeBindException. Handle it globally so validation errors use the same API response style.

@ExceptionHandler(WebExchangeBindException.class)
public Mono<ResponseEntity<ApiErrorResponse>> handleValidation(
        WebExchangeBindException error,
        ServerWebExchange exchange) {

    String message = error.getFieldErrors().stream()
            .map(field -> field.getField() + ": " + field.getDefaultMessage())
            .findFirst()
            .orElse("Request validation failed");

    ApiErrorResponse body = new ApiErrorResponse(
            "VALIDATION_FAILED",
            message,
            exchange.getRequest().getPath().value(),
            traceId(exchange)
    );

    return Mono.just(ResponseEntity.badRequest().body(body));
}

For real APIs, you might return a list of field errors instead of only the first one. The important point is that validation failures are expected client errors, not server failures.

WebClient Error Handling

WebClient is the common non-blocking HTTP client in WebFlux. It does not automatically know your business meaning, so translate dependency responses deliberately.

public Mono<PaymentAuthorization> authorizePayment(
        PaymentAuthorizationRequest request) {

    return webClient.post()
            .uri("/payments/authorizations")
            .bodyValue(request)
            .retrieve()
            .onStatus(HttpStatusCode::is4xxClientError, response ->
                    response.bodyToMono(String.class)
                            .defaultIfEmpty("Payment request rejected")
                            .map(PaymentRejectedException::new)
            )
            .onStatus(HttpStatusCode::is5xxServerError, response ->
                    Mono.error(new PaymentProviderException(
                            "Payment provider returned server error"
                    ))
            )
            .bodyToMono(PaymentAuthorization.class)
            .timeout(Duration.ofSeconds(2))
            .retryWhen(Retry.backoff(2, Duration.ofMillis(200))
                    .filter(this::isTransientFailure))
            .onErrorMap(TimeoutException.class, error ->
                    new PaymentProviderException(
                            "Payment provider timed out",
                            error
                    ));
}

The sequence matters. First map HTTP statuses from the provider, then decode the body, then apply timeout and retry policy. Retries should be limited to transient failures and only used when the operation is safe to retry.

doOnError Is Not Recovery

doOnError is for side effects such as logging or metrics. It does not recover the pipeline. The error still continues downstream.

Logging Only

return reservationService.getReservation(id)
        .doOnError(error ->
                log.warn("Reservation lookup failed: {}", id, error)
        );

The caller still receives the error because doOnError only observes the signal.

Actual Recovery

return reservationService.getReservation(id)
        .onErrorResume(ReservationNotFoundException.class, error ->
                Mono.just(defaultReservationResponse(id))
        );

This changes the outcome by replacing the error with another publisher.

onErrorReturn vs onErrorResume vs onErrorMap

Operator Meaning Example Use
onErrorReturn Replace an error with a fixed value. Return a static fallback flag or default display value.
onErrorResume Replace an error with another reactive publisher. Fallback to cache, return controlled response, or call a backup service.
onErrorMap Convert one exception type into another exception type. Translate WebClientResponseException into PaymentProviderException.
doOnError Observe the error without changing it. Log, increment a metric, or add diagnostic information.

Common Mistakes

  • Calling block() inside an error handler.
  • Using doOnError and expecting it to recover.
  • Returning a successful fallback for a payment or booking failure when the business action did not really complete.
  • Mapping every exception to HTTP 500 instead of separating validation, not found, conflict, dependency, and unexpected failures.
  • Leaking stack traces, SQL messages, hostnames, tokens, or provider response bodies to clients.
  • Retrying non-idempotent operations without an idempotency key.
  • Forgetting that errors inside Flux streams usually terminate the stream unless handled per item.

Flux Item-Level Error Handling

In a Flux, one item can fail and terminate the whole stream if the error is not isolated. If the business rule allows skipping bad items, handle the error inside the per-item operation.

public Flux<BoardingPassPreview> previewBoardingPasses(String sailingId) {
    return reservationRepository.findBySailingId(sailingId)
            .flatMap(reservation ->
                    boardingPassClient.preview(reservation)
                            .onErrorResume(error -> {
                                log.warn(
                                        "Skipping boarding pass preview for reservation {}",
                                        reservation.id(),
                                        error
                                );
                                return Mono.empty();
                            })
            );
}

This design says one failed preview should not stop every other reservation from being streamed. That is a business decision. For payments or state changes, silently skipping failures may be unsafe.

Disney Cruise Reservation Example

This example combines common WebFlux error handling decisions: 404 for a missing reservation, 400 for validation, 502 for payment provider failure, and 500 for unexpected failures.

POST /api/reservations/{reservationId}/payments

Possible outcomes:
201 CREATED
  Payment authorized and reservation confirmed.

400 BAD REQUEST
  Request body failed validation.

404 NOT FOUND
  Reservation id does not exist.

409 CONFLICT
  Reservation is already cancelled or already paid.

502 BAD GATEWAY
  Payment provider failed or timed out.

500 INTERNAL SERVER ERROR
  Unexpected service failure.

The senior-level goal is not just catching exceptions. The goal is giving clients correct status codes, preserving business truth, keeping internal details private, and making failures easy to investigate in production.

Interview Reference Answer

In Spring WebFlux, errors are Reactor signals, so I handle them without blocking and without manually subscribing. I use switchIfEmpty for empty results such as not found, onErrorMap to translate low-level dependency exceptions into domain exceptions, onErrorResume only when a real fallback or controlled response is correct, and doOnError for logging or metrics. For API consistency, I centralize response mapping with @RestControllerAdvice or a global WebFlux error handler, returning stable JSON with an error code, safe message, path, and trace ID. I separate validation errors, not-found errors, conflicts, dependency failures, and unexpected failures into appropriate HTTP statuses. For WebClient, I map provider 4xx and 5xx responses deliberately, configure timeouts, and retry only transient and safe operations.

Reactive Architecture Patterns

Core question: how do you design a WebFlux service so the whole request flow remains non-blocking, composable, observable, and reliable under load?

Mental Model

Reactive architecture is not just returning Mono from a controller. It means the request, service logic, database calls, HTTP clients, messaging, error handling, and tests are designed as a pipeline. Each step describes what should happen when data arrives, when no data exists, or when a failure occurs.

HTTP request
  -> validate input
  -> load current state
  -> call non-blocking dependencies
  -> save result
  -> publish event
  -> return response

Each step returns Mono or Flux.
No step blocks the event loop.

Pattern 1: Thin Reactive Controller

The controller should be boring. It accepts HTTP input, delegates to the service, and returns the reactive publisher. It should not call block(), call subscribe(), or hide business rules inside HTTP code.

@RestController
@RequestMapping("/api/reservations")
public class CruiseReservationController {
    private final CruiseReservationService service;

    public CruiseReservationController(CruiseReservationService service) {
        this.service = service;
    }

    @PostMapping
    public Mono<ResponseEntity<CruiseReservationResponse>> create(
            @Valid @RequestBody CruiseReservationRequest request) {

        return service.createReservation(request)
                .map(response -> ResponseEntity
                        .status(HttpStatus.CREATED)
                        .body(response));
    }
}

The controller does not control execution. Spring WebFlux subscribes to the returned Mono and writes the HTTP response when the pipeline completes.

Pattern 2: Service Pipeline as Business Workflow

The service composes business steps. Use map for synchronous transformation and flatMap when the next step returns another Mono or Flux.

public Mono<CruiseReservationResponse> createReservation(
        CruiseReservationRequest request) {

    return validateSailingIsOpen(request)
            .then(checkDuplicateReservation(request))
            .then(authorizePayment(request))
            .flatMap(payment -> repository.save(toEntity(request, payment)))
            .flatMap(saved -> eventPublisher.publishReservationCreated(saved)
                    .thenReturn(saved))
            .map(this::toResponse);
}

This reads like a workflow, but every step stays asynchronous. The key architectural discipline is that helper methods also return reactive types instead of doing hidden blocking work.

Pattern 3: Sequential Composition

Use sequential composition when one step depends on the result of a previous step. For example, a payment authorization needs the reservation amount, and saving the reservation needs the payment result.

public Mono<CruiseReservationResponse> confirmReservation(String id) {
    return repository.findById(id)
            .switchIfEmpty(Mono.error(new ReservationNotFoundException(id)))
            .flatMap(reservation ->
                    pricingClient.price(reservation)
                            .flatMap(price ->
                                    paymentClient.authorize(reservation, price)
                            )
                            .map(payment ->
                                    reservation.confirm(payment.authorizationId())
                            )
            )
            .flatMap(repository::save)
            .map(this::toResponse);
}

The nested shape is sometimes acceptable, but if it gets too deep, extract methods with meaningful names.

Cleaner Sequential Composition

public Mono<CruiseReservationResponse> confirmReservation(String id) {
    return findReservation(id)
            .flatMap(this::priceReservation)
            .flatMap(this::authorizePayment)
            .flatMap(this::saveConfirmedReservation)
            .map(this::toResponse);
}

This version is easier to read because each method represents one business step. The important rule is that each method must preserve the reactive chain.

Pattern 4: Fan-Out and Fan-In

Reactive services often need to call multiple independent services and combine the results. Use Mono.zip when calls can run at the same time and all results are required.

public Mono<ReservationDetailsResponse> getReservationDetails(String id) {
    Mono<CruiseReservation> reservation = findReservation(id);
    Mono<GuestProfile> guest = guestClient.findByReservationId(id);
    Mono<Itinerary> itinerary = itineraryClient.findByReservationId(id);
    Mono<PaymentSummary> payment = paymentClient.findSummary(id);

    return Mono.zip(reservation, guest, itinerary, payment)
            .map(tuple -> new ReservationDetailsResponse(
                    tuple.getT1().id(),
                    tuple.getT2().fullName(),
                    tuple.getT3().shipCode(),
                    tuple.getT4().status()
            ));
}

This pattern reduces latency when independent calls would otherwise happen one after another. The tradeoff is dependency pressure: under high traffic, fan-out multiplies downstream calls.

Fan-Out Risk

Production risk: if one request calls four services, then 500 incoming requests can become 2,000 downstream calls. Reactive code makes concurrency easier, but it does not remove the need for timeouts, rate limits, bulkheads, retries, and circuit breakers.

Pattern 5: Controlled Concurrency with Flux

Use flatMap with a concurrency limit when processing many items. This protects downstream systems from being flooded.

public Flux<BoardingPassPreview> previewBoardingPasses(String sailingId) {
    return reservationRepository.findBySailingId(sailingId)
            .flatMap(
                    reservation -> boardingPassClient.preview(reservation),
                    20
            );
}

The number 20 means at most twenty boarding pass preview calls are in flight at once. Without a limit, a large sailing could create too many concurrent dependency calls.

flatMap vs concatMap

Operator Behavior Use When
flatMap Runs inner publishers concurrently and may emit results out of order. You want throughput and order does not matter.
flatMap(..., concurrency) Runs concurrently with a maximum number of in-flight operations. You need throughput but must protect downstream systems.
concatMap Runs one inner publisher at a time and preserves order. Order matters or side effects must happen sequentially.

Pattern 6: Reactive Gateway/Aggregator

A common WebFlux use case is an aggregator API. The service calls several backend APIs and returns one response to the client.

@GetMapping("/{id}/summary")
public Mono<ReservationSummary> getSummary(@PathVariable String id) {
    return summaryService.getReservationSummary(id);
}
public Mono<ReservationSummary> getReservationSummary(String id) {
    return Mono.zip(
            reservationClient.getReservation(id),
            guestClient.getGuestForReservation(id),
            itineraryClient.getItinerary(id)
    ).map(tuple -> ReservationSummary.from(
            tuple.getT1(),
            tuple.getT2(),
            tuple.getT3()
    ));
}

This is a strong fit for WebFlux because the service spends most of its time waiting on remote I/O. The event-loop threads stay free while those requests are in progress.

Pattern 7: Fallback to Cache

A fallback is only safe when the response still tells the truth. For read-only summary data, falling back to a cached version may be acceptable. For payment, booking, or inventory state, fake success is dangerous.

public Mono<ReservationSummary> getSummary(String id) {
    return liveSummaryClient.getSummary(id)
            .timeout(Duration.ofSeconds(2))
            .onErrorResume(TimeoutException.class, error ->
                    cachedSummaryRepository.findByReservationId(id)
            );
}

This says: try live data first, but if the live dependency times out, return a cached summary if one exists. The API should make stale data visible if that matters to the client.

Pattern 8: Outbox with Reactive Persistence

When a service saves state and publishes an event, it must avoid saving one without the other. The outbox pattern records the business change and an event record together, then a separate publisher sends the event.

public Mono<CruiseReservationResponse> createReservation(
        CruiseReservationRequest request) {

    CruiseReservationEntity reservation = toEntity(request);
    OutboxEvent event = OutboxEvent.reservationCreated(reservation);

    return transactionalOperator.transactional(
            repository.save(reservation)
                    .then(outboxRepository.save(event))
                    .thenReturn(reservation)
    )
    .map(this::toResponse);
}

The exact transaction support depends on the database and driver. The architectural idea is stable: persist the state change and event intent together, then publish from the outbox with retry and idempotency.

Pattern 9: Reactive Event Publisher

Event publishing should also be part of the pipeline. Avoid manual subscribe() because it hides failures from the request flow and makes tests harder.

Bad

repository.save(reservation)
        .doOnNext(saved ->
                eventPublisher.publish(saved).subscribe()
        )
        .map(this::toResponse);

The publish failure is detached from the main pipeline and may be missed.

Better

repository.save(reservation)
        .flatMap(saved ->
                eventPublisher.publish(saved)
                        .thenReturn(saved)
        )
        .map(this::toResponse);

The publish operation is part of the pipeline, so errors, retries, and tests can observe it.

Pattern 10: Idempotent Reactive Command

Retries happen in distributed systems. A reactive API still needs idempotency for operations that create side effects.

public Mono<CruiseReservationResponse> createReservation(
        String idempotencyKey,
        CruiseReservationRequest request) {

    return idempotencyRepository.findByKey(idempotencyKey)
            .flatMap(existing ->
                    repository.findById(existing.resourceId())
            )
            .switchIfEmpty(
                    createNewReservation(idempotencyKey, request)
            )
            .map(this::toResponse);
}

This prevents duplicate reservations if the client retries after a timeout. In real systems, use conditional writes or unique constraints so two concurrent requests with the same key cannot both create records.

Pattern 11: Boundary for Blocking Code

If a legacy library is blocking, isolate it at the boundary and make that decision obvious. Do not let blocking calls hide inside methods that look reactive.

public Mono<LegacyCabinQuote> quoteCabin(CabinQuoteRequest request) {
    return Mono.fromCallable(() -> legacyCabinClient.quote(request))
            .subscribeOn(Schedulers.boundedElastic())
            .timeout(Duration.ofSeconds(3));
}

This is a bridge pattern, not the ideal end state. The long-term goal is to replace blocking dependencies with non-blocking clients where practical.

Pattern 12: Context Propagation

Reactive code may move across threads. Do not rely only on ThreadLocal for request metadata. Reactor Context can carry values such as correlation IDs through the pipeline.

public Mono<CruiseReservationResponse> getReservation(String id) {
    return Mono.deferContextual(context -> {
        String correlationId = context.getOrDefault(
                "correlationId",
                "missing"
        );

        return repository.findById(id)
                .doOnEach(signal ->
                        log.debug("correlationId={}", correlationId)
                )
                .switchIfEmpty(Mono.error(
                        new ReservationNotFoundException(id)
                ))
                .map(this::toResponse);
    });
}

In Spring applications, tracing libraries often manage this for you, but it is important to understand why context propagation matters in reactive systems.

Architecture Decision Checklist

  • Are all major dependencies non-blocking, or are blocking calls isolated with boundedElastic?
  • Does each service method return a Mono or Flux instead of subscribing internally?
  • Are timeouts set for remote calls?
  • Are retries limited, delayed, and restricted to safe transient failures?
  • Is fan-out concurrency controlled?
  • Are errors translated into domain exceptions and stable API responses?
  • Are write operations idempotent?
  • Are correlation IDs, logs, metrics, and traces preserved across the pipeline?
  • Are tests using StepVerifier and WebTestClient instead of blocking the service code?

End-to-End Disney Cruise Example

This flow creates a reservation, authorizes payment, saves state, writes an outbox event, and returns a response without blocking the WebFlux event loop.

public Mono<CruiseReservationResponse> bookCruise(
        String idempotencyKey,
        CruiseReservationRequest request) {

    return idempotencyRepository.findByKey(idempotencyKey)
            .flatMap(existing ->
                    reservationRepository.findById(existing.resourceId())
            )
            .switchIfEmpty(
                    validateRequest(request)
                            .then(cabinClient.holdCabin(request))
                            .flatMap(hold ->
                                    paymentClient.authorize(request, hold)
                                            .map(payment ->
                                                    toReservation(request, hold, payment)
                                            )
                            )
                            .flatMap(reservation ->
                                    transactionalOperator.transactional(
                                            reservationRepository.save(reservation)
                                                    .flatMap(saved ->
                                                            outboxRepository.save(
                                                                    OutboxEvent.reservationCreated(saved)
                                                            )
                                                            .then(idempotencyRepository.save(
                                                                    idempotencyKey,
                                                                    saved.id()
                                                            ))
                                                            .thenReturn(saved)
                                                    )
                                    )
                            )
            )
            .map(this::toResponse)
            .timeout(Duration.ofSeconds(5))
            .onErrorMap(WebClientResponseException.class, error ->
                    new DependencyFailureException(
                            "Reservation dependency failed",
                            error
                    ));
}

This example shows the main reactive architecture idea: compose the business workflow as one pipeline, keep side effects visible, preserve correctness with idempotency and transaction boundaries, and translate dependency failures intentionally.

Testing the Architecture

A good test proves the pipeline behavior, not just that methods were called. Use StepVerifier to assert success, errors, and completion.

@Test
void bookCruiseShouldReturnExistingReservationForDuplicateKey() {
    when(idempotencyRepository.findByKey("key-123"))
            .thenReturn(Mono.just(new IdempotencyRecord(
                    "key-123",
                    "res-123"
            )));
    when(reservationRepository.findById("res-123"))
            .thenReturn(Mono.just(existingReservation));

    StepVerifier.create(service.bookCruise("key-123", request))
            .assertNext(response ->
                    assertThat(response.id()).isEqualTo("res-123")
            )
            .verifyComplete();

    verifyNoInteractions(cabinClient);
    verifyNoInteractions(paymentClient);
}

The duplicate-key path should not hold another cabin or authorize another payment. That is the kind of behavior a senior engineer protects with tests.

Common Mistakes

  • Returning Mono from the controller while the service secretly blocks.
  • Calling subscribe() inside services to publish events or run side effects.
  • Using unlimited flatMap against a slow dependency.
  • Assuming reactive code automatically improves performance without measuring bottlenecks.
  • Adding retries without idempotency, backoff, jitter, or timeout boundaries.
  • Using stale fallback data for operations that require strong correctness.
  • Losing correlation IDs when execution moves across threads.

Interview Reference Answer

A reactive architecture is more than returning Mono or Flux from controllers. I design the full request path as a non-blocking pipeline: thin controllers, service methods that compose business steps, reactive repositories and WebClient calls, explicit timeout and retry policies, controlled concurrency for Flux processing, and centralized error translation. For independent remote calls, I may use Mono.zip to fan out and combine results, but I watch downstream pressure because concurrency can multiply quickly. For write operations, I design idempotency and transactional boundaries carefully, often using conditional writes or an outbox pattern. I avoid hidden block() and internal subscribe(), preserve correlation IDs, and test pipelines with StepVerifier and APIs with WebTestClient.

Current Disney Cruise reservation slice: WebFlux controller, reactive service, MongoDB reactive repository, DTO validation, domain error, and Reactor unit tests.

Current API Behavior

CruiseReservationService.java

package com.disney.app.disneycruise.service;

import com.disney.app.disneycruise.dto.CruiseReservationRequest;
import com.disney.app.disneycruise.dto.CruiseReservationResponse;
import com.disney.app.disneycruise.entity.CruiseReservationEntity;
import com.disney.app.disneycruise.error.ReservationNotFoundException;
import com.disney.app.disneycruise.repository.CruiseReservationRepository;
import org.springframework.stereotype.Service;
import reactor.core.publisher.Mono;

@Service
public class CruiseReservationService {

    private final CruiseReservationRepository repository;

    public CruiseReservationService(CruiseReservationRepository repository) {
        this.repository = repository;
    }

    public Mono<CruiseReservationResponse> createReservation(
            CruiseReservationRequest request
    ) {
        CruiseReservationEntity entity = new CruiseReservationEntity(
                null,
                request.guestId(),
                request.shipCode(),
                request.sailingDate(),
                request.stateroomType(),
                request.numberOfGuests(),
                "PENDING"
        );

        return repository.save(entity)
                .map(saved -> new CruiseReservationResponse(
                        saved.guestId(),
                        saved.shipCode(),
                        saved.sailingDate(),
                        saved.status()));
    }

    public Mono<CruiseReservationResponse> getReservation(String id) {
        return repository.findById(id)
                .switchIfEmpty(Mono.error(new ReservationNotFoundException(id)))
                .map(entity -> new CruiseReservationResponse(
                        entity.guestId(),
                        entity.shipCode(),
                        entity.sailingDate(),
                        entity.status()));
    }
}
