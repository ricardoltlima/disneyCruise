Core Reactor threading rule:
Reactor does not automatically create a new thread for every pipeline. In ordinary synchronous sources/operators, execution remains on the subscribing/calling thread unless an asynchronous boundary or scheduler changes it.

Schedulers:
- Schedulers.parallel(): CPU-bound work
- Schedulers.boundedElastic(): blocking I/O / legacy blocking APIs
- Schedulers.single(): one shared worker for ordered work
- Schedulers.immediate(): current thread

Blocking work should be isolated from non-blocking event-loop threads.

----------------------------------------------------------------------
fromCallable
----------------------------------------------------------------------

ASSISTANT:
Mono.fromCallable(...) means:
“Create a Mono that will invoke this Callable later, at subscription time, and emit its result; if it throws, emit an error signal.”

A Callable<T> is similar to Supplier<T>, but it may throw checked exceptions.

Example:
Mono<String> mono = Mono.fromCallable(() -> blockingCallThatReturnsString());

Use cases:
- blocking JDBC
- file I/O
- legacy libraries
- imperative methods that return a value and may throw

Important: it is lazy. Nothing runs until subscription.

If the callable throws:
Mono.fromCallable(() -> { throw new RuntimeException("boom"); })
    .onErrorReturn("fallback");

----------------------------------------------------------------------
subscribeOn vs publishOn
----------------------------------------------------------------------

Mental model:
subscribeOn(scheduler):
- controls where subscription/source-side work is scheduled
- commonly used to move a blocking source to boundedElastic

publishOn(scheduler):
- creates a scheduling boundary
- downstream onNext/onComplete/onError processing after that point runs on the chosen scheduler until another boundary changes it

Example:
Mono.fromCallable(this::blockingCall)
    .subscribeOn(Schedulers.boundedElastic())
    .publishOn(Schedulers.parallel())
    .map(this::cpuTask)
    .subscribe();

blockingCall -> boundedElastic
cpuTask -> parallel

USER:
please explain why Only the operators after publishOn move.

ASSISTANT:
Example:
Mono.just("x")
    .map(a -> a)
    .publishOn(Schedulers.parallel())
    .map(b -> b);

Visual model:
SOURCE -> map1 -> [publishOn scheduling boundary] -> map2

publishOn changes downstream signal execution. Upstream operators are not retroactively moved.

At runtime:
Thread A:
1. source emits x
2. map1 processes x
3. publishOn schedules/hands the signal downstream

Parallel scheduler thread:
4. map2 processes x
5. downstream subscriber receives it

Important mental distinction:
An operator invocation does not pause halfway and migrate between threads. A signal is handed across an asynchronous boundary, and downstream processing continues on another worker.

USER:
so the source X just run in a parallel thread? It started in one thread and then moved to another?

ASSISTANT:
No. With publishOn only, the upstream source and operators before publishOn run on the original subscription thread. The signal is then handed off to the scheduler for downstream processing.

Example:
Mono.just("x")
    .map(v -> {
        System.out.println("map1: " + Thread.currentThread().getName());
        return v;
    })
    .publishOn(Schedulers.parallel())
    .map(v -> {
        System.out.println("map2: " + Thread.currentThread().getName());
        return v;
    })
    .subscribe();

map1 -> original thread
map2 -> parallel scheduler thread

just vs fromCallable
----------------------------------------------------------------------

ASSISTANT:
Dangerous:
Mono.just(blockingCall());

blockingCall() executes before Mono.just receives the value, so the call happens immediately during assembly and can block the caller/event-loop thread.

Correct:
Mono.fromCallable(() -> blockingCall());

The method invocation is deferred until subscription.

Safe blocking pattern:
Mono.fromCallable(this::blockingDbCall)
    .subscribeOn(Schedulers.boundedElastic());

fromCallable:
- defers computation
- converts thrown exceptions to onError
subscribeOn(boundedElastic):
- ensures the blocking source executes on a scheduler intended for blocking work

----------------------------------------------------------------------
defer
----------------------------------------------------------------------

ASSISTANT:
Mono.defer(...) means:
“Create the Publisher fresh for each subscription.”

Example:
Mono<Long> m = Mono.just(System.currentTimeMillis());
The timestamp is computed at assembly time and reused.

Mono<Long> m = Mono.defer(() -> Mono.just(System.currentTimeMillis()));
The lambda executes for every subscription, creating a fresh Mono/value.

fromCallable vs defer:
Mono.fromCallable(System::currentTimeMillis)
also evaluates the callable per subscription.

Key distinction:
fromCallable -> defer one computation and turn its result/error into a Mono signal
defer -> defer creation of the Publisher/pipeline itself

Quiz:
A)
Mono<UUID> m = Mono.just(UUID.randomUUID());

B)
Mono<UUID> m = Mono.fromCallable(UUID::randomUUID);

C)
Mono<UUID> m = Mono.defer(() -> Mono.just(UUID.randomUUID()));

USER:
C will return a different value persubscription because it's lazy and a defer creates a fresh pipeline persubscription

ASSISTANT REVIEW:
C is correct, but B is also correct.

A computes UUID.randomUUID() immediately.
B invokes UUID::randomUUID on each subscription.
C creates a fresh Mono containing a newly generated UUID on each subscription.

Interview answer:
“fromCallable defers a single computation, while defer defers creation of the entire reactive Publisher per subscription.”

USER:
error handling

ASSISTANT:
Errors in Reactor are terminal signals:
- onNext
- onComplete
- onError

Core operators:

doOnError:
side effect such as logging; does not recover.

onErrorReturn:
static fallback value.

onErrorResume:
dynamic fallback Publisher; can inspect the exception.

onErrorMap:
transform one exception/error into another.

retry(n):
re-subscribe after failure. retry(2) means original attempt + 2 retries = 3 attempts total.

retryWhen:
retry with strategy/backoff/filtering.

Ordering matters:
Mono.fromCallable(this::callApi)
    .retry(2)
    .onErrorReturn("fallback");

If onErrorReturn comes before retry, the error has already been recovered, so retry sees no failure to retry.

BACKPRESSURE
----------------------------------------------------------------------

USER:
backpressure

ASSISTANT TEACHING:
Backpressure is demand control.

Analogy:
Producer = factory
Consumer = delivery truck

Without flow control, a fast producer can overwhelm a slow consumer.

Reactive Streams demand:
Subscriber requests N.
A compliant Publisher emits no more than the requested demand.

Important:
Backpressure is not the same as buffering.
Buffering is one strategy for dealing with sources/operators that can outpace downstream demand.

Common Reactor strategies:
- onBackpressureBuffer()
- onBackpressureDrop()
- onBackpressureLatest()
- onBackpressureError()

USER:
Backpressure is a mechanism that ensures the reactive consumer to signal demand to a producer, so it can consume data as fast as it is emmited by the producer. It prevents overwhelming consumers and out of memory problems in systems. It cannot prevent kafka or sockets, but it can signs Flux.range the amount of data to be emmited.

ASSISTANT REVIEW:
Core idea correct. Better wording:
“Backpressure allows a reactive consumer to signal demand so a compliant producer emits only as fast as downstream demand allows. This helps prevent overwhelming consumers and uncontrolled buffering.”

Flux.range is demand-aware and can emit according to downstream requests.

For external push systems, flow control depends on the integration/protocol. If the upstream cannot be slowed enough, buffering, dropping, latest-value, pausing/poll control, or errors may be needed.

public class UserService {
    private final UserRepo userRepo;
    private final UserMapper mapper;

    public Mono<User> getUserById(String id) {
        return userRepo.findById(id);
    }

    public Flux<User> getAllUsers() {
        return userRepo.findAll();
    }

    public Mono<User> createUser(CreateUser user) {
        return userRepo.existsById(user.id())
                .flatMap(exists -> {
                    if (exists) {
                        return Mono.error(new RuntimeException("User already exists"));
                    }
                    return userRepo.save(mapper.toEntity(user));
                })
                .onErrorMap(throwable -> new RuntimeException("Error occurred"));
    }

    public Mono<Void> deleteUser(String id) {
        return userRepo.deleteById(id);
    }

    public Mono<String> patchUser(PatchUser user) {
        return userRepo.save(mapper.toEntity(user)).thenReturn(user.name());
    }

    public Mono<String> updateUser(UpdateUser user) {
        return userRepo.save(mapper.toEntity(user)).thenReturn(user.name());
    }
}

Improvements:
1. Repository should persist UserEntity, not DTO User.
2. Map UserEntity -> API/domain User in service.
3. Do not blanket-map every error to RuntimeException/DatabaseException; preserve known domain errors.
4. Duplicate user should use DuplicateUserException.

6. PUT should load existing user and replace intended fields.
7. PATCH should load existing entity, merge provided fields, save.

10. DELETE with Mono<Void> should use thenReturn/then(...) rather than map.
11. DatabaseException should have an explicit handler if used.
12. Validation errors should have a consistent 400 response.

Edge cases identified:
- GET missing -> 404
- DB failure -> 500
- invalid POST -> 400
- duplicate ID/email -> 409
- DELETE missing -> 404 or idempotent 204
- PUT missing -> 404 or documented upsert
- PUT invalid -> 400
- PATCH one field
- PATCH invalid age -> 400
- PATCH missing -> 404
- preserve 404 instead of accidentally converting to 500

@Mapper(componentModel = "spring")

    User toEntity(UpdateUser user);

}

ASSISTANT REVIEW:
The return type is dto.User, so this is DTO -> DTO, not DTO -> entity.

Recommended conceptual mapper:
User toDto(UserEntity entity);

UserEntity toEntity(CreateUser dto);
UserEntity toEntity(UpdateUser dto);

For PATCH, a direct conversion can lose existing values. PATCH is a merge operation.

MapStruct can support partial merge with:
@BeanMapping(nullValuePropertyMappingStrategy = NullValuePropertyMappingStrategy.IGNORE)
void mergePatch(PatchUser patch, @MappingTarget UserEntity target);

Note: if UserEntity is a Java record, in-place @MappingTarget mutation is not suitable because records are immutable. For a record entity, create a new merged UserEntity in the service/mapper instead. If using a mutable entity class, @MappingTarget works naturally.

Reactive programming mental model:
“Describe asynchronous data flows that are lazy, composable, and backpressure-aware.”

Functional programming:
Pure function:
- output depends only on inputs
- no externally observable side effects
- same inputs -> same result

Immutability:
- state does not change after creation
- reduces shared mutable-state problems in concurrent/asynchronous systems

Higher-order functions:
- receive functions or return functions
- map/filter/flatMap accept functional interfaces

Mono:
- 0 or 1 value

Flux:
- 0..N values

Laziness:
- Publisher describes work
- work commonly begins on subscription

just:
- use when you already have a value
- method arguments are evaluated before just() is called

fromCallable:
- evaluate computation at subscription
- exceptions -> onError

defer:
- create Publisher fresh at subscription

subscribeOn:
- schedule subscription/source-side execution

publishOn:
- downstream scheduling boundary

boundedElastic:
- blocking I/O integration

parallel:
- CPU-bound tasks when scheduler isolation is needed

Errors:
- terminal onError signal
- doOnError, onErrorReturn, onErrorResume, onErrorMap, retry/retryWhen

Backpressure:
- downstream demand controls compliant upstream emission
- buffer/drop/latest/error are possible overflow strategies

WebFlux:
- reactive HTTP framework
- Spring subscribes
- don't manually subscribe in controllers
- avoid block()
- isolate unavoidable blocking work
- reactive DB/client libraries usually do not need boundedElastic
